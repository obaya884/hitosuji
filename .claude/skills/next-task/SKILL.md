# 次にやること選出（hitosuji）

作業の手が空いたときに、**いま着手できる候補**をプロジェクト全体から拾い上げ、根拠のある
**推奨1件**を添えて提示するためのワークフロー。オーナーが「次の一手」を素早く選べるように
することが目的。台帳を丸ごと転記するのではなく、**着手可能なものだけに絞り、なぜそれかを
言えるように**して出す。

## 最優先の規律（絶対に飛ばさない）

- **推奨はするが、最終判断はオーナー**。各台帳の「着手トリガ（着手条件）」は運用の実感が要り、
  AI だけでは達成を断定できない。トリガ文は**そのまま添えて**、満たされたかの判断は委ねる
- **挙動レベルの仕様判断はここでしない**。「候補・見極め中」（要件バックログ22）や
  「改善（要仕様整理）」（FB管理簿21）は“着手＝まず実装”ではない。**オーナーとの対話で仕様を
  決め、docs を先に更新する**工程が要る。推奨・提示のときは「これは着手前に仕様判断が必要」と
  明示する（[CLAUDE.md](../../../CLAUDE.md) 最重要ルール）
- **選ぶだけ。実装・編集はしない**。このスキルの成果物は「状況＋候補＋推奨」の提示まで。
  オーナーが選んだら、そこで初めて通常の実装フロー（docs 反映 → 実装 → レビュー）に入る
- **公開リポジトリ配慮**: 提示テキストにオーナーの生活が読み取れる実タスク名・ルーチン名を
  書かない。**ID＋一般的な機能名まで**に丸める（例: FB 本文に具体的な生活の例が混じっていても
  「セクションの時間帯付記」程度の機能説明にとどめる）。台帳の例示と同じ配慮
  （[CLAUDE.md](../../../CLAUDE.md)「public」節）

## 手順

### 1. 状況を集める（読み取り対象）

次を読む。**完了・対応済みを退避した `closed_*` は読まない**（ライブ台帳＝未完了だけを見る）。

- **git 状況** — いま何かの途中か、直近で何を終えたか:
  ```bash
  git -C ~/hitosuji status --short && git -C ~/hitosuji branch --show-current && git -C ~/hitosuji log --oneline -8
  ```
  **実装の WIP**（`src/` 等のコードの未コミット変更）があれば、それは**継続候補の最有力**。
  ただし**区別する**: docs 台帳への起票・状態更新だけの diff（例 `docs/案件/21_…`）や、
  このスキル自身の未追跡ディレクトリ（`.claude/skills/next-task/`）は**実装 WIP ではない**。
  ノイズとして扱い、継続候補に挙げない。直近コミット列からは「今終えたことの自然な続き」が読める
- **FB管理簿21** — `docs/案件/21_ユーザーフィードバック.md`。本書に残るのは `未対応`/`対応中` のみ。
  分類（不具合／改善（軽微）／改善（要仕様整理）／要求／開発環境）ごとに拾う。
  **候補集めは §一覧（ID・起票日・タイトル・状態の索引）だけで足りる**。§詳細の各節は着手対象を
  選んだあとに読む（先に全部読むと出力が長くなり、選ぶ判断も鈍る）
- **要件バックログ22** — `docs/案件/22_要件バックログ.md`。3レーンを区別して読む（下記）。各レーンは
  `ID / タイトル / 熟度 / 内容 / トリガ / 参照` の表で、**トリガ列は必ず埋まっている**（`docs:check` が保証）
- **技術改善バックログ23** — `docs/案件/23_技術改善バックログ.md`。本書に残るのは
  `未着手`/`進行中`/`保留`。**候補集めは §一覧（ID・タイトル・種別・優先度・状態の索引）だけで
  足りる**——優先度（高／中／低／様子見）と種別（内部設計／型安全／テスト／ツール整備／依存追随／
  調査＝**何に触るか**）は索引の列にある。**着手条件（トリガ）は §詳細に
  あるので、候補を数件に絞ってからその節だけを読む**（21 と同じ二段構え）
- **要件定義書§3 現況** — `docs/仕様/12_要件定義書.md` §3。**ここから拾うのは「今の状況」の
  全体モード1行だけ**（例: 継続運用中）。詳細な状態一覧は持たないので、台帳が正

読み取りが広くなる／出力が長くなる場合は、結論だけ受け取れるよう `Explore` サブエージェントに
台帳の棚卸しを委ねてよい（コードの編集は伴わないため委譲して問題ない）。

### 2. 「着手できるもの」に絞る（レーン・状態の意味を使う）

台帳ごとに“いま動かせる”ものの意味が違う。ここを取り違えない。

- **要件バックログ22の3レーン**:
  - 熟度列は 仕様済／設計済／列済／未詰め／`-`。**レーン（決定状態）とは直交する軸**で、
    「やると決めたか」と「仕様が固まっているか」を混同しない
  - `確定・着手待ち` = やると決定済み。仕様が固まっているか着手時展開で足りる。**作業枠が
    空き次第そのまま着手できる**＝最も素直な候補（現状 F-118 等）
  - `候補・見極め中` = 実施可否を運用で判断中。**判断は覆りうる**。“着手”の前に「やると決める＋
    仕様整理」が要る。候補としては挙げるが「まず見極め／仕様判断が必要」と明示する
  - `監視項目` = 作るのではなく観察するもの（N-08 性能確認 等）。**実装候補には入れない**
- **FB管理簿21**:
  - `不具合` = あれば最優先で拾う（破壊操作の誤爆など害の大きいものは特に）
  - `改善（軽微）` = 仕様判断がほぼ不要で画面定義書更新＋実装で完結。**小さい作業枠を埋める好適**
  - `改善（要仕様整理）` = 挙動・デザインの方針をオーナーと決めてから docs 反映 → 実装。
    候補に挙げつつ「着手前に仕様判断」と明示
  - `要求（新規・優先度変更）`= あれば要求定義書起票が絡む。内容次第で扱う
- **技術改善バックログ23**:
  - `未着手` でトリガが今の状況に合いそうなもの、`進行中` の継続を拾う
  - `保留` は根治条件・再確認条件が付いているものが多い（例: 上流の対応待ち）。基本は待ちだが、
    条件が動いていそうなら「再確認どき」として添える
  - 優先度 `高`＞`中`＞`様子見` を目安に

各エントリの**トリガ文はそのまま引く**。「トリガ: 〜」を候補に併記し、達成判断はオーナーへ。

### 3. 出力する（整理＋推奨1件）

次の構成で提示する。**ALWAYS この3ブロック**。

```markdown
## 今の状況
- ブランチ / WIP の有無（何を途中で持っているか）
- 直近コミットから読める「今終えたこと」（1〜2行）
- 全体モード（継続運用中 等、§3から）

## 着手できる候補
台帳ごと・レーンごとにまとめる。各行に「ID 一言・トリガ・（必要なら）仕様判断の要否」を添える。
- **継続（WIP）**: あれば最上段に
- **確定・着手待ち（要件バックログ）**: F-XXX …（トリガ: …）
- **FB（軽微）**: FB-XX …（画面定義書更新＋実装で完結）
- **FB（要仕様整理）**: … ← 着手前に仕様判断が必要
- **候補・見極め中（要件バックログ）**: 全 ID を並べず、**件数＋代表1〜2件**に圧縮する
  （大半はトリガ未達で「今ではない」ため）。← やるならまず見極め・仕様判断
- **技術改善（T-XX）**: … （優先度・トリガ）

## 推奨
→ **これ**。理由（なぜ今これか）を1〜2行。
次点: … / 保留すべきもの: …（あれば、なぜ今ではないか）
```

### 推奨の組み立て方（判断の目安）

“いま最も素直に前に進むもの”を選ぶ。順に当てる:

1. **WIP があれば継続を最優先に推す**（中断した作業を放置しない）
2. **不具合**があれば次点以上に上げる（害の大きさで判断）
3. **確定・着手待ち**の要求（決定済み・優先度順。F-118 は Should ゆえ候補群より上）
4. **軽微な FB**は“小さい作業枠を埋める”のに向く（独立・完結が早い）
   - **3 と 4 が競合したら（WIP も不具合も無い局面）**: 決定済みの「確定・着手待ち」が1件でも
     あればそれを**主推奨**にし、軽微 FB は「短い枠を埋めたいならこちら」と**次点**で速さを訴求する
     （＝“やると決まっているもの”を優先し、軽微 FB は代替として添える）
5. **要仕様整理 / 候補・見極め中**は「まず仕様を決める対話」を推奨アクションにする
   （＝“実装を推す”のではなく“判断の場を持つ”ことを推す）
6. **技術改善 T-XX**はトリガが今の状況に噛み合うとき（例: 直近で該当領域を触った）に上げる

推奨は1件に絞るが、**理由を必ず言う**（軽微・独立・トリガ該当・WIPの続き 等）。オーナーが
別を選べるよう**次点**も1〜2件添える。トリガ達成が微妙なものは「トリガ次第」と正直に書く。

## この手順を使わない例

- 「FB-46 をやろう」など**やる対象が既に決まっている**とき → 選出は不要。通常の実装フロー
  （guide_21 → docs 反映 → 実装 → レビュー）へ直行する
- Dependabot / 依存更新 / 脆弱性アラートの取捨 → `dependabot-triage` スキル
- docs の書き方・台帳の運用ルールそのものの相談 → CLAUDE.md「書き方の規約」を参照
