## 最重要ルール: 仕様変更は docs/ 反映が先

挙動の契約はドキュメント群にある。実装中に挙動レベルの仕様判断が発生した場合、**コードより先に該当ドキュメントを更新する**。どの文書が何の正かは `docs/README.md` の表に従う。

実運用で得たオーナーの気づきは `docs/ユーザーフィードバック.md` に起票してから対応する。**着手時は同ファイルの「着手手順」に従い、要求定義書 → 要件定義書 → 詳細層（画面定義書等）の順に上から判定する**（FB は画面の話として書かれるため、詳細層だけ直して上位文書への反映を忘れやすい。既存の F-XXX / N-XX に収まらない FB は要求定義書に新しい ID を起こす）。

### 書き方の規約

同じ挙動が複数文書に全文で書かれると改訂のたびに食い違う。次を守る。

- **詳細は下位文書に1か所だけ書く**。上位文書は1〜2行の要約＋参照リンクに留める。同じ規則を2か所に書きたくなったら、それは下位に寄せるべき合図
- **判断の経緯（「なぜそうしたか」）は本文に書かず、各文書と同階層の `log_<文書名>.md` へ日付順に積む**。本文は現在の仕様だけを書く。「決めない決定」（スコープ外・保留）も理由付きで記録する
- 完了した事項に `(Phase 2)` のような予定表記を残さない。フェーズの現況は要件定義書と実装計画が持つ
- **プロセスの事故（文書の反映漏れ・重複記述の食い違い等）が起きたら、原因をチェックリスト・規約に変換して該当文書に残す**（事故の実例を添える）

## サブエージェント運用

実装サイクルの各段階で以下へ委譲し、メインセッションのコンテキストを実装そのものに集中させる。読み取り中心・出力が長くなる作業を委譲し、**コードの編集は常にメインセッションが行う**。

| 段階 | 委譲先 | 内容 |
|---|---|---|
| 着手前の調査 | 組み込み `Explore` | 既存コードの把握・影響範囲の特定（結論だけ受け取る） |
| 実装方式の設計 | 組み込み `Plan` | 実装方針の立案・トレードオフ整理 |
| 実装の一区切り | `verifier` | lint / build / テスト等の機械的検証 |
| 実装の一区切り | `code-quality-reviewer` | 可読性・重複・命名・簡潔さの品質レビュー（verifier と並列起動可） |
| 機能の完成時 | `spec-reviewer` | docs/ 仕様書群との整合＋設計原則チェック |
| 機能の完成時 | `test-reviewer` | テスト観点の網羅性・正しさ・カバレッジのレビュー（spec-reviewer と並列起動可） |
| 定期・節目のリファクタ棚卸し | `refactor-scout` | リファクタ観点の診断と T-XX 案の起票（記入はメイン） |
| 節目のプロセス監査 | `process-reviewer` | 開発フローの不変条件（docs 先行・ID参照・契約と経緯の分離等）の遵守監査 |

- **挙動レベルの仕様判断は委譲しない**。オーナーとの対話で決め、docs/ を先に更新する。`Plan` に委譲するのは実装方式レベルの設計のみ
- **実装は原則メインセッションが行う**（会話で決めた文脈を最も必要とする工程のため）。例外: 仕様がドキュメントで完結している自己完結的な純ロジックは、仕様条項を指定して `general-purpose` に実装委譲してよい
- 検証・レビュー系エージェントは独立なので**バックグラウンドで並列起動**し、結果を待つ間に次の作業を進めてよい
- 軽微な変更（typo・文言・1ファイルの小修正）ではエージェントを起動せず、メインセッションで直接 lint/build する
- 指摘への対処（修正）はメインセッションが行い、必要なら同じエージェントに再検証させる
- `refactor-scout` と `process-reviewer` は定常フローに載せず、**契機が来たときに回す**（オーナーの発意・機能をいくつか重ねた節目・負債やフロー乱れの兆候に気づいたとき）

### 実装完了後のフロー（レビュー → 動作確認 → コミット/push）

機能実装が一区切りしたら次の順序を必ず踏む。**サブエージェントのレビューとオーナーの動作確認の両方を経るまで「完了」扱いにしない。**

1. **サブエージェントによるレビュー**: `verifier`・`code-quality-reviewer`・`spec-reviewer`・`test-reviewer` を並列起動し、指摘があればメインセッションで対処する
2. **オーナーによる動作確認**: メインセッションがローカル環境を立ち上げ、**確認手順を提示する**。オーナーが実機で挙動を確認する
3. **コミット / push**: 上記2つを通してからコミットする。<!-- TODO(spec-init): push が本番デプロイに直結する構成なら「push は必ずオーナーの合図を待つ」と明記。そうでなければマージ条件を書く -->

軽微な変更（typo・文言・1ファイルの小修正）は 1・2 を省略してよい。

## 規約

- **コードの変更は必ず Edit / Write ツールで行う**。スクリプトによる一括置換は使わない（変更内容がチャットに差分として表示されず、オーナーがレビューできなくなるため）
- UI文言・ドキュメント・コミットメッセージは日本語
- コミットは Conventional Commits（`feat:` `fix:` `docs:` `chore:` 等）＋日本語サマリ。**本文・サマリに作業項目の ID（F/N/T/FB-XX）を含める**
