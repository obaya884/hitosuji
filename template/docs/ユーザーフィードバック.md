## 運用ルール

1. 気づきはまず本書に**起票**する（粒度はバラバラで良い。会話で出たものは AI が転記する）
2. 起票時に**分類**する: `不具合` / `改善（軽微）` / `改善（要仕様整理）` / `要求（優先度変更含む）` / `開発環境`
   - この分類軸は機能ではなく**仕様判断の要否**。「軽微」は AI が自走でき、「要仕様整理」だけがオーナーとの対話に乗る
3. 対応するときは通常の開発ルールに従う — **挙動レベルの変更は該当仕様書を先に更新**し（下記「着手手順」）、本書には対応結果と参照先だけを残す
4. 状態は `未対応` / `対応中` / `対応済み` / `見送り` の4つ。対応済み・見送りには日付と理由（または反映先）を書く

## 着手手順（FB → 仕様書 → 実装）

FB は「画面・使い勝手の話」として書かれるため、**詳細層の文書だけ直して上位文書に反映し忘れる**事故が起きやすい。着手時は必ず上から順に判定する。

### 手順1: 既存の要求（F-XXX / N-XX）に当てはまるか判定する

`docs/要求定義書.md` の機能要求を検索し、この FB が実現しようとしていることが**既存要求の範囲に収まるか**を確かめる。

- **収まる** → 手順2へ（要求定義書の変更は不要）
- **収まらない** → **要求定義書に新しい ID を起こす**（要求文と優先度のみを表に書く）
- **既存要求の優先度を上げ下げする** → 要求定義書の優先度列の値だけを差し替える

> 理由は表に書かず、要求定義書の決定ログ（`log_要求定義書.md`）へ日付付きで積む（CLAUDE.md「書き方の規約」）。

### 手順2: 要件定義書へ反映する

- 要求IDを**新設・優先度変更**したなら §3 のフェーズ表を必ず直す
- §5 の該当節に、挙動の要件を1行以上書く（画面の詳細ではなく「何がどうなるか」）

### 手順3: 詳細層の文書へ反映する（画面定義書・データモデル定義書等）

- 対象文書の本文（表示要素・操作仕様・データ規則）に詳細を書く
- 画面定義書ならヘッダの「対応要求」行に要求IDを追記する

### 手順4: 実装 → 本書の状態を更新

対応済みにするとき、**どの文書のどこに反映したか**を状態欄に書く。

> チェック: 実装に入る前に「要求定義書 → 要件定義書 → 詳細層」の階層すべてを見たか？ 詳細層しか触っていないなら、手順1の判定を飛ばしていないか確認する。
