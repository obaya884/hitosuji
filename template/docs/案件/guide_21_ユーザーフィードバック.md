# FB 着手手順（FB → 仕様書 → 実装）

- 対象: [ユーザーフィードバック管理簿](./21_ユーザーフィードバック.md)のエントリに着手するときの手順（起票の運用ルールは管理簿側にある）

FB は「画面・使い勝手の話」として書かれるため、**詳細層の文書だけ直して上位文書に反映し忘れる**事故が起きやすい。着手時は必ず上から順に判定する。

## 手順1: 既存の要求（F-XXX / N-XX）に当てはまるか判定する

`docs/仕様/11_要求定義書.md` の機能要求を検索し、この FB が実現しようとしていることが**既存要求の範囲に収まるか**を確かめる。

- **収まる** → 手順2へ（要求定義書の変更は不要）
- **収まらない** → **要求定義書に新しい ID を起こす**（要求文と優先度のみを表に書く）
- **既存要求の優先度を上げ下げする** → 要求定義書の優先度列の値だけを差し替える

> 理由は表に書かず、要求定義書の決定ログ（`log_11_要求定義書.md`）へ日付付きで積む（CLAUDE.md「書き方の規約」）。要件定義書・画面定義書も同様。

## 手順2: 要件定義書・要件バックログへ反映する

- 要求IDを**新設・優先度変更**したなら [要件バックログ](./22_要件バックログ.md) の該当レーンへ反映する
- 要件定義書 §5 の該当節に、挙動の要件を1行以上書く（画面の詳細ではなく「何がどうなるか」）

## 手順3: 詳細層の文書へ反映する（画面定義書・データモデル定義書等）

- 対象文書の本文（表示要素・操作仕様・データ規則）に詳細を書く
- 画面定義書ならヘッダの「対応要求」行に要求IDを追記する

## 手順4: 実装 → 管理簿の状態を更新

対応済みにするとき、**どの文書のどこに反映したか**を状態欄に書き、そのエントリを同じコミットで `closed_21_ユーザーフィードバック.md` へ移す。

> チェック: 実装に入る前に「要求定義書 → 要件定義書 → 詳細層」の階層すべてを見たか？ 詳細層しか触っていないなら、手順1の判定を飛ばしていないか確認する。
