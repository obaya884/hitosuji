# docs/ 文書体系

この docs/ が**挙動の唯一の契約**である。コードと文書が食い違ったら文書が正（コードを直す）。ただし文書に書かれていない挙動判断がコードに必要になったら、**先に文書を直してから**実装する（CLAUDE.md 最重要ルール）。

## 文書の階層と責務

上位ほど抽象的で変更頻度が低い。**詳細は下位文書に1か所だけ書き、上位は1〜2行の要約＋参照リンクに留める**。

| 文書 | 責務（何の「正」か） | 主なID |
|---|---|---|
| [要求定義書](./要求定義書.md) | **何を実現したいか**。機能要求・非機能要求の一覧と優先度 | F-XXX / N-XX |
| [要件定義書](./要件定義書.md) | **何がどうなるか**。システム方式・フェーズ・機能要件・トレーサビリティ | S-XX（画面） |
| [画面定義書/](./画面定義書/)（UI がある場合） | **どう見えるか・どう操作するか**。表示要素・操作仕様・ショートカット | O-X（操作） |
| [データモデル定義書](./データモデル定義書.md)（DB がある場合） | **どう持つか**。スキーマ・導出ロジック・採番規則 | §番号 |
| [アーキテクチャ定義書](./アーキテクチャ定義書.md) | **どう作るか**。レイヤー・依存方向・規約・テスト戦略 | §番号 |
| [実装計画](./実装計画.md) | **いつやるか**。前半=これからの計画 / 後半=完了記録 | — |
| [ユーザーフィードバック](./ユーザーフィードバック.md) | 実運用の気づきの**入力口**。トリアージと着手手順 | FB-XX |
| [技術改善計画](./技術改善計画.md) | **挙動を変えない技術活動**（負債返済・リファクタ・ツール整備）。要求軸と別軸 | T-XX |

## ID体系

すべての作業項目は一意 ID を持ち、コミットメッセージ・会話・文書間参照はこの ID で行う。

- `F-XXX` 機能要求 / `N-XX` 非機能要求（要求定義書が採番。百の位で領域を分けると読みやすい: F-1XX=領域A, F-2XX=領域B, …）
- `S-XX` 画面（要件定義書が採番）
- `O-X` 画面内の操作（各画面定義書が採番）
- `FB-XX` 実運用フィードバック（FB管理簿が採番・通し番号）
- `T-XX` 技術活動（技術改善計画が採番・通し番号）

## 決定ログ（`log_<文書名>.md`）の規約

- 本文には**現在の仕様だけ**を書く。判断の経緯（なぜそうしたか・何を捨てたか）は同階層の `log_<文書名>.md` へ日付順に積む（画面定義書は `docs/画面定義書/log_NN_*.md`）
- 決定ログを持たない文書は、最初のエントリが出た時点で作る。本文側の「決定ログ」節は参照スタブとして残す
- **「決めない決定」も記録する**（スコープ外にした・保留にした・データ設計だけ残した等）。将来再検討しうる前提だけ本文に1行残してよい
- 完了した事項に `(Phase 2)` のような予定表記を残さない。フェーズの現況は要件定義書と実装計画が持つ
