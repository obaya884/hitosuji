# docs/ 文書体系

この docs/ が**挙動の唯一の契約**である。コードと文書が食い違ったら文書が正（コードを直す）。ただし文書に書かれていない挙動判断がコードに必要になったら、**先に文書を直してから**実装する（CLAUDE.md 最重要ルール）。

## ディレクトリと文書番号

docs のファイル名は**全体で一意な2桁番号**を持つ（0X=画面定義書内 / 1X=仕様 / 2X=案件 / 3X=検討。新規文書は該当ブロックの次番号を使う）。`log_` / `closed_` / `guide_` の付属ファイルは親の番号を引き継ぐ（例: `log_23_技術改善バックログ.md`）。役目を終えて凍結した独立文書には `archive_` を前置する（番号はその文書自身のもの。ライブ台帳と対で追記され続ける `closed_` とは区別する）。

### `仕様/`（1X）— 挙動の契約。変更頻度が低く、常に現在形

| 文書 | 責務（何の「正」か） | 主なID |
|---|---|---|
| [11_要求定義書](./仕様/11_要求定義書.md) | **何を実現したいか**。機能要求・非機能要求の一覧と優先度 | F-XXX / N-XX |
| [12_要件定義書](./仕様/12_要件定義書.md) | **何がどうなるか**。システム方式・開発の現況・機能要件・トレーサビリティ | S-XX（画面） |
| [13_画面定義書/](./仕様/13_画面定義書/)（UI がある場合） | **どう見えるか・どう操作するか**。画面ごとに `0X_画面名.md`、共通は `00_共通.md` | O-X（操作） |
| [14_データモデル定義書](./仕様/14_データモデル定義書.md)（DB がある場合) | **どう持つか**。スキーマ・導出ロジック・採番規則 | §番号 |
| [15_アーキテクチャ定義書](./仕様/15_アーキテクチャ定義書.md) | **どう作るか**。レイヤー・依存方向・規約・テスト戦略 | §番号 |

### `案件/`（2X）— ライブ台帳。日常的に読み書きし、小さく保つ

| 文書 | 責務 | 主なID |
|---|---|---|
| [21_ユーザーフィードバック](./案件/21_ユーザーフィードバック.md) | 実運用の気づきの**入力口**。分類（トリアージ）と状態管理。着手手順は [guide_21](./案件/guide_21_ユーザーフィードバック.md) | FB-XX |
| [22_要件バックログ](./案件/22_要件バックログ.md) | **未実装要求の案件管理**。決定状態（レーン）＋熟度タグ＋着手トリガ | — |
| [23_技術改善バックログ](./案件/23_技術改善バックログ.md) | **挙動を変えない技術活動**（負債返済・リファクタ・ツール整備）。要求軸と別軸 | T-XX |

**closed_ 分離ルール**: 台帳の完了・対応済みエントリは、状態更新と同じコミットで同階層の `closed_<文書名>.md` へ原文のまま移す。ライブ台帳には未完了だけを残し、**AI が日常的に読むファイルを小さく保つ**（コンテキスト供給コストの最適化。仕様書の「現在形の契約のみ」と同じ動機）。

### `検討/`（3X）— 設計検討ドキュメント。必要になったとき起こす

方式・設計のトレードオフ整理が台帳エントリの数行に収まらなくなったら、`3X_<テーマ>検討.md` を起こして「詳細は 3X が正」と参照する。決定ログ（過去の判断の記録）とは役割が違い、**これから決めるための比較・分析**を書く。採用が決まったら結論を仕様/台帳へ反映し、検討文書は経緯資料として残る（不要になれば `archive_` 化）。

## ID体系

すべての作業項目は一意 ID を持ち、コミットメッセージ・会話・文書間参照はこの ID で行う。

- `F-XXX` 機能要求 / `N-XX` 非機能要求（要求定義書が採番。百の位で領域を分けると読みやすい: F-1XX=領域A, F-2XX=領域B, …）
- `S-XX` 画面（要件定義書が採番）
- `O-X` 画面内の操作（各画面定義書が採番）
- `FB-XX` 実運用フィードバック（FB管理簿が採番・通し番号）
- `T-XX` 技術活動（技術改善バックログが採番・通し番号）

## 決定ログ（`log_<文書名>.md`）の規約

- 本文には**現在の仕様だけ**を書く。判断の経緯（なぜそうしたか・何を捨てたか）は同階層の `log_<文書名>.md` へ日付順に積む
- 決定ログを持たない文書は、最初のエントリが出た時点で作る。本文側の「決定ログ」節は参照スタブとして残す
- **「決めない決定」も記録する**（スコープ外にした・保留にした・データ設計だけ残した等）。将来再検討しうる前提だけ本文に1行残してよい
- 完了した事項に予定表記（フェーズ語等）を残さない。開発の現況は要件定義書、未実装要求の状態・トリガは要件バックログが持つ
