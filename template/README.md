# 仕様駆動開発テンプレート（spec-driven-template）

AI（Claude Code）と1人の意思決定者で回す、小規模プロダクト向け仕様駆動開発の開始キット。
実プロジェクト（タスク管理アプリ Hitosuji）で「仕様策定3日 → MVP 2日 → 実運用しながら2日でフィードバック39件消化」を実証したフローの汎用化。

このテンプレートの本体はファイル群ではなく、下の**不変条件6か条**である。ファイルはその器にすぎない。

## なぜ効くか（前提となる考え方）

AI 支援開発では、コードを書く速度はもうボトルネックではない。ボトルネックは次の3つに移っている。

1. **意思決定の待ち時間** — 仕様判断が出るまで AI は正しく進めない
2. **検証のコスト** — 生成されたものが正しいかを確かめる手間
3. **AI へのコンテキスト供給** — 何が契約なのかを毎回伝え直す手間

このテンプレートの仕組みはすべて、この3つのどれかを潰すためにある。

- **仕様書＝意思決定のキャッシュ**。一度した判断（しない・決めないという判断を含む）を記録し、再議論をなくす
- **ID体系（F/N/T/FB-XX）＝AI との圧縮された共通言語**。「FB-37 を対応して」が完全な指示として成立する
- **フィードバックのトリアージ＝判断コストによるルーティング**。希少資源（意思決定者の時間）を要判断案件だけに使う
- **サブエージェント分業＝コンテキスト経済**。読み取り中心の作業を逃がし、メインセッションは実装の文脈に集中する

## 不変条件6か条

各条には理由を添える。理由ごと新プロジェクトへ持ち出すこと（理由を失った規約は形骸化する）。すべて実運用の失敗から学ばれた規約である。

| # | 不変条件 | 理由 |
|---|---|---|
| 1 | **挙動の変更は docs/ 反映が先**。コードより先に該当仕様書を更新する | コードは仕様の写像。逆順だと文書が現実からずれ、AI の前提が腐る |
| 2 | **すべての作業項目に一意 ID**（F/N/T/FB-XX）を振り、コミットメッセージで参照する | 会話・仕様書・コミットが同じ座標系で繋がり、指示と探索のコストが激減する |
| 3 | **作業は「仕様判断の要否」でトリアージする**（機能分類ではなく） | 判断不要な作業は AI が自走でき、意思決定者の時間を要判断案件に集中できる |
| 4 | **AI が日常的に読むファイルを小さく保つ**: 仕様書は現在形の契約のみ・経緯は `log_` へ・台帳の完了分は `closed_` へ分離。同じ規則は下位文書の1か所にだけ書く | 契約が短く読みやすく保たれ、コンテキスト供給コストが下がる。重複は改訂のたびに食い違う |
| 5 | **「決めない決定」も理由付きで即日記録する**（スコープ外・保留・将来の退路） | 再議論を防ぎ、後日の拡張点（例: データ設計だけ先に維持）を安全に残せる |
| 6 | **プロセスの事故は規約（チェックリスト）に変換して残す** | フロー自体が運用で改善され続ける。事故の実例を添えると規約が守られやすい |

## 成立条件と縮退運転

このフローは次の4条件の上に成立している。欠ける条件があるときは、フロー全体を捨てず該当行の縮退で代替する。

| 成立条件 | 欠けたときの縮退 |
|---|---|
| 意思決定者が1人で、即応できる | 仕様判断の担当者と回答SLA（例: 24時間以内）を決める。判断待ち案件は FB 管理簿で「要仕様整理」として滞留を可視化する |
| 作った当日から本物の利用でフィードバックが得られる | 社内ドッグフーディングか、週次のユーザーテストで代替。FB 起票の習慣は同じに保つ |
| デプロイ摩擦がほぼゼロ（push ≒ リリース） | リリース列車（定期リリース）を決め、「オーナー動作確認済み」をマージ条件にする |
| docs 全体が AI のコンテキストに収まる規模 | 文書を集約単位で分割し、参照リンクで辿れるようにする（書き方の規約は同じ）。それでも溢れるならプロダクト分割を検討する |

## 適用判断（使う前に確認）

**コード開始前に要求定義書・要件定義書を書き切る期間（目安2〜3日）を取れるか？**

- 取れる → このテンプレートで開始する
- 書こうとしても書けない → それは要求の不確実性が高いシグナル。仕様駆動の前に**探索フェーズ**（仕様書を書かない使い捨てプロトタイプ）を挟み、要求が言語化できるようになってから本テンプレートで作り直す

## 使い方

1. GitHub で「Use this template」からリポジトリを作成する
2. Claude Code を開き、`/spec-init` を実行する（対話で聞き取り、`TODO(spec-init)` プレースホルダをすべて埋め、要求定義書の初版まで作る）
3. 要求定義書 → 要件定義書を書き切ってから実装を開始する（書き切れない場合は上の適用判断へ戻る）
4. 実装開始後は `CLAUDE.md` のフロー（docs 先行・サブエージェント運用・完了フロー）に従う
5. 節目ごとに `process-reviewer` エージェントで不変条件の遵守を監査する

## 構成

docs のファイル名は全体で一意な2桁番号を持つ（0X=画面定義書内 / 1X=仕様 / 2X=案件 / 3X=検討）。付属ファイルは接頭辞で区別する（`log_`=決定ログ / `closed_`=台帳の完了分 / `guide_`=手順書 / `archive_`=凍結文書）。詳細は `docs/README.md`。

```
├── README.md                    ← 本書（プロセス憲章）。新プロジェクトでは自プロダクトの README に置き換え、
│                                   本書は docs/ へ移す
├── CLAUDE.md                    ← AI 向け開発ガイド。プロセス規則は完成済み、プロジェクト固有部は TODO(spec-init)
├── docs/
│   ├── README.md                ← 文書体系の説明（3ディレクトリ・採番・ID体系・log/closed 規約）
│   ├── 仕様/                    ← 挙動の契約（常に現在形）
│   │   ├── 11_要求定義書.md     ← 何を実現したいか（F-XXX / N-XX）
│   │   ├── 12_要件定義書.md     ← 何がどうなるか（S-XX、現況、トレーサビリティ）
│   │   ├── 13_画面定義書/       ← どう見えるか（UI がある場合。不要なら削除）
│   │   ├── 14_データモデル定義書.md ← どう持つか（DB を使う場合。不要なら削除）
│   │   └── 15_アーキテクチャ定義書.md ← どう作るか（レイヤー・依存方向・テスト戦略）
│   ├── 案件/                    ← ライブ台帳（完了分は closed_ へ分離して小さく保つ）
│   │   ├── 21_ユーザーフィードバック.md ← 実運用の気づきの入力口（＋着手手順の guide_21）
│   │   ├── 22_要件バックログ.md ← 未実装要求の案件管理（レーン＋熟度タグ＋着手トリガ）
│   │   └── 23_技術改善バックログ.md ← 挙動を変えない技術活動（T-XX。要求軸とは別軸）
│   └── 検討/                    ← 設計検討ドキュメント（3X。ディレクトリごと必要になったとき作る）
└── .claude/
    ├── settings.json            ← 秘匿情報の閲覧禁止（deny）のみ設定済み
    ├── agents/                  ← verifier / code-quality-reviewer / spec-reviewer /
    │                               test-reviewer / refactor-scout / process-reviewer
    └── skills/spec-init/        ← 立ち上げ用スキル
```
