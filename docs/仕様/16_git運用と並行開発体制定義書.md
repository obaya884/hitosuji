## 1. git 運用ルール

単独作業・並行作業を問わず全作業に適用する。

### 1.1 リスク別ルーティング

変更の種類で入口を分ける。判断に迷ったらリスクの高い側（ブランチ＋PR）に倒す。

| 変更の種類 | 経路 |
|---|---|
| docs・軽微（typo・文言・挙動に触れない小修正） | `main` 直コミット。push（＝本番デプロイ）はオーナーの合図でまとめて行ってよい |
| コード・挙動の変更 | ブランチ → PR → CI 緑 → オーナー動作確認 → **合図でマージ**（マージ＝本番デプロイ） |
| スキーマ変更を含む | 上に加えて「本番へ migrate 適用 → マージ」の順序を厳守（[README](../../README.md)「スキーマ更新（本番マイグレーション）」が正） |

### 1.2 ブランチ命名と worktree／テストDB の対応

- ブランチ名は **`<タスクID>-<slug>`**（すべて小文字、使える文字は `a-z 0-9 -` のみ・**49文字以内**。スラッシュは使わない）。例: `t-26-git-strategy` / `fb-54-section-jump`。長さ上限は、テストDB名（`hitosuji_test_` ＋ 変換後のブランチ名）が PostgreSQL の識別子63バイト制限に収まる値
- タスクID は既存の台帳・要求の ID 体系（T-XX / FB-XX / F-XXX / N-XX）をそのまま使う。ID の無い作業は先に台帳へ起票するのが原則
- スラッシュを使わないのは、ブランチ名を **worktree ディレクトリ名**（`../hitosuji-wt/<ブランチ名>`）と**テストDB名**（`hitosuji_test_<ブランチ名の - を _ に置換>`）へ機械的に変換するため（§3.1）
- **1ブランチ＝1PR。ブランチは使い回さない**。リモートブランチは GitHub の「Automatically delete head branches」（有効化済み）によりマージ時に自動削除される。ローカルブランチはマージ後に削除する——マージ方式は squash（main のログを線形に保つ）のため `git branch -d` はマージを検出できず失敗する。マージ済みを確認のうえ `-D` で消す。**squash 以外はリポジトリ設定で塞いである**（Allow merge commits / Allow rebase merging をいずれも無効化。2026-08-01。条項を読み違えても方式を取り違えられないようにするため——経緯は決定ログ）
- **ブランチは push 済みの main から切る**。squash は派生元からの全差分を1コミットに畳むので、**未 push のコミットが main に残ったまま切ると、その内容まで PR の squash に取り込まれ、マージ後にローカル main が前にも後ろにもずれる**（`gh pr merge` の後処理も `git pull --rebase` も通らなくなる）。並行モードでは `wt:new` が起点を検査して中断する（§3.4・T-46）が、**手で `git checkout -b` するときは同じ検査が働かない**——切る前に `git status` で ahead を見て、あれば先に push する
- `dependabot/*` ブランチはこの命名の対象外

### 1.3 マージ規律

- **push・マージは常にオーナーの合図が前提**。自動マージ・CI 必須チェック化（ブランチ保護）は設けず（T-01 の「検証のみ・手動マージ」方針の継承）、ヘッドエージェントにも自動マージ権を与えない。ワーカーが push できるのは feature ブランチのみ
- **並行時のマージはヘッドがマージキューで逐次調停する**: 1本マージ → 残ブランチを rebase → CI 再走 → 次。スキーマ変更を含むブランチは常に最大1本とし、キューの先頭付近に置く（§3.3）
  - **中間 rebase の省略**: 残ブランチとマージ済みブランチの変更ファイル集合が交わらないことを機械的に確認できたときは、rebase と CI 再走を省略してよい（逐次 rebase を律儀に踏むと N 本で O(N²) 回の CI 再走になり、並行度を上げるほど待ち時間が支配的になるため）。交わるならこの省略はしない（自動マージが通っても意味的に壊れうる）
  - **交わらないことの判定は `npm run wt:overlap` が行う**（T-35）。稼働中のブランチを総当たりし、`git diff --name-only` の積集合が空か検査する（重なるペアはファイル名を、重ならないペアは「省略してよい」を出す）。積集合が空でもマージが衝突する形（ディレクトリとファイルの取り違え・リネーム・削除）があるため、空のペアには `git merge-tree --write-tree` を重ねて掛ける。終了コードは 0＝重なりなし / 1＝重なりあり / 2＝判定できなかった（引数不正・ブランチ不在）。**別ファイルだが前提が壊れる意味的な衝突は検出できない**ので、分割の妥当性そのものは人が見る
- **rebase 後の force push はヘッドが実行する**（`git push --force-with-lease`。オーナーの代行は不要）。素の `git push --force` / `-f` はグローバル設定の deny で塞がれたままで、`--force-with-lease` だけが通る（経緯は決定ログ 2026-07-25）。**lease なしの force は使わない**——リモートに他者の更新があれば失敗して気づけることが防護の本体なので、そこは迂回しない

## 2. 並行開発体制（ヘッド1＋ワーカーN）

並行モードへの切替は**オーナーの明示指示のみ**を契機とする（例「これとこれを並行で」）。既定は常に単独モード（メインセッションが実装・チャット差分でレビュー）で、AI が自律的に切り替える判断基準は設けない。統合経路（ブランチ＋PR＋CI、§1）は両モードで同一なので、どちらで作っても後工程は変わらない。

```
オーナー ←対話→ ヘッドセッション（main 常駐・リポジトリ本体）
                    │ タスク分配・worktree/ブランチ作成・マージ順序調停・共有 docs 記入
                    ├─ worktree A（../hitosuji-wt/<task>）← ワーカー A
                    ├─ worktree B                         ← ワーカー B
                    └─ …
各ワーカー → feature ブランチへ push → PR → CI（lint/build/test）→ ヘッドが順序調停 → オーナー合図でマージ
```

### 2.1 役割と分担

- **ヘッド**: リポジトリ本体（main）に常駐する1セッション。タスク分割と影響範囲の見積り（`Explore` 委譲）、worktree／ブランチの作成・破棄、マージキューの管理、レビュー結果の集約、共有 docs への記入の一元化を担う。**コードは編集しない**
- **ワーカー**: worktree ごとに1つ。実体は Claude Code のサブエージェント（`isolation` で worktree を指定し、`SendMessage` で完了後も往復継続できる）。worktree の内側では CLAUDE.md の運用をそのまま実行する（Explore/Plan → 実装 → verifier・code-quality-reviewer → spec-reviewer・test-reviewer）。オーナーが worktree で別セッションを開いてワーカーにしてもよい
- **1タスク＝1 worktree＝1ブランチ＝1PR**。ブランチ名は §1.2 の命名に従い、worktree ディレクトリ名と一致させる
- **挙動レベルの仕様判断は従来どおりオーナーとの対話でのみ決める**。ワーカーが仕様判断に突き当たったら手を止め、ヘッド経由でオーナーに上げる（docs 先行の最重要ルールは不変）
- 並行モードでは**レビューの正は PR の diff**（ワーカーの編集はヘッドのチャットに差分表示されないため）。**オーナーの動作確認は各 worktree の dev サーバで行う**（固有ポート。§3.2。ヘッドで checkout を切り替えない）

### 2.2 レビューの分担（起動と対処はワーカー・見送りの裁定はオーナー）

- **レビューの起動と指摘への対処はワーカーが行い、見送りの裁定だけをヘッド経由でオーナーが持つ**（T-70）。起動するレビュアーの判定は CLAUDE.md「起動の契機」を worktree 内でそのまま引く（`git diff --name-only` で機械的に決まる）。指摘への対処も CLAUDE.md「サブエージェント運用」冒頭の読み替え規定（並行モードでは「メインセッション」＝各ワーカー）のとおり、ワーカーが自分の worktree で追加コミットとして直す（ヘッドを集約役にすると並行性・実装文脈・ヘッドのコンテキストの3点で損をする。実害の詳細は決定ログ 2026-07-26）
- **指摘へ対処したあとの再検証は、同じレビュアーを `SendMessage` で resume せず、新しく起動する**。ワーカーが起動したレビュアーは呼び出し元へメッセージを返す手段を持たず、resume で頼むと結果がワーカーではなくヘッドへ届くため、ワーカーは返らない返事を待ち続ける（経緯は決定ログ 2026-08-01）
- **ただしワーカーは指摘を自分で見送らない**。完了報告では「対処した」と「見送りたい（＋理由）」を分けて書き、**見送りの可否はオーナーが裁定する**。書いた本人が採否も決めると自己レビューの利益相反になるため、ここだけヘッド経由に残す。`spec-reviewer` が docs の条項に関わる指摘を出した場合も、ワーカーは docs を編集せずエスカレーションする（共有 docs はヘッドが一元記入＝§3.4／挙動レベルの仕様判断は委譲しない）

### 2.3 ワーカーのモデル選択

既定はヘッドからの継承。次の4条件を**すべて**満たすタスクに限り `sonnet` へ落としてよい——①影響が1〜2ファイル・1レイヤに収まる ②仕様が docs に式・表として書き切られており判断の余地が小さい ③既存挙動の書き換えを含まない（追加のみ）④テストで機械的に赤/緑が判定できる。1つでも欠けるなら継承のまま（複数レイヤ縦断／既存 state・分岐の一般化／楽観的更新・Undo のような順序と巻き戻しの意味論が典型）。レビュアー各体は `.claude/agents/*.md` に `model:` を持ち**ワーカーのモデルに依存しない**ため、この判断で安全網は変わらない。

### 2.4 並行度の目標

**4本以上を目標にする**（上限を2〜3に抑える方向は採らない。目標値の根拠と並行4本の実測は決定ログ 2026-07-25）。本数を増やすと**実装ではない工程が律速する**ため、動作確認の並行化（§3.2）・マージキューの CI 再走の抑制（§1.3 の中間 rebase 省略）・ファイル衝突の機械判定（§1.3）・台帳記入の機械化（§3.4）で非実装工程を作り込んで成立させる。

## 3. 共有リソースの分離

worktree はファイルを分けるが、次の4つは worktree を作っただけでは分かれない。全体像と各節の対応:

| 共有リソース | 扱い | 詳細 |
|---|---|---|
| テストDB（db-test コンテナ :5433） | worktree ごとに DB を分ける | §3.1 |
| dev サーバと開発DB（:5432） | サーバは worktree ごとに立てる・DB は共有 | §3.2 |
| Drizzle マイグレーション（ジャーナル＋連番） | 並行させない（スキーマ変更は常に最大1本） | §3.3 |
| 共有 docs（台帳21〜23・`log_*`） | ヘッドが一元記入（文案はワーカー） | §3.4 |

### 3.1 テストDB — worktree ごとに分離

- **unit テストは DB 不要**なので並行しても無干渉
- 統合テストは全テーブル TRUNCATE でリセットする設計（`test-db.ts` の `truncateAll`）のため、複数 worktree が同じ DB を同時に叩くと互いのデータを消し合う。そこで **同一 db-test コンテナ（:5433, tmpfs）内に worktree ごとの DB（`hitosuji_test_<task>`）を持つ**（コンテナ追加・ポート追加なし）
- 仕組み: `scripts/wt-new.sh` が db-test 内に worktree 用 DB を CREATE し、worktree 直下に **`.env.worktree`**（`TEST_DATABASE_URL` 1行。Next.js の自動読み込み対象外の名前）を生成する。`vitest.config.mts` が起動時にこのファイルを読む——ただし**シェルから渡された環境変数が常に優先**（CI は `.env.worktree` が存在しないため完全に無影響）。ワーカーは何も意識せず `npm run test:int` を打てば自分の DB に向く
- worktree 内の統合テストは従来どおり直列（`fileParallelism: false`）。worktree 間は DB が別なので同時実行できる
- **worktree 内の「別プロセスどうし」も排他される**（T-65。ワーカーとそのレビュアーが同時にテストを叩く形が常態のため）。`scripts/with-test-db-lock.sh` がワークツリー単位のロックを取り、取れなければ空くまで待つ。詳細は[テスト戦略定義書](./17_テスト戦略定義書.md) §5

### 3.2 dev サーバは worktree ごと・開発DBは共有

**dev サーバは worktree ごとに固有ポートで立てられる**（T-34）。`wt-new.sh` が 3001 から順に、**他の worktree へ割り当て済みのポート（各 `.env.worktree` の `DEV_PORT`）と使用中のポートの両方を避けて**選び、`.env.worktree` に `DEV_PORT` を書く。`npm run dev`（`scripts/dev.sh`）がそれを読んで `next dev -p` に渡す。2種類のポートを両方避ける理由は決定ログ 2026-07-26（T-40）。本体ワークツリーには `.env.worktree` がないため従来どおり :3000。**起動はオーナーが自分のターミナルで行う**（AI のバックグラウンドから立てたプロセスは30分前後で回収され、長い動作確認が持たない。実測は決定ログ 2026-07-25）。

`.env.local`（`DATABASE_URL` 等）は**本体へのシンボリックリンク**を張る。コピーにしないのは資格情報の実体を1か所に保つため（`.gitignore` の `.env*` でリンクも git から外れる）。

**開発DB（:5432）は本体と共有する**。worktree ごとに複製する案（`createdb -T` は本体が接続中だと失敗し、`pg_dump` は遅い）は採らず、実データの厚みをそのまま使う。**同時に打刻・削除すると互いに干渉する**ため、データを触る確認は1つずつ行う（干渉が実害になったらそのとき分離を足す）。

テストDBは §3.1 のとおり worktree ごとに分離済みで、こちらは同時実行して構わない。

### 3.3 スキーマ変更（Drizzle マイグレーション）は並行不可

マイグレーションはジャーナル＋連番で管理され、複数ブランチで生成すると必ず衝突する。**「スキーマ変更を含むタスクは常に最大1本、かつマージキューの先頭付近に置く」を規約**にする（§1.3）。

### 3.4 共有 docs はヘッドが一元記入

`docs/案件/23_技術改善バックログ.md`・`docs/案件/21_ユーザーフィードバック.md`・各 `log_*.md` は最大の衝突源。**記入はヘッドに一元化**し、ワーカーが触ってよい docs は自タスクの仕様として事前に確定した範囲のみとする。

ただし**文案はワーカーが書く**。完了報告（§4）に、自タスクの台帳エントリの**行そのものの文案**（状態・反映先・オーナー確定事項・実装上の要点）を含めさせ、ヘッドはそれをファイルへ適用する役に徹する（一次情報を本人が書く。記入をヘッドに残すのは `closed_*` への追記衝突の回避——検討の経緯は決定ログ 2026-07-25）。台帳更新にワーカーの持ち主がいないエントリ（他タスクのレビューから派生した新規 FB・並行運用そのものから出た T-XX・オーナーとの対話を記録する `log_*`）はヘッドが書く。

**ヘッドの記入は手編集せずスクリプト経由で行う**（2か所へ分かれたエントリの手編集は事故を起こす。実績は決定ログ 2026-07-25）。

- `npm run ledger:move -- <FB-XX|T-XX> [--status '<新しい状態列>']` — 台帳21・23 のエントリを対応する `closed_*` へ移す。**1エントリは §一覧の行と §詳細の節に分かれており、本スクリプトが両方を移す**（片方の置き忘れが新書式の主な事故）。行の切り出しは ID の完全一致、挿入はテーブルの内側に限る
- `npm run docs:check` — docs 全体の機械検査（旧 `ledger:check`。CI の `docs` ジョブが同じものを回す）。台帳3冊と `closed_*` の表構造（列数・エントリの混入・テーブル内の空行）、台帳21・23 の**一覧の行と詳細節が1対1か・詳細列のリンク先が自分の ID を指すか**、**ライブ台帳に完了エントリが残っていないか**、および docs・CLAUDE.md・README・`.claude/` の**相対リンクとアンカーの実在**を見る（**検査項目の全量はスクリプト冒頭の一覧が正**）。手で触ったあとは必ず通す
- **`ledger:move` の直後は特に効く**——移送は移した側しか直さないので、その ID を指していた他所のリンクがライブ台帳を向いたまま残る（`closed_` へ移すたびに構造的に切れる）。検査はその向き先違いを名指しで出す
- 22 は1エントリが1行に収まるため索引と詳細に分けず、完了時は行を `closed_22` の節形式へ書き下ろす（機械化していない）。移動用スクリプトは持たず、**列の記入漏れ（熟度タグの語彙・トリガ欄の空）を `docs:check` で見る**

## 4. 通信プロトコル

定型の成果物を基本とし、メッセージは例外処理に限定する。ワーカー間のやり取りは設計上ほぼゼロが正常で、**ワーカー同士が直接調整を始めたら「タスク分割が間違っていた」シグナル**として扱い、統合か直列化に倒す。

- **ヘッド → ワーカー（起票時）**: 起動プロンプトで「タスクカード」を渡す。内容＝タスクID／ブランチ名／確定済み仕様の参照（docs の該当節）／触ってよいファイル範囲・触ってはいけない共有 docs／完了条件（lint・build・unit 緑＋push＋報告書式）。ワーカーはヘッドの会話文脈を持たないため、**仕様はすべて docs 参照で自己完結させる**（「仕様は docs が正」の強制にもなる）
- **ワーカー → ヘッド（3種類に限定）**:
  1. **完了報告**（定型）: ブランチ名・変更ファイル一覧・検証結果・仕様上の注意点に加え、**レビュー結果を4点で書く**——①起動した各レビュアーの指摘件数と要旨（1行ずつ）②対処した内容 ③**見送りたい指摘とその理由**（オーナーが裁定する）④再検証の結果と追加コミット。**生のレビュー本文は送らない**（ヘッドのコンテキストは裁定と共有 docs のために温存する）。件数を必ず書かせるのは、`test-reviewer` の沈黙する失敗（T-66。見逃しが「指摘なし」として返る）に対しせめて範囲を観測可能にするため。ヘッドはこれを受けて PR 作成 → CI 確認 → マージキューへ
  2. **仕様質問**（ブロッカー）: 手を止めてターンを終え質問を返す。ヘッドがオーナーに確認 → 必要なら docs を先に直す → SendMessage で回答を返して続行
  3. **中断報告**: 影響範囲が事前見積りを超えた場合。ヘッドがタスクの分割・直列化を再判断
- **ワーカー ↔ ワーカー**: 直接通信は設けない。タスク間の接点は必ずヘッド経由（実体はマージキューでの rebase 調停＝§1.3）

## 5. 運用手順

並行作業1件あたりのヘッドの一連。ワーカーをサブエージェントにする場合も、オーナーが worktree で別セッションを開いてワーカーにする場合も同じ。

1. タスク分割と影響範囲の見積り（`Explore` 委譲）。**影響ファイルが重なるタスクは並行させない**（直列化する）。着手前の見積りは予測なので外れうる。各ブランチに最初のコミットが乗った時点で `npm run wt:overlap` に掛け直し、実差分で検算する
2. `npm run wt:new -- <ブランチ名>` — worktree（`../hitosuji-wt/<ブランチ名>`）＋ブランチ＋`npm ci`＋テストDB＋`.env.worktree` を一括準備。**起点と `origin` のずれはスクリプトが検査する**（既定で `origin` を fetch し、起点が `origin/<起点>` より**進んでいれば中断**——未 push のコミットが全ブランチの PR 差分に写り込むため（T-46）。意図して進める場合だけ `--allow-unpushed`、fetch を省くなら `--no-fetch`。**遅れている場合は警告のみで続行**し、`git pull` するかの判断はオーナーが持つ。非対称の理由は決定ログ 2026-07-26）
3. ワーカーを起動し、タスクカード（§4）を渡す。作業ディレクトリは手順2の worktree を指定する
4. 完了報告を受領 → PR 作成 → CI 緑を確認
5. マージキューで調停: オーナー動作確認（該当 worktree の dev サーバ。§3.2）→ **合図でマージ**（squash）→ 残ブランチを rebase（`npm run wt:overlap` が重なりなしと出たペアは省略可・§1.3）→ CI 再走 → 次
6. `npm run wt:rm -- <ブランチ名>` — worktree・ローカルブランチ・テストDB を後片付け。リモートブランチも削除（§1.2）

## 6. 設けないもの

いずれも過剰抽象回避（アーキテクチャ定義書 §1）と同じ判断軸。

- **自動マージ・ブランチ保護**（§1.3。T-01 で見送った方針の維持）
- **ヘッドからのワーカー自動 spawn**（tmux 等の凝った仕組み。シングルオーナーの規模では、本数によらずオーナーがセッションを開くだけで足りる）
- **worktree ごとの docker compose 複製**（同一インスタンス内の DB 分離で足りる）
- **Agent Teams（Claude Code の実験的機能）の採用**（通信を最小化する本体制ではサブエージェントで必要能力が揃う。選定の経緯は決定ログ 2026-07-23）
