## 1. 学派

古典学派。モック・スタブは原則使わない。domain は本物の値で、リポジトリは本物の PostgreSQL でテストする。

## 2. 偽物を置いてよい境界

差し替え・詰め物を許すのは**プロセス外の依存**だけで、内側の協力者（domain・別コンポーネント・hooks）は必ず本物を使う。許す対象は次の5つに限る。最初の3つは「本物と同じ契約を満たす偽物」であって、呼ばれ方を検証するモックではない。

- **リポジトリ（usecases のテスト）** — Port のインメモリ実装
- **Server Action（コンポーネントテスト）** — `actions.ts` は `"use server"` で、その先は実DB接続とフレームワークの要求スコープ（`revalidatePath`）に届く。**同じ返り値の契約（`ActionResult` / スナップショット）を返す関数**へ差し替える。差し替えの目的は「呼ばれたか」の検証ではなく、**成功・失敗のどちらを返すかを固定して楽観的更新（N-01）とロールバックの両分岐を通すこと**
- **フレームワークのランタイム API（コンポーネントテスト）** — `next/navigation` の `useRouter` 等。アプリのルータ文脈の外では本物が動かないため。**これは画面ごとの判断ではなく段そのものの前提**なので、`src/app/_testing/setup.ts` が全コンポーネントテストへ一括で差し替える（偽物の実体と使い方は `src/app/_testing/next-navigation.ts`）。ナビゲーションを主張するテストだけがそこから import する（遷移先を検証するなら `router`、現在地に応じた描画を見るなら `pathname`）。別の契約が要るテストはファイル側で `vi.mock` を書けば優先される
- **jsdom が実装していないブラウザ API（コンポーネントテスト）** — `window.confirm`・`ResizeObserver`・`Element.prototype.scrollIntoView` 等。上の3つと違い**契約を満たす偽物ですらなく、単に欠落を埋める詰め物**である点に注意——これらの戻り値や副作用に依存した主張を書くと嘘の緑になる（`ResizeObserver` のコールバックを発火しないスタブの上で `offsetHeight` 由来の値を検証する、等）。**差し替えたものは必ず後始末する**（`vi.spyOn` ＋ `restoreAllMocks` を既定とし、`stubGlobal` を使うなら `unstubAllGlobals` を対にする）
  - **段そのものの前提として一括で敷かない**（ルータと違う扱いにする理由）。同じ API でも**ファイルごとに要る契約が違う**——`scrollIntoView` は「描画を通すだけの空実装」と「追従したかを検証する `vi.fn`」の2通りで使われており、一方に寄せるともう一方が嘘の緑になる
- **プロセスの設定と標準エラー出力** — 環境変数（`vi.stubEnv` ＋ `unstubAllEnvs`）と `console`（`vi.spyOn` ＋ `restoreAllMocks`）。どちらもアプリ内部の協力者ではなくプロセスの外側にあり、テストから与える以外に固定する手段がない（`proxy.ts` の認証判定 N-03 が典型）。**ログは「抑制するだけ」で終えない**——黙らせた出力は消えても気づけないので、出ること・出ないこと・値を含まないことのいずれかを主張する

**同じコンポーネントを複数のテストファイルで描くとき（§3 の分割）は、前後処理を画面配下の `_testing/` に置いた登録関数へ畳んでよい**（例: `(daily)/_testing/board-helpers.tsx` の `setupBoard`）。畳めるのは上の対象のうち**そのコンポーネントを描くのに毎回同じ形で要るもの**——詰め物・固定時計・Server Action の既定の返り値・保留の後始末。条件は2つ:

- **契約が同一のものだけ**を畳む。1ファイルでも別の契約が要るなら、そのファイルが自前で敷く（`scrollIntoView` の空実装と `vi.fn` のように、一方へ寄せるともう一方が嘘の緑になる）
- **関数の doc に積むものを列挙する**。呼び出し側からは名前しか見えないので、列挙が「何を差し替えたか」の可視性の代わりになる

## 3. テストピラミッドと段の境界

```
          ／ 手動での実運用確認 ＼        ← E2E相当（自動E2Eは未導入）
        ／  ブラウザテスト（未導入） ＼     ← 実ブラウザ × コンポーネント（幾何・スクロール）
      ／   統合テスト（少数）        ＼    ← リポジトリ実装 × 実DB（db-test）
    ／  コンポーネントテスト（中）     ＼   ← Client Component・hooks × jsdom
  ／    ユニットテスト（多数）           ＼ ← domain 純関数・ユースケース
```

**段の呼び名と境界**: presentation を「自動テスト対象外」と一括りにはしない。**何が測れるかで段が決まる**。

- **ユニットテスト** — 純粋関数。`.tsx` から `.ts` へ切り出したロジック（`_lib/section-options.ts` 等）もここ。最優先で、コンポーネントに紛れ込んだ純粋ロジックは切り出してこの段に落とす
- **コンポーネントテスト** — Client Component と hooks を jsdom 上で描画・操作する。描画結果・イベント応答・状態遷移を見る
- **ブラウザテスト** — 同じコンポーネントを実ブラウザで描画する。**jsdom はレイアウト計算をせず `offsetHeight`・`getBoundingClientRect()` が常に 0 を返す**ため、幾何・スクロール位置に依存する判定はコンポーネントテストでは**嘘の緑**になる。ただし線引きは**ファイル単位ではなく「DOM の実測値を読む箇所」単位**——実測値を引数に取る純関数へ切り出せばユニット段に落とせる（`popover-scroll.ts` が実例）。ブラウザテストに残るのは実測値そのものを読む箇所だけ（未導入。[技術改善バックログ](../案件/23_技術改善バックログ.md) T-03 で管理）
- **E2E** — サーバ・DB まで通す。**async Server Component は Testing Library で描画できない**ため、`page.tsx` 系の検証はここしかない（未導入）

**配置と命名**: テストは対象ファイルの隣に置く（コロケーション）。ユニット `*.test.ts` / コンポーネント `*.test.tsx` / 統合 `*.int.test.ts`。**jsdom を要するテストは対象が `.ts`（hooks 等）でも `.test.tsx` に置く**——拡張子が実行環境を表し、vitest の project 分けと一致する。ブラウザテストを導入するときは `*.browser.test.tsx` を足す。

**1ファイルが読み通せない大きさになったら主題ごとに分割し、`<対象>.<主題>.test.tsx` と名付ける**（例: `daily-board.punch.test.tsx`）。**対象は1つに保つ**——分けるのは主題であって対象ではない。主題は「その名前で説明できる範囲」に絞り、名前から外れるものを同居させない（同居させると、次に読む人がその主題の全量をそのファイルだと誤読する）。**複数のファイルが使う土台は画面配下の `_testing/` へ出す**（§4）。

## 4. テスト補助の置き場

テストからしか使わないコード（フィクスチャ・インメモリ実装・DOM 操作ヘルパー）は `testing/`（domain・usecases・infrastructure）または `_testing/`（`src/app` 配下。Next.js のルーティング対象から外すためのアンダースコア）に置く。`vitest.config.ts` の `coverage.exclude` が両方を計測対象から外している。

- **ブラウザ実機確認（§8）のフィクスチャも同じ置き場**（`src/infrastructure/db/testing/browser-check-fixtures.ts`）。自動テストではないが、**本番へ混ざってはいけない開発用データ**という点は同じで、計測対象からの除外もそのまま効く。初期データ（`seed.ts`）とは分ける——あちらは本番の初期投入に使う[データモデル定義書](./14_データモデル定義書.md) §5 の契約で、確認用フィクスチャは確認観点に従属して変わる
- **ドメインの型を組み立てるものは `src/domain/` の下に1本だけ置き、全層から使う**。集約に属するものは `<集約>/testing/`（`task()`・`routine()`）、集約をまたぐ道具は `shared/testing/`（`atJst()` / `TEST_DATE`）——本体側の `shared/` と同じ切り分け（アーキテクチャ定義書 §2）。domain は最下層なので、どの層から参照しても依存方向に反しない
- **既定値は中立に固定する**（未設定・未打刻・素の並び）。テストが依拠する値は**呼び出し側に書く**——既定を「それらしい値」にすると、本文のどこにも現れない値にテストが寄りかかって読めなくなる。**NOT NULL で中立値が存在しない項目**（ルーチンの繰り返し種別・開始想定時刻など）は最も単純な値を既定に置き、**そこに依拠するテストは値を明示する**
- 「呼び出し側に書く」対象には、**そのテストが通す前提の値**も含む。中立な既定は手前のガード（見積もり未設定など）に引っかかりやすく、**本題に届かないまま緑になる**ことがある。異常系が2本並ぶときは、入力が互いに別物であることを確かめる
- **基準日は `TEST_DATE` 1つ**。曜日そのものに依拠するテストだけが自前の日付を持つ。`taskDate` の既定と、テストがユースケースへ渡す表示日は**同じ定数を参照する**（リテラルで書くと手動同期になる）
- **同じフィクスチャ内の別の値から一意に決まる従属値は、手写しせずフィクスチャ内で導出する**（セクション枠の終了時刻は `sectionRanges` で `SECTIONS` の `startTime` から導く）。テストが前提として選ぶ値ではないので上の「呼び出し側に書く」には当たらない——導出元は同じフィクスチャに残り、どの時間帯かはそこで追える（T-82）
- 画面ごとのデータ・操作ヘルパーは `src/app/<画面>/_testing/` に置く。**そこに置いてよいのは「その画面でしか意味を持たないもの」だけ**（表示単位の組み立て・その画面の表操作・盤面の描画と前後処理）。画面をまたぐ操作は `src/app/_testing/interactions.ts`、jsdom の表記に合わせた期待値の組み立てとクラス判定は同階層の `dom.ts`
  - **行の取り方は共有しない**。表の作りが画面ごとに違うため——デイリーは名前セルが必ずボタンなので役割で引き（`taskRow`）、マスタは有効行がボタン・アーカイブ済み行が素のテキストなので文言で引く（`rowOf`）。共有側に1つ置くと、**引き方の前提が合わない画面で静かに取り違える**（同名の別要素を拾う・行が見つからない）
- **Server Action を呼ぶコンポーネントのテストでは、クリックを `interactions.ts` の `click` に通す**（そのファイルに素の `fireEvent.click` を混ぜない）。押下から応答の解決までを `act` で流し切るので、以降は同期に見てよい。混ぜると**どのクリックを待つかを assert ごとに書き手が判断する**ことになり、待たずに読んだ箇所がフレークになる（T-62 で実際に出した）。**応答を保留したまま「保存中」を主張するテストは `deferredAction`（§2）と組み合わせる**——解決の時点をテストが握れば `waitFor` で待つ必要がなくなり、「解けた」と「そもそも抑止されなかった」を取り違えずに済む
- 同じファイルの中で **Server Action に届かないクリック**（行の選択・トーストを閉じる・一覧の開閉）は `interactions.ts` の `clickWithoutServer` に通す。中身は素の `fireEvent.click` だが、**待つ相手が無いと判断済みであることを名前で示す**ためのもの——**応答の解決まで流し切らない**ぶん同期のまま書け、`click` との使い分けが呼び出し側で読める。素の `fireEvent.click` はどちらの道具にも通さない印になるので混ぜない（T-96）
- **クラスは部分文字列ではなくトークンで見る**——`classList.contains`（または同じことをする `hasClass`）を使い、**`className.toContain` は使わない**（`toContain("bg-accent")` は `hover:bg-accent-weak` にも一致してしまう）。**色の期待値はリテラルで書かずフィクスチャの値から組み立てる**（リテラルだと、挙動が変わっていないのにフィクスチャの色を変えただけで赤くなる）
- **日時は運用タイムゾーンの壁時計（`atJst`）で組む**。アプリは解釈（`applyClockTime`）・導出（`projection`）・表示（`format.ts`）のすべてを `APP_TIME_ZONE` 基準で扱うため（T-47）、テストデータも1本の契約で組めば実行環境の TZ に依らない。**ローカル壁時計で組む道具（旧 `atLocal`）は置かない**——取り違えると JST の手元では通り UTC で走る CI だけが落ちる

## 5. 統合テスト

docker compose の `db-test`（port 5433、tmpfs で使い捨て）に実マイグレーションを適用して実行。テストごとに TRUNCATE でリセット、直列実行。`src/infrastructure/db/testing/` にヘルパーあり。

## 6. 何をどの層でテストするか

- domain: 仕様書の条項（採番規則・導出規則・展開判定）を網羅的にユニットテスト。仕様条項をテスト名に書く
- usecases: ユースケースの手順をユニットテスト（Port はテスト用のインメモリ実装で代替してよい — これはモックではなく「本物と同じ契約を満たす偽物」）
- infrastructure: リポジトリ実装とDB制約を統合テスト
- presentation: **まず純粋ロジックを `.ts` へ切り出してユニットテスト**。残る描画・操作は Client Component と hooks をコンポーネントテスト（jsdom）。幾何依存はブラウザテスト、async Server Component は E2E に委ねる（いずれも未導入のため、その範囲は手動確認＋実運用テストが担保する）
- `proxy.ts`（層の外）: `NextRequest → NextResponse` の純粋関数なので**ユニットテスト**。デプロイ環境（`VERCEL_ENV`）による素通し・認証を要求する環境で資格情報が欠けたときの 500・資格情報の照合・不正な `Authorization` を例外でなく 401 に倒す防御・matcher の対象範囲を固定する（N-03）。**資格情報の値はテストに書かず架空の値を組み立てる**（本リポジトリは public）

## 7. カバレッジ

主指標は「仕様書の条項に対応するテストがあるか」（数値ゲート・合格基準は設けない）。補助として `npm run test:coverage`（`@vitest/coverage-v8`）で行/分岐カバレッジの数値を参照できる。**計測対象は `src` 配下の `.ts` と `.tsx` の両方**（`vitest.config.ts` の `include: ["src/**/*.{ts,tsx}"]`）。presentation も含めるのは、コンポーネントテストで測れるようになった以上、含めないとテストを足した成果と UI 変更の未カバー箇所が数字に出ないため。**本書は全体値の水準を書かない**——数値ゲートが無い（上記）ので水準を定める必要がなく、書けばテストを足すたびに古びる。読み方は下の「カバレッジの参照」のとおり層ごとに見る。テスト観点の網羅・正しさ・カバレッジは `test-reviewer` が、仕様条項⇔テスト存在の照合は `spec-reviewer` が確認する。

- **同一ワークツリーでのカバレッジ計測は同時に1本まで**。vitest は起動時に `coverage/` を消して作り直すため、2本目が始まると1本目の中間結果ごと消えて異常終了する（メインセッションと `verifier` が同時に叩くと起きる。T-58）。`npm run test:coverage` は排他ロックを持つラッパ（`scripts/test-coverage.sh`）で、2本目は理由を表示して即座に落ちる。カバレッジを伴わない `npm test` は無関係で、いつ何本走らせてもよい
- `include` は「**未実行ファイルを走査する範囲**」しか制御しない。テストが読み込んだファイルは `include` に関係なく計上されるため、`.ts` と `.tsx` の片方だけを含めると「テスト済みのファイルだけが分母に入り、未テストのファイルは見えない」非対称集計になる

**カバレッジの参照**: CI は毎回 `test:coverage` を回し、`src` 直下2階層の層（アーキテクチャ定義書 §2 のレイヤー構成）ごとに集計した表を **PR コメント（実行ごとに同じコメントを更新）と Actions のジョブサマリの両方**へ出す（生成は `scripts/coverage-summary.sh`）。**全体値ではなく層ごとの数字で読む**——`src/app` 配下には未着手の段（ブラウザテスト・E2E）に委ねた範囲と、コンポーネントテストが未着手のコンポーネントが混ざるため、全体値はテスト密度の指標にならない。

**変更箇所のカバレッジ**: PR のときは上に加えて「その PR が追加・変更した行のうち計測対象の行」の実行状況と**未カバーの行番号**を出す（`lcovonly` reporter の行データと `base...HEAD` の差分の突き合わせ）。空行・コメント・型宣言は計測対象に無いため分母から自然に落ちる。**`src` 外の変更（docs・scripts・設定）は判定対象にならない**ので、その種の PR は「計測対象なし」と表示される。

## 8. E2E・ブラウザ実機確認

- **E2E**: 未導入。手動確認と実運用で代替している。導入するとしたら Playwright（[技術改善バックログ](../案件/23_技術改善バックログ.md) T-85 で管理）。**ブラウザテスト段（T-03）とは別物**——あちらは部品を実ブラウザに描くだけでサーバもDBも要らない
- **ブラウザ実機確認（テストではない）**: §3 のピラミッドとは別軸の道具。`npm run dev:check` で確認専用DBに向けた dev サーバを立て、`browser-checker`（サブエージェント）が MCP のブラウザツールで**機械的に真偽が決まることだけ**を測る（幾何・スクロール量・クラストークン・フォーカスとキーナビの追従・コンソールとネットワークエラーの不在）。**自動テストではないので回帰の網にはならず、オーナーの動作確認も置き換えない**——その手前で機械判定できる分を潰す道具として、動作確認の直前に走らせる。色・折り返し・見やすさといった知覚の判断は対象外（T-37）

## 9. コマンド

コマンド一覧は CLAUDE.md「開発コマンド」を正とする。テストの実行単位だけ再掲: `npm test`（全件）/ `test:unit` / `test:component` / `test:int`（要 `docker compose up -d db-test`）/ `test:coverage`（排他ロックあり。§7）。

**テストコード自身の型検査は `npm run typecheck`（`tsc --noEmit`）が持つ**。vitest は型を検査せず実行し、`next build` の型検査はアプリのビルドを通る範囲しか見ないため、これを回さないとテストの型は**書いた瞬間から誰の網にもかからない**（T-69 で実際に10件を見落としていた）。CI と `verifier` の手順に載っている。

### 実行タイムゾーン

**CI はテストを UTC と JST の2本で回す**（T-62）。アプリが実際に走るタイムゾーンがその2つだから——Node 段（unit・integration）の本番は Vercel の **UTC**、ブラウザ段（component）の本番はオーナーの端末の **JST**。片方だけだと、もう一方の本番環境をどのテストも通らない。

- CI のジョブ全体は `TZ: UTC` を基準にし、テストだけ `TZ=Asia/Tokyo` でもう一度回す（カバレッジは UTC 側だけで採る）。**2本目も全段を回す**——変えるのは TZ だけで、段では分けない
- **手元は JST なので、CI の UTC 側が「本番のサーバ環境」を受け持つ**。ローカル解釈の日時（`new Date("2026-07-26T10:00")` のようにオフセットを書かない形）を書くと UTC 側だけが落ちる——これは §4 の「`atJst` 1本で組む」の裏返しの網
- 手元で TZ を変えて確かめるときは `TZ=UTC npm test` のように渡す

## 10. 変異テスト

本番コードを1か所だけ壊して、**狙ったテストが赤くなるか**を確かめる。カバレッジ（§7）が「その行を通ったか」しか見ないのに対し、変異テストは「その行を**守っているか**」を見る。**怠っても緑のまま**で誰も気づかないため、実施するかどうかを都度の判断に委ねず、差分で引く。

**実施する差分**（`git diff --name-only` で機械的に決まる。レビューの起動条件（CLAUDE.md「起動の契機」）と同じ引き方）:

- **テストを新規に足したとき** — 足したテストのうち1本を選び、それが守る条件を壊して、そのテストが落ちることを確認する。**差分あたり1回でよい**（足した全部を順に壊す必要はない）。どれを選ぶかは「これが無かったら一番困る」もの
- **種別「内部設計」の T-XX に着手したとき**（挙動を変えないリファクタ）— 既存テストが振る舞い保存の唯一の網なので、その網が効くことを1点確認する（[技術改善バックログ](../案件/23_技術改善バックログ.md)の種別表）

**手続き（誰が・どう壊して戻すか）は CLAUDE.md「規約」が正**（メインセッションが Edit で壊して戻す。`verifier` に委譲できるのは変異後のコマンド実行だけ。経緯は[完了記録](../案件/closed_23_技術改善バックログ.md#t-67) T-67）。

**結果はコミットメッセージ本文に1行残す**（何を壊して何が落ちたか）。台帳や決定ログには積まない——実施頻度が高く、1件ずつ記録する値打ちがない。

**`test-reviewer` が「この変異は検出できない」と指摘したときは、指摘どおり壊して赤くならないことを確かめる**。あの指摘はテストの穴の予告であって実施可否の話ではない。穴が確定したら、その場でテストを足すか T-XX に起こす。

**どこを壊すかを機械に選ばせる網羅的な変異（Stryker 等）は導入していない**（[技術改善バックログ](../案件/23_技術改善バックログ.md) T-68）。
