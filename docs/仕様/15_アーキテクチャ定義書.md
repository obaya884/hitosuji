# Hitosuji（ひとすじ） アーキテクチャ定義書

- 版数: 1.3
- 作成日: 2026-07-19
- 更新日: 2026-08-02
- 上位文書: [要件定義書](./12_要件定義書.md) §2（方式）
- 目的: 実装を迷いなく進めるための、レイヤー構成・DDD規約の判断基準。**このリポジトリのコード配置と依存方向の契約はこの文書が正**（テスト戦略の詳細は[テスト戦略定義書](./17_テスト戦略定義書.md)へ分離。§8 は要点の再掲）

## 1. 基本方針

- クリーンアーキテクチャ（レイヤードアーキテクチャ）に則り、ドメインロジックをフレームワーク・DBから隔離する
- DDD の戦術パターン（値オブジェクト・集約・リポジトリ）を**関数型スタイル**で適用する（§4）
- テストは**古典学派**（モック・スタブは原則使わない）で書き、**テストピラミッド**を保つ（[テスト戦略定義書](./17_テスト戦略定義書.md)）
- オーナー1人のアプリである。層のための層（無意味な DTO 変換・過剰な抽象）は作らない。迷ったら「テストしやすく、仕様書と対応が取れる」方を選ぶ

## 2. レイヤー構成

```
src/
├── domain/          # ドメイン層: 純粋な TypeScript のみ（他レイヤー・FW・DBに依存しない）
│   ├── shared/      #   Result 型などの共通基盤
│   ├── task/        #   集約ごとにフォルダを切る
│   ├── section/
│   ├── routine/
│   ├── mode/
│   └── project/
├── usecases/        # ユースケース層: ユースケース＋Port(IF)
│   └── ports/       #   リポジトリIF（実装は infrastructure）
├── infrastructure/  # インフラ層: Drizzle スキーマ・リポジトリ実装・DB接続
│   └── db/          #   schema.ts / index.ts / migrations / seed.ts / testing/
├── app/             # プレゼンテーション層: Next.js（画面＋Server Actions）
│   ├── _components/ #   全画面で共有するUI（ヘッダ・タブ・アイコン）
│   ├── _lib/        #   全画面で共有するUI補助（整形・ショートカット・スタイル定数・エラー文言辞書）
│   ├── (daily)/     #   デイリー（S-01。URL は「/」。route group で画面単位にまとめる）
│   ├── routines/    #   ルーチン管理（S-02）
│   └── masters/     #   マスタ管理（S-03）
└── proxy.ts         # Basic認証（Next.js の規約ファイル。層の外）
```

画面配下のコード（`_components/` / `_lib/` / `actions.ts`）は**使う画面の直下に置く**（コロケーション）。2つ目の利用者が現れた時点で1つ上の階層へ引き上げる。デイリーは URL が `/` のため、route group `(daily)/` でディレクトリだけを分けている。

ただし**エラー文言辞書は例外で、利用画面が1つでも `_lib/` に置く**（`_lib/error-messages.ts` に全画面分を集める。利用者数で置き場を分けると、文言の流用時に追跡と置き場の判断が壊れるため。T-75）。

| 層 | 責務 | 置くもの / 置かないもの |
|---|---|---|
| domain | 業務ルールの表現と計算 | タスク状態導出・セクション導出・sort_order 採番・終了予定計算・ルーチン展開判定などの純関数。**I/O・日時取得（`new Date()`）・乱数を書かない**（すべて引数で受け取る） |
| usecases | ユースケースの手順 | 「打刻する」「タスクを複製する」等の1操作＝1関数。Port(IF) の定義。**SQL・Drizzle を書かない** |
| infrastructure | 技術詳細 | Drizzle スキーマ（データモデル定義書 §3 と1:1）・リポジトリ実装・接続・シード |
| presentation (src/app) | 画面と入口 | Server Component（表示日1日分＋マスタの読み取り）・Server Actions（更新の入口）・クライアントUI。**業務ルールを書かない** |

domain と usecases の判別基準は1つ: **リポジトリ（I/O）に触るなら usecases、触らない純関数なら domain**。domain にも `punch.ts` のような動詞のファイルが並ぶが、これらはユースケースではなく純粋な判断・生成規則である。

### ファイル命名規約

domain / usecases はドメイン別ディレクトリ（`task/` `routine/` …）が集約を表すため、**ファイル名にディレクトリと同じオブジェクト名を繰り返さない**。概念・動詞を kebab-case でそのまま置く（`task/reorder.ts` `task/edit.ts` `routine/order.ts`。`task/task-reorder.ts` のような重複は作らない）。

- **集約の代表型**を定義するファイルはディレクトリ名と同じにする（`task/task.ts` `routine/routine.ts`）。これは重複ではなくその集約の主役型を指す慣習
- **横断ディレクトリ**（`usecases/ports/` `domain/shared/` `infrastructure/db/repositories/`）は複数ドメインが1ディレクトリに同居するため、識別用のオブジェクト名 prefix を残す（`ports/task-repository.ts` `drizzle-task-repository.ts`）
- usecase ファイルは、**domain 側に同名のファイルがある場合だけ** `-usecases` を付けて区別する（`domain/task/punch.ts` ⇔ `usecases/task/punch-usecases.ts`）。同名がなければ無印にする——`usecases/task/operations.ts`（中断・複製等の束で対応 domain なし）、`usecases/routine/expand.ts`（対応 domain は `expansion.ts` で同名でない）。集約の一般操作を1ファイルにまとめたものは、素直な名前が集約名（`mode.ts`）だが domain の集約代表ファイルと同名衝突するため `-usecases` を付ける（`usecases/mode/mode-usecases.ts`）

### コメントの仕様参照

docs の各文書は独立に `§` 番号を持ち、**同じ字面が文書ごとに別条項を指す**（`§4.2-a` はデータモデル定義書では「明示的な中断での再開タスクの配置」、画面定義書01 では「開始タスク自身の自動セクション移動」）。どちらを指すかを字面から決められる形にする。

- **`src/app` 配下は裸の `§` をその画面の定義書とみなす**——`(daily)` → 画面定義書01 / `routines` → 02 / `masters` → 03 / `review` → 04。既定を決めるのは**画面ディレクトリ**で、その配下の `_components` / `_lib` / `_testing` は同じ既定を継ぐ。`src/app` **直下**の画面をまたぐ場所（`_components` `_lib` `layout.tsx`）だけが 00_共通。**他文書を指すときは必ず文書名を書く**
- **`src/domain` / `src/usecases` / `src/infrastructure` は属する画面が無いので既定が置けない**。ファイル冒頭（または同じ JSDoc ブロック）で指す文書を示し、**1つのファイルが2つ以上の文書の `§` を指すときは、各参照に文書名を書く**——同じ字面が別条項を指す事故はここでだけ起きる（`§4.2-a` はデータモデル定義書と画面定義書01 の両方に実在する）
- **裸の `§` を一律には禁じない**。1文書しか指さないファイルで文書名を繰り返すのは冗長なだけで、曖昧さを減らさない
- 既定外の文書名を書いた直後に同じブロック・数行内で同じ文書を指すときは `同書 §X` で受けてよい（**裸には戻さない**——裸は既定の文書を指すため意味が変わる）
- **`F-XXX` / `N-XX` / `O-XX` は文書名を要さない**（採番が全文書で一意なため）

## 3. 依存方向ルール

```
domain ← usecases ← { infrastructure, presentation }
```

- domain は何にも依存しない（`next` / `react` / `drizzle-orm` / `pg` の import も禁止）
- usecases は domain のみに依存する。DBアクセスは Port(IF) を引数で受け取る（依存性注入）
- infrastructure は domain / usecases（Port の実装のため）に依存できる。presentation には依存しない
- presentation は usecases を呼ぶ。**合成ルート（composition root）として infrastructure のリポジトリ実装をユースケースへ注入する import は許可**
- 以上は `eslint.config.mjs` の `no-restricted-imports` で機械的に強制している

## 4. 関数型DDDの規約

クラスは使わない。RSC / Server Actions のシリアライズ境界（プレーンオブジェクトしか渡せない）をそのまま通すため。

- **エンティティ・値オブジェクト**: `Readonly<{...}>` の type で表現。変更は「新しい値を返す純関数」で行う
- **ID型**: プレーンな `number` のエイリアス（`type TaskId = number`）。ブランド型は導入しない（過剰）。**適用は全層**——domain・Port だけでなく presentation の props・Server Action の引数・`useState` の型でもエイリアスを使う（安全性は増えないが「これはどの ID か」が型で読める）。**例外は ID の種類が静的に決まらない箇所**（例: `field` でモード／プロジェクト／セクションが決まる割り当てハンドラ、マスタ種別を跨いで共通化した部品＝選択ポップオーバー・アーカイブ済み一覧・名前の引き当て・実績の集計軸）で、そこは素の `number` を使う。**テストのビルダー・フィクスチャは対象外**（`Partial<Task>` 側が型を持つので読みの利得がない）だが、**Port 実装は `testing/` 配下（インメモリ）でも対象**——本物と偽物で契約の書き方が割れるため
- **ドメイン関数**: `動詞(対象, 引数) => 新しい値 or Result` の純関数。現在時刻が必要な関数は `now: Date` を引数で受け取る（打刻はクライアント現在時刻、の原則とも整合）
- **エラー方針**: ドメイン・ユースケースの「業務的に起こりうる失敗」は自作の最小 `Result<T, E>`（`src/domain/shared/result.ts`）で返す。throw はインフラの予期外エラー（接続断など）のみ
- **バリデーション**: 業務ルール由来の検証（開始≦終了、有効セクション最低1件など）は domain に置く。入力形式の検証は presentation / usecases で行ってよい
- **Server Action の形**: 「ユースケースを呼ぶ → `if (result.ok) { 反映して成功を返す } else { return failure(文言) }`」に揃え、**戻り値型を明示したうえで早期 return にしない**。早期 return だと失敗側の `return` を落としても関数末尾の `return` が全経路を埋めてしまい型検査を素通りするが、if/else ならどちらの枝が欠けても値を返さない経路ができて `TS2366` で落ちる（戻り値型の注釈が無いと推論に `undefined` が入り、この検査が効かない）。失敗は `src/app/_lib/action-result.ts` の `failure(文言)` だけで作り、**表示文言は呼び出し側が辞書から引く**（打刻・タスク操作は `taskActionErrorMessage` を通す）

## 5. 集約の単位

| 集約 | 内容 | 備考 |
|---|---|---|
| task | tasks 1行 | 打刻・中断・複製・先送りの主体。「実行中は全体で最大1件」は集約を跨ぐ不変条件なのでユースケース＋リポジトリで保証する |
| routine | routines 1行 | 展開判定は domain の純関数、展開INSERTは infrastructure |
| section / mode / project | 各マスタ1行 | アーカイブのみ（物理削除しない） |

## 6. Port（リポジトリIF）

- 置き場所: `src/usecases/ports/`、命名: `TaskRepository` など
- 実装: `src/infrastructure/db/repositories/`、命名: `drizzle-task-repository.ts`
- メソッド粒度は「ユースケースが必要とする操作」単位で定義する（汎用 CRUD を先回りで作らない）

## 7. トランザクション方針

- トランザクション境界は**リポジトリメソッド内**に置く。「割り込み打刻（実行中の終了＋新規開始を1トランザクション）」のような複数行更新は、その操作を1つのリポジトリメソッドとして定義し、実装内で `db.transaction()` を使う
- ユースケース層にトランザクション抽象（UnitOfWork 等）は導入しない（このアプリの規模では過剰）

## 8. テスト戦略

**テスト戦略の正は[テスト戦略定義書](./17_テスト戦略定義書.md)**（2026-07-26 に本節から分離。本節を参照する既存の台帳・完了記録は、同書の同名の節——「偽物を置いてよい境界」「段の呼び名と境界」「テスト補助の置き場」等——で読み替える）。要点:

- **学派**: 古典学派。モック・スタブは原則使わない。domain は本物の値で、リポジトリは本物の PostgreSQL でテストする。偽物を置いてよい境界は**プロセス外の依存**の4つだけ（同書 §2）
- **テストピラミッド**: ユニット（多数）→ コンポーネント（中）→ 統合（少数）→ ブラウザテスト・E2E（未導入）。presentation を「自動テスト対象外」と一括りにせず、**何が測れるかで段が決まる**（同書 §3）
- **配置と命名**: コロケーション。ユニット `*.test.ts` / コンポーネント `*.test.tsx` / 統合 `*.int.test.ts`（同書 §3）。テスト補助は `testing/` / `_testing/` に置く（同書 §4）
- **カバレッジ**: 主指標は「仕様書の条項に対応するテストがあるか」。数値ゲートは設けない（同書 §7）

## 11. 実行環境とバージョン整合

ランタイムとDBの版は、**本番（Vercel / Neon）が決めた版に他をそろえる**。版のピンは複数ファイルに散るため、「何が何に追随するか」は本節を正とする（各ファイルの値そのものは各ファイルが持つ）。

| 対象 | 追随先 | 実体の場所 |
|---|---|---|
| 本番 Node ランタイム | Vercel の既定（＝起点） | Vercel 設定 |
| CI・db-migrate の Node | 本番 Node ランタイム | `.github/workflows/ci.yml` / `db-migrate.yml` |
| `@types/node` | 本番 Node ランタイムのメジャー | `package.json` |
| 本番 PostgreSQL | Neon の提供版（＝起点） | Neon 設定 |
| ローカル開発DB・統合テストDB | 本番 PostgreSQL | `docker-compose.yml` / `ci.yml`（service コンテナ） |
| `pg_dump` / `pg_restore` クライアント | 本番 PostgreSQL 以上 | `scripts/db-backup.sh` / `db-restore.sh` |

- **追い越さない**: 追随側を起点より新しくしない。`@types/node` が先行すると、本番ランタイムに存在しない API を型が許してしまう。DB クライアントだけは例外で、サーバより**古いと dump できない**ため「以上」を満たす最新に寄せる
- **Dependabot に任せきれない**: Dependabot は最新版しか PR にしない（例: ランタイムが 24 系でも `@types/node` は 26 の PR が来る）。追随先に合わせた**中間版へは手動で上げる**。最新版の PR はクローズするだけでは追随が完了しない点に注意する
- 起点（Vercel / Neon）が上がったときは、上表の追随側を**まとめて1コミットで**更新する。起点が上がっていないのに追随側だけを上げる更新（例: 本番が PostgreSQL 17 のまま `docker-compose.yml` だけ 18 にする Dependabot PR）は**クローズする**。`@types/node` の未追随は [技術改善バックログ](../案件/23_技術改善バックログ.md) T-30 で管理する
- **本番 PostgreSQL のメジャー移行**（起点そのものを上げる場合）は、Neon がメジャーの in-place アップグレードに未対応のため（2026-07 時点。要再確認）、新しい版の Neon プロジェクトを作って **dump/restore で移し `DATABASE_URL` を差し替える**作業になる。移行手段は N-06 のバックアップ資産（`scripts/db-backup.sh` / `db-restore.sh`）をそのまま使い、クライアント側を先に新版へ上げてから dump する
