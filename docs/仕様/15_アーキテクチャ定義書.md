# Hitosuji（ひとすじ） アーキテクチャ定義書

- 版数: 1.1
- 作成日: 2026-07-19
- 更新日: 2026-07-21
- 上位文書: [要件定義書](./12_要件定義書.md) §2（方式）
- 目的: 実装を迷いなく進めるための、レイヤー構成・DDD規約・テスト戦略の判断基準。**このリポジトリのコード配置と依存方向の契約はこの文書が正**

## 1. 基本方針

- クリーンアーキテクチャ（レイヤードアーキテクチャ）に則り、ドメインロジックをフレームワーク・DBから隔離する
- DDD の戦術パターン（値オブジェクト・集約・リポジトリ）を**関数型スタイル**で適用する（§4）
- テストは**古典学派**（モック最小・状態検証・実DB使用）で書き、**テストピラミッド**を保つ（§8）
- オーナー1人のアプリである。層のための層（無意味な DTO 変換・過剰な抽象）は作らない。迷ったら「テストしやすく、仕様書と対応が取れる」方を選ぶ

## 2. レイヤー構成

```
src/
├── domain/          # ドメイン層: 純粋な TypeScript のみ（他レイヤー・FW・DBに依存しない）
│   ├── shared/      #   Result 型などの共通基盤
│   ├── task/        #   集約ごとにフォルダを切る
│   ├── section/
│   ├── routine/
│   ├── mode/
│   └── project/
├── usecases/        # ユースケース層: ユースケース＋Port(IF)
│   └── ports/       #   リポジトリIF（実装は infrastructure）
├── infrastructure/  # インフラ層: Drizzle スキーマ・リポジトリ実装・DB接続
│   └── db/          #   schema.ts / index.ts / migrations / seed.ts / testing/
├── app/             # プレゼンテーション層: Next.js（画面＋Server Actions）
│   ├── _components/ #   全画面で共有するUI（ヘッダ・タブ・アイコン）
│   ├── _lib/        #   全画面で共有するUI補助（整形・ショートカット・スタイル定数）
│   ├── (daily)/     #   デイリー（S-01。URL は「/」。route group で画面単位にまとめる）
│   ├── routines/    #   ルーチン管理（S-02）
│   └── masters/     #   マスタ管理（S-03）
└── proxy.ts         # Basic認証（Next.js の規約ファイル。層の外）
```

画面配下のコード（`_components/` / `_lib/` / `actions.ts`）は**使う画面の直下に置く**（コロケーション）。2つ目の利用者が現れた時点で1つ上の階層へ引き上げる。デイリーは URL が `/` のため、route group `(daily)/` でディレクトリだけを分けている。

| 層 | 責務 | 置くもの / 置かないもの |
|---|---|---|
| domain | 業務ルールの表現と計算 | タスク状態導出・セクション導出・sort_order 採番・終了予定計算・ルーチン展開判定などの純関数。**I/O・日時取得（`new Date()`）・乱数を書かない**（すべて引数で受け取る） |
| usecases | ユースケースの手順 | 「打刻する」「タスクを複製する」等の1操作＝1関数。Port(IF) の定義。**SQL・Drizzle を書かない** |
| infrastructure | 技術詳細 | Drizzle スキーマ（データモデル定義書 §3 と1:1）・リポジトリ実装・接続・シード |
| presentation (src/app) | 画面と入口 | Server Component（表示日1日分＋マスタの読み取り）・Server Actions（更新の入口）・クライアントUI。**業務ルールを書かない** |

domain と usecases の判別基準は1つ: **リポジトリ（I/O）に触るなら usecases、触らない純関数なら domain**。domain にも `punch.ts` のような動詞のファイルが並ぶが、これらはユースケースではなく純粋な判断・生成規則である。

### ファイル命名規約

domain / usecases はドメイン別ディレクトリ（`task/` `routine/` …）が集約を表すため、**ファイル名にディレクトリと同じオブジェクト名を繰り返さない**。概念・動詞を kebab-case でそのまま置く（`task/reorder.ts` `task/edit.ts` `routine/order.ts`。`task/task-reorder.ts` のような重複は作らない）。

- **集約の代表型**を定義するファイルはディレクトリ名と同じにする（`task/task.ts` `routine/routine.ts`）。これは重複ではなくその集約の主役型を指す慣習
- **横断ディレクトリ**（`usecases/ports/` `domain/shared/` `infrastructure/db/repositories/`）は複数ドメインが1ディレクトリに同居するため、識別用のオブジェクト名 prefix を残す（`ports/task-repository.ts` `drizzle-task-repository.ts`）
- usecase ファイルは、**domain 側に同名のファイルがある場合だけ** `-usecases` を付けて区別する（`domain/task/punch.ts` ⇔ `usecases/task/punch-usecases.ts`）。同名がなければ無印にする——`usecases/task/operations.ts`（中断・複製等の束で対応 domain なし）、`usecases/routine/expand.ts`（対応 domain は `expansion.ts` で同名でない）。集約の一般操作を1ファイルにまとめたものは、素直な名前が集約名（`mode.ts`）だが domain の集約代表ファイルと同名衝突するため `-usecases` を付ける（`usecases/mode/mode-usecases.ts`）

## 3. 依存方向ルール

```
domain ← usecases ← { infrastructure, presentation }
```

- domain は何にも依存しない（`next` / `react` / `drizzle-orm` / `pg` の import も禁止）
- usecases は domain のみに依存する。DBアクセスは Port(IF) を引数で受け取る（依存性注入）
- infrastructure は domain / usecases（Port の実装のため）に依存できる。presentation には依存しない
- presentation は usecases を呼ぶ。**合成ルート（composition root）として infrastructure のリポジトリ実装をユースケースへ注入する import は許可**
- 以上は `eslint.config.mjs` の `no-restricted-imports` で機械的に強制している

## 4. 関数型DDDの規約

クラスは使わない。RSC / Server Actions のシリアライズ境界（プレーンオブジェクトしか渡せない）をそのまま通すため。

- **エンティティ・値オブジェクト**: `Readonly<{...}>` の type で表現。変更は「新しい値を返す純関数」で行う
- **ID型**: プレーンな `number` のエイリアス（`type TaskId = number`）。ブランド型は導入しない（過剰）
- **ドメイン関数**: `動詞(対象, 引数) => 新しい値 or Result` の純関数。現在時刻が必要な関数は `now: Date` を引数で受け取る（打刻はクライアント現在時刻、の原則とも整合）
- **エラー方針**: ドメイン・ユースケースの「業務的に起こりうる失敗」は自作の最小 `Result<T, E>`（`src/domain/shared/result.ts`）で返す。throw はインフラの予期外エラー（接続断など）のみ
- **バリデーション**: 業務ルール由来の検証（開始≦終了、有効セクション最低1件など）は domain に置く。入力形式の検証は presentation / usecases で行ってよい

## 5. 集約の単位

| 集約 | 内容 | 備考 |
|---|---|---|
| task | tasks 1行 | 打刻・中断・複製・先送りの主体。「実行中は全体で最大1件」は集約を跨ぐ不変条件なのでユースケース＋リポジトリで保証する |
| routine | routines 1行 | 展開判定は domain の純関数、展開INSERTは infrastructure |
| section / mode / project | 各マスタ1行 | アーカイブのみ（物理削除しない） |

## 6. Port（リポジトリIF）

- 置き場所: `src/usecases/ports/`、命名: `TaskRepository` など
- 実装: `src/infrastructure/db/repositories/`、命名: `drizzle-task-repository.ts`
- メソッド粒度は「ユースケースが必要とする操作」単位で定義する（汎用 CRUD を先回りで作らない）

## 7. トランザクション方針

- トランザクション境界は**リポジトリメソッド内**に置く。「割り込み打刻（実行中の終了＋新規開始を1トランザクション）」のような複数行更新は、その操作を1つのリポジトリメソッドとして定義し、実装内で `db.transaction()` を使う
- ユースケース層にトランザクション抽象（UnitOfWork 等）は導入しない（このアプリの規模では過剰）

## 8. テスト戦略

- **学派**: 古典学派。モック・スタブは原則使わない。domain は本物の値で、リポジトリは本物の PostgreSQL でテストする
- **ピラミッド**:

```
        ／ 手動での実運用確認 ＼   ← E2E相当（自動E2Eは未導入）
      ／  統合テスト（少数）    ＼  ← リポジトリ実装 × 実DB（db-test）
    ／   ユニットテスト（多数）   ＼ ← domain 純関数・ユースケース
```

- **配置と命名**: テストは対象ファイルの隣に置く（コロケーション）。ユニット `*.test.ts` / 統合 `*.int.test.ts`
- **統合テスト**: docker compose の `db-test`（port 5433、tmpfs で使い捨て）に実マイグレーションを適用して実行。テストごとに TRUNCATE でリセット、直列実行。`src/infrastructure/db/testing/` にヘルパーあり
- **何をどの層でテストするか**:
  - domain: 仕様書の条項（採番規則・導出規則・展開判定）を網羅的にユニットテスト。仕様条項をテスト名に書く
  - usecases: ユースケースの手順をユニットテスト（Port はテスト用のインメモリ実装で代替してよい — これはモックではなく「本物と同じ契約を満たす偽物」）
  - infrastructure: リポジトリ実装とDB制約を統合テスト
  - presentation: 自動テスト対象外（手動確認＋実運用テストで担保）
- **カバレッジ**: 主指標は「仕様書の条項に対応するテストがあるか」（数値ゲート・合格基準は設けない）。補助として `npm run test:coverage`（`@vitest/coverage-v8`）で行/分岐カバレッジの数値を参照できる。テスト観点の網羅・正しさ・カバレッジは `test-reviewer` が、仕様条項⇔テスト存在の照合は `spec-reviewer` が確認する
- **E2E**: 未導入。手動確認と実運用で代替している。導入するとしたら Playwright（[技術改善バックログ](../案件/23_技術改善バックログ.md) T-03 で管理）
