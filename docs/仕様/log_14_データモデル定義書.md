# データモデル定義書 決定ログ

データ構造・主要ロジックの「なぜそうしたか」を日付順に残す。仕様そのものは[データモデル定義書](./14_データモデル定義書.md)が正。

| 日付 | 決定 | 理由 |
|---|---|---|
| 2026-07-25 | §4.3 の予想開始時刻（F-120）で、実行中タスクの残りは**表示順の位置に依らず**常に起点へ含めることを本文に明記した | 式は元から「実行中の残り」を無条件、「未実行の見積もり」だけを「それより前」と限定して書いていたが、実行中タスクより上に未実行行が並ぶ場合（並び替え後・未分類の残置など）にどう読むかが式だけでは判じにくく、実装時に判断点として浮上した。位置で差し引く読みを採らないのは、そうすると「最後の未実行タスクの予想開始 ＋ その見積もり ＝ 終了予定時刻（F-104）」の恒等式が崩れ、同じ積み上げの途中経過という F-120 の定義（サマリの終了予定と行の予想開始が別勘定になる）と矛盾するため。実装ではこの恒等式をテストで固定した |
| 2026-07-22 | 日界（F-116）を専用の設定テーブルではなく `sections.is_day_start`（有効セクション内でちょうど1件）で表す | 日界は「どのセクションが1日の開始か」の1点であり、設定操作も「セクションを選ぶ」形（画面定義書03 §3.1）。1値のために新テーブル＋リポジトリ＋ポート＋ユースケースを増やすより、既にアプリ層の不変条件（有効最低1件・start_time 重複禁止）を持つ sections にフラグを足す方が構成が小さく、オーナーの捉え方とも一致する。有効内の重複は部分ユニーク索引、最低1件はアプリ層、日界セクションのアーカイブ禁止で担保する |
| 2026-07-25 | weekly に `week_interval`（n週おき。NULL/1=毎週）を追加し、隔週などを表現できるようにした（FB-44 / F-301） | 曜日を持つ weekly と n日ごとの interval の隙間（「特定曜日を n週間隔で」）を埋める。新 recurrence_type を足すと weekly と機能重複するため weekly を拡張。起算は start_date を含む週を第0週とし月曜始まり（datepicker と週の起点を揃える）。既存 weekly 行は NULL=毎週で無変更、次回保存時に 1 が入る |
| 2026-07-25 | `week_interval` の値域を 1〜53 に定め、CHECK を `BETWEEN 1 AND 53` にした（FB-44） | weekly は本質的にサブ年のリズムを表す道具で、意味のある最大間隔は「約年1回」。1年が触れうる最大週数=53を上限とし、それ以上（数年に一度）は weekly では表さない。上限は誤入力（530 等）の防御も兼ねる。0003 適用後の追い CHECK 変更のため migration を分けた（0004） |
| 2026-07-26 | §3.5・§4.4 の振り直しの範囲を「その日の中で全体／当日分」から「**挿入先（移動先）のセクション内**」へ訂正した（T-50） | `sort_order` の集約作業で `spec-reviewer` が実装との齟齬として報告し、検算したところ**文言のほうが不正確**だった。根拠3点: ①`daily-list.ts` は `tasks.filter(t => t.sectionId === section.id)` してから `sortOrder` で並べており、**`sort_order` はセクション内でしか比較されない**（表示順は「セクション（start_time 順）→ `sort_order`」） ②§3.5 自身が「末尾追加・ルーチン展開: **セクション内**最大値 +1000」と書いており、採番がセクション単位なのに振り直しだけ日単位というのは内部矛盾 ③スキーマに `sort_order` の一意制約が無いので、セクションをまたいで値が重なっても害がない。日単位で振り直しても意味がなく書き込みが増えるだけなので、**実装（セクション単位）が正しい**。なお「その日の中で」という表現は、おそらく「日をまたがない」（`sort_order` は `task_date` ごとに独立）を意図した書き方が、範囲の限定と読めてしまったもの。**挙動は変えていない**——実装は旧来どおりで、条項の記述だけを実態へ寄せた |
