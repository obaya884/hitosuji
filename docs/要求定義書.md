## 1. 背景

TaskChute Cloud（以下 TCC）は、日本発の時間管理メソッド「タスクシュート時間術」の公式クラウドツールである。2024年8月に後継版「TaskChute Cloud 2」（以下 TCC2）がリリースされ、旧版は2025年1月にサービス終了、既存ユーザーはTCC2への移行を余儀なくされた。

TCC2への移行に伴い、以下のような変化が発生した。

- UI・操作体系が旧版から大きく変わり「別物」となった（タスク追加の操作性、ショートカットキーの挙動などへの不満が報告されている）
- 旧版の機能が完全には移行されていない
- 料金が大幅に値上げされた（年額 4,860円 → 12,980円）

本プロジェクトのオーナー（＝本アプリの主たる利用者）も、このサービス変更によりUIが使いづらくなったと感じており、**自分の使い方に最適化したTCCクローンアプリ「Hitosuji（ひとすじ）」を自作する**ことを決めた。

## 2. 目的

- タスクシュート時間術を日々実践するための、自分にとって使いやすいツールを手に入れる
- 旧TCC（またはTCC2の良い部分）の使用感を再現しつつ、不満点を解消する
- 自作アプリとすることで、外部サービスの仕様変更・値上げ・終了リスクから独立する

### 2.1 成功基準（案）

- 日常のタスク管理をTCC2から本アプリへ完全に移行できる
- 1日の運用（プラン作成 → 実行・記録 → 振り返り）が本アプリだけで完結する（振り返りは、初期は過去日付のタスクリスト閲覧（F-106）で代替できれば良い → §6.5 注記参照）
- タスクの開始・終了などの高頻度操作がストレスなく行える

## 3. 対象ユーザーと利用シーン

- **対象ユーザー**: プロジェクトオーナー本人（シングルユーザー前提。将来的な他者への公開は現時点ではスコープ外）
- **利用シーン**:
  - 朝（または前日夜）: 当日のタスクリストを確認・調整するプラン作業
  - 日中: タスクの開始・終了を記録しながら1日を進める（1日に数十回の高頻度操作）
  - 夜: 1日のログを振り返るレビュー作業
- **利用環境**: PC（ブラウザ）がメイン。私用PC・業務PCなど**複数のPCから同一データにアクセス・操作**できること。スマートフォン対応は必須としない

## 4. 前提知識: タスクシュート時間術の概要

本アプリが実装対象とするメソッドの骨子。要求の妥当性判断の基準となる。

### 4.1 3つの基本要素とサイクル

| 要素 | 内容 |
|---|---|
| **プラン** | 1日の初めに、今日実行するタスクを実行順に並べ、各タスクに見積もり時間を設定した「今日1日のタスクリスト」を作る |
| **ログ** | タスクを「完了チェック」するのではなく、開始時刻・終了時刻を記録する。プランは実行とともに実績記録に変わる |
| **ルーチン** | 定期的に繰り返すタスクをあらかじめ登録しておき、指定スケジュールで自動的にプランへ展開する |

この3要素は循環する: **プランがログになり、ログからルーチンが生まれ、ルーチンが未来のプランを作る。**

### 4.2 メソッドの特徴的な仕組み

- **終了予定時刻の自動計算**: 現在時刻に残タスクの見積もり時間を積み上げ、「このままいくと今日は何時に終わるか」を常に表示する。タスクシュート最大の特徴
- **セクション**: 1日を時間帯（例: 朝・午前・午後・夜）で区切り、タスクを配置する枠として使う
- **モード / プロジェクト**: タスクの分類軸（詳細は §4.3）
- **先送りゼロ**: ①1日の初めに今日やることを決める、②1日の終わりに先送りした数を数える、③1分でも手をつけたら「先送り」にしない、という3ルール

### 4.3 モードとプロジェクトの意味と使い分け

タスクシュートでは、同じ「分類」でもモードとプロジェクトは役割が明確に異なる。

|  | モード | プロジェクト |
|---|---|---|
| **意味** | 自分の**動作・活動の種類**を表す（タスクを「どうやるか」） | 1つの**ゴールに向かう複数タスクのまとまり**（タスクが「何のためか」） |
| **例** | 執筆、読書、集中作業、単純作業、ミーティング、休憩、移動、睡眠 | 資格取得（講義受講→宿題→試験）、転職活動、ブログ運営 |
| **主な目的** | **1日の流れの組み立て**。集中作業・単純作業・気分転換をバランスよく交互に配置する基準になる。色分けによりリスト上で1日の構成が視認できる | **タスクの抜け漏れ防止**。ゴールに必要なタスク群を束ねて進捗を追う |
| **性質** | 1タスクに1つ。有限個の固定的なカテゴリ | ゴールに到達すれば完了する（終わりがある）。ただし「暮らし」のような完了しない受け皿的プロジェクトを併用する運用もある |

両者は直交する軸であり、1つのタスクに両方を設定できる。例: タスク「ブログ記事を書く」→ プロジェクトは「ブログ運営」（何のため）、モードは「執筆」（どんな動作）。

**運用上の指針（実践者の知見）**:
- プロジェクトは「実行を忘れたら困るタスク群」に絞って作る。粒度を細かくしすぎると管理負荷が上がる
- モードは1日のレビュー時に「どの種類の活動に時間を使ったか」を見る単位にもなる（F-503 の集計軸）

## 5. 現状の課題（本アプリで解消したいこと）

| # | 課題 | 出所 |
|---|---|---|
| C-1 | 旧TCCはシンプルなリストで良かったのに、TCC2で下手にUIがリッチになった | オーナー |
| C-2 | TCC2で動作速度が遅くなった | オーナー |
| C-3 | 気に入っていたショートカット操作がTCC2で使いづらくなった | オーナー |
| C-4 | 外部サービスの仕様変更に振り回される（旧版強制終了の経験） | オーナー |
| C-5 | 料金が高い（年額12,980円） | オーナー / Web上の評判 |

→ 本アプリのUI・操作感は**旧TCC（TaskChute Cloud 1）を基準**とし、「シンプルなリスト・高速動作・キーボードショートカット」を設計の柱とする。

## 6. 機能要求

優先度: **Must**（ないと移行できない） / **Should**（早期に欲しい） / **Could**（将来的に検討） / **対象外**（実装しないことを決定済み）

### 6.1 デイリータスクリスト（プラン）

| ID | 要求 | 優先度 |
|---|---|---|
| F-101 | 1日単位のタスクリストを表示し、タスクを実行順に並べられる | Must |
| F-102 | タスクの追加・編集・削除・並び替え（ドラッグ等）が素早く行える | Must |
| F-103 | 各タスクに見積もり時間を設定できる | Must |
| F-104 | 残タスクの見積もり合計から**終了予定時刻を自動計算・常時表示**する | Must |
| F-105 | セクション（時間帯区分）を定義し、タスクをセクションに配置できる | Must |
| F-110 | セクションごとに、配置タスクの見積もり時間合計とセクション枠に対する過不足が分かる（F-105 から分割） | Must |
| F-106 | 過去・未来の日付のタスクリストを閲覧・編集できる | Must |
| F-107 | タスクを翌日以降へ移動（先送り）できる | Must |
| F-108 | 過去に実行したタスク名から入力補完でき、属性（見積もり・分類等）ごと流用できる | Should |
| F-109 | カレンダー形式で期間を俯瞰表示できる | Could |
| F-111 | タスクをワンアクションで複製できる（名前・見積もり・分類を引き継ぎ、未実行タスクとして追加。完了済みタスクの「もう一回」の再実行用） | Must |
| F-112 | モード・プロジェクト・セクションの選択ポップオーバーを、矢印キーでの候補移動と Enter での確定だけで操作できる（Phase 1 はクリック選択のみ。2026-07-19 追加） | Could |

### 6.2 実行・ログ（記録）

| ID | 要求 | 優先度 |
|---|---|---|
| F-201 | タスクの開始・終了をワンアクションで記録できる（開始時刻・終了時刻の打刻） | Must |
| F-202 | 実績時間と見積もり時間の差異が一目で分かる | Must |
| F-203 | 開始・終了時刻を後から手動修正できる | Must |
| F-204 | タスクを中断すると、**そのタスクの残り見積もり時間分のタスクが自動生成される**（旧TCC1の動作を再現） | Must |
| F-205 | 実行中タスクの経過時間をリアルタイム表示する | Must |
| F-206 | タスクにコメント（一言メモ）を残せる | Should |
| F-207 | タスクごとにノート（手順書・議事録などの長文メモ）を持てる | Could |
| F-208 | 完了済みタスクに対する打刻操作（Enter）で、複製と開始をまとめて行える（「もう一回」の高速化。Phase 1 は複製 Y と開始 Enter の2操作。2026-07-19 追加） | Could |

### 6.3 ルーチン

| ID | 要求 | 優先度 |
|---|---|---|
| F-301 | ルーチンタスクを登録し、日次・週次・月次などの繰り返しルールで自動的にデイリーリストへ展開できる | Must |
| F-302 | ルーチンに見積もり時間・**開始想定時刻**・分類（モード/プロジェクト）を設定できる。デイリーリストへの展開順とセクション配置は開始想定時刻から導出する（セクションや並び順を個別に設定させない） | Must |
| F-303 | ルーチンの一括管理（一覧・編集・有効/無効切替）ができる | Must |
| F-304 | 特定日のルーチン展開を個別にスキップ・変更できる（ルーチン本体には影響しない） | Could |
| F-305 | 実行したタスクをそのままルーチン化できる（ログ → ルーチンの導線） | Could |

### 6.4 分類（プロジェクト / モード）

| ID | 要求 | 優先度 |
|---|---|---|
| F-401 | タスクにモード（色付きカテゴリ）を設定でき、リスト上で色として視認できる | Must |
| F-402 | タスクにプロジェクトを設定できる | Must |
| F-404 | 分類による絞り込み表示ができる | Could |

※ F-403（タグ）は要求なしのため削除（欠番）。

### 6.5 レビュー・分析

| ID | 要求 | 優先度 |
|---|---|---|
| F-501 | 1日の実績ログ（開始・終了・実績時間・コメント）を一覧で振り返られる | Should |
| F-502 | 先送りしたタスク数を日次で確認できる（先送りゼロの実践支援） | Should |
| F-503 | モード・プロジェクト別の時間集計（日次・週次・月次）ができる | Should |
| F-504 | ログをCSV等でエクスポートできる（N-06 が求めるDBレベルのバックアップとは別の、アプリ画面上の機能） | Should |
| F-505 | 見積もり精度（見積もり vs 実績）の傾向を分析できる | Could |

※ レビュー機能（F-5XX）は初期開発では Must としない。デイリータスクリスト上で過去日付へ移動すれば（F-106）、当面の振り返りは自身で行えるため。

## 7. 非機能要求

| ID | 要求 | 優先度 |
|---|---|---|
| N-01 | 高頻度操作（開始・終了打刻、タスク追加）が体感即応であること。1日数十回の操作が苦にならないこと（TCC2の「遅さ」の解消が動機のひとつ） | Must |
| N-02 | **Webアプリとしてデプロイ**し、私用PC・業務PCなど複数のPCからブラウザでアクセス・操作できること | Must |
| N-03 | Basic認証等により、オーナー以外のアクセスを制限すること（シングルユーザー前提の簡易な認証で良い） | Must |
| N-04 | **キーボードショートカットで主要操作（打刻・タスク追加・移動・編集など）が完結**できること。旧TCCのショートカット体系を参考にする（旧TCCは仕様の一次情報が入手困難なため、要件定義時にオーナーの記憶ベースで「必須ショートカット一覧」を作成する） | Must |
| N-05 | UIは装飾を排したシンプルなリスト表示を基本とすること（リッチなUIにしない） | Must |
| N-06 | データはオーナー自身の管理下にあること。オーナー名義のアカウントで契約するDBaaS等の利用も可。ただし①標準的な形式でエクスポート・バックアップ可能、②特定サービスにロックインされず他DBへ移行可能な構成とすること | Must |
| N-07 | ランニングコストが低いこと（目安: TCC2の年額12,980円を大幅に下回る。無料〜数百円/月程度。DBaaS・ホスティングの無料枠の活用を想定） | Must |
| N-08 | 数年分のログが蓄積してもデイリー画面の性能が劣化しないこと | Should |
| N-09 | スマートフォン対応は必須としない（崩れず閲覧できる程度で可） | Could |
| N-10 | オフライン対応は当面不要（Webアプリ前提のため） | 対象外 |

## 8. スコープ外（現時点）

- マルチユーザー対応・チーム機能・一般公開
- TCC2の完全再現（あくまで「自分の使い方」に必要な機能に絞る）
- ネイティブモバイルアプリ（まずはWebで検証）
- 有料サービス化
- TCC2からの既存データ移行
- 料金プランに伴う機能制限（タスク数上限・ルーチン数上限・分析期間制限など）— 自作のためすべて無制限とする

## 9. 制約・前提

- 開発者はオーナー本人＋AI支援。個人開発として維持可能な技術スタック・運用規模とする
- 「タスクシュート」「TaskChute」は商標であるため、アプリを公開する場合は名称・表現に注意する（私的利用の範囲では問題になりにくいが留意）
- TCC2のUIデザインの複製ではなく、メソッドの実装＋独自UIとする

## 12. 用語集

| 用語 | 意味 |
|---|---|
| タスクシュート | プラン・ログ・ルーチンのサイクルで1日を管理する時間管理メソッド |
| TCC / TCC2 | TaskChute Cloud（旧版）/ TaskChute Cloud 2（2024年〜の現行版） |
| セクション | 1日を区切る時間帯の枠（例: 朝・午前・午後・夜） |
| モード | 動作・活動の種類を表す色付き分類（執筆・会議・休憩など）。1日の流れを組み立てる基準（→ §4.3） |
| プロジェクト | 1つのゴールに向かうタスクのまとまり（資格取得など）。抜け漏れ防止が目的（→ §4.3） |
| ルーチン | 繰り返しルールに基づき自動でデイリーリストに展開されるタスク |
| 開始想定時刻 | ルーチンが持つ時刻。展開時の並び順とセクション配置の導出に使う。実行を固定する予約時刻ではない（F-302） |
| 中断 | 実行中タスクをいったん終了し、残り見積もり時間分のタスクを自動生成して後で再開できるようにする操作（F-204） |
| 先送りゼロ | 今日やると決めたタスクに1分でも手をつけ、先送り数ゼロを目指す実践ルール |
| 終了予定時刻 | 現在時刻＋残タスク見積もり合計で算出される、その日の全タスク終了見込み時刻 |
