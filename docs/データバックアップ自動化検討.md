## 1. 動機と現状

N-06 のバックアップは `pg_dump`（カスタム形式）で取得でき、2026-07-20 に本番ダンプからの復元も実演済み（README・データモデル定義書 §6）。ただし**取得は手動**で、README・要件定義書 §6 とも「自動化（GitHub Actions cron）は運用の負担を見てから判断する」に留めていた。

手動運用の弱点は**取得漏れ**。取り忘れた期間はどこにも退避が無く、Neon 側の PITR/履歴保持の窓（無料枠は短い）を超えると復元不能になる。週次の定期取得を自動化し、取得漏れをなくしたい。

## 2. 結論と難所

**技術的には容易**。`pg_dump` は GitHub Actions ランナーから Neon へ到達でき、cron（`schedule`）＋手動（`workflow_dispatch`）で定期実行できる。実行自体は標準的なパターン。

本質的な難所は「取得の実行」ではなく次の1点で、**これが本検討の主題**。

### 難所: public リポジトリで、実データを含むダンプをどこへどう置くか

本リポジトリは公開（CLAUDE.md「このリポジトリは public」）。ダンプには**オーナーの生活が読み取れる実データ**が入るため、平文でリポジトリ内や公開されうる場所（public リポジトリの Actions artifact 等）に置けない（スキーマ更新パイプライン検討 §5 でも「backups の artifact 保存は不向き」と整理済み）。

この難所は**保存先の秘匿**として捉えると難しく見えるが、実際は次の2軸に分解でき、**暗号化を先に決めると保存先選びが素直になる**。

- **暗号化**: ダンプを信頼境界（＝Actions ランナー）を出る前に暗号化するか
- **保存先**: 暗号化済み blob をどこに置くか（durable であれば十分）

## 3. 暗号化設計（全案共通の前提・秘匿の核）

**`age`（または gpg）の非対称暗号を使う。**

- 暗号化に使う鍵（recipient **公開鍵**）は**リポジトリにコミットしてよい**（公開鍵から平文は復元できない）。ワークフローはこの公開鍵で暗号化するだけ
- 復号鍵（identity）は**オーナーの手元／パスワードマネージャにだけ置き、CI には一切渡さない**
- 結果、ダンプが漏れても・保存先が半公開でも**復号鍵なしには中身を読めない**。「保存先が秘匿されているか」を気にする必要がなくなり、問題が「安く durable な置き場所はどこか」に単純化される

CI に渡すシークレットは **DB 接続文字列（unpooled）** と（保存先によっては）**保存先の資格情報**だけ。**復号鍵は CI に載らない**ため、鍵の漏洩面が最小になる。

## 4. 保存先の実現方式（A を採用。B・C は将来の選択肢）

扱う投資が「新アカウント不要の最小構成」→「オブジェクトストレージで運用を厚く」→「静的キーを CI から排除して認証を最堅に」と上がっていく（A は低コストで即効、C は最も堅牢だが初期設定が重い）。**オーナーは AWS/GCP/R2 いずれのクラウドアカウントも未保有**であり、**個人開発・単一ユーザー・極小データ（週次で KB〜数MB）**という規模では **A（プライベート GitHub リポジトリ）で必要十分**と判断し、A を採用する。暗号化（§3）は全案共通なので、B・C への移行はいつでも効く two-way door。

| 案 | 保存先 | CI 認証 | 何がうれしい / 主なトレードオフ |
|---|---|---|---|
| **A（採用）** | プライベート GitHub リポジトリ | 専用リポジトリへ push する PAT（fine-grained・contents:write） | **新規クラウドアカウント不要**・既存 GitHub だけで完結。ダンプは Neon 外の移植可能形式＝**N-06② も満たす**。git は binary に不向きだが極小データ＋prune で無害。世代管理はスクリプトで自前 |
| **B（将来）** | Cloudflare R2 / Backblaze B2 | オブジェクトストレージの静的キー（Environment 隔離） | **lifecycle rule で世代管理が自動**・オブジェクトストレージとして素直。10GB 無料枠。新ベンダ1つ＋（多くは）支払い方法登録が要る。取得頻度・世代数が増え git 運用が重くなったら移行 |
| **C（将来）** | AWS S3 / GCP Cloud Storage | **GitHub OIDC / Workload Identity Federation（静的キーなし）** | CI に長期キーを置かない**最も堅い認証**。S3 は Glacier、GCS は Archive で長期保管も安い。課金アカウント新設＋IAM ロール／WIF プール設定が要る。より堅牢な認証が必要になった／既にアカウントを持ったときに |

### 案A: age 暗号化 ＋ プライベート GitHub リポジトリ（採用）

- **仕組み**: `schedule`（週次 cron）＋ `workflow_dispatch`（手動）で `pg_dump` → `age -r <公開鍵>` で暗号化 → **別の非公開リポジトリ**（例: `hitosuji-backups`）へ commit/push
- **秘匿**: 保存先が非公開リポジトリ、かつ中身は age 暗号化済み（**二重の防御**）。本リポジトリ（public）には暗号化 blob を一切置かない
- **N-06②（ロックイン回避）**: 保存物は素の `pg_dump` を暗号化しただけ。落として `age -d` → `pg_restore`（既存の `npm run db:restore`）で他の Postgres／自宅サーバへそのまま復元できる
- **世代管理**: prune ステップ（古い世代を削除して commit）で「週次 N 世代＋月次数世代」を保つ。極小データなので肥大化は実害にならない
- **位置づけ**: ローカルの手動 `db:backup` を、既存 GitHub だけで回る cron に置き換える**最小の一歩**。新ベンダ・新課金アカウントを増やさない

### 案B: age 暗号化 ＋ Cloudflare R2 / Backblaze B2（見送り・将来の選択肢）

> git 運用が重くなる／世代管理を自動化したくなったら着手する。以下は将来の設計メモ。

- **仕組み**: cron で `pg_dump` → age 暗号化 → S3 互換 API でバケットへ upload。世代管理は**バケットの lifecycle rule**（N 日で失効／Archive へ移行）に任せる
- **利点**: オブジェクトストレージとして素直・lifecycle で世代管理が運用レス。10GB 無料枠で極小データは実質無料
- **トレードオフ**: 新ベンダ1つ＋（多くは）支払い方法の登録。静的キーを CI に置く（Environment 隔離＋暗号化で担保するが、案C の OIDC より鍵の管理面は残る）

### 案C: age 暗号化 ＋ S3 / GCS + GitHub OIDC/WIF（見送り・将来の選択肢）

> より堅牢な認証が必要になった／AWS・GCP のアカウントを持ったときに着手する。以下は将来の設計メモ。

- **仕組み**: cron で `pg_dump` → age 暗号化 → GitHub OIDC（AWS は IAM ロール引き受け、GCP は Workload Identity Federation）で得た**一時クレデンシャル**でアップロード。長期キーを CI に置かない
- **利点**: シークレット漏洩面が最小（静的キーなし）。Glacier/Archive クラスで長期保管も安い
- **トレードオフ**: 課金アカウント新設＋ OIDC プロバイダ・IAM ロール／WIF プールの設定が要る。**この規模では初期コストが投資に見合わない**（オーナーは両クラウド未保有）

## 5. ワークフロー設計（public 対応・全案で必須）

`.github/workflows/db-migrate.yml`（T-22）のパターンを流用する。ただし**承認ゲートは使わない**（下記）。

- **契機は `schedule` ＋ `workflow_dispatch` のみ**。`pull_request` では絶対に走らせない（fork PR にシークレットを渡さないため）。scheduled workflow は default ブランチ（main）で走る＝ワークフロー本体と age 公開鍵は main に置く
- **承認ゲート（required reviewers）は付けない**: 定期実行のたびに人手承認を待つのは自動化の目的に反する。代わりに「**シークレットを非 PR イベントにしか露出しない＋最小権限**」で担保する（db-migrate の手動 migrate とは要件が違う。あちらは人の合図が要るので承認ゲート、こちらは無人実行なので付けない）
- **接続**: `pg_dump` に渡す接続文字列は **unpooled** を専用シークレット（例 `BACKUP_DATABASE_URL`）に。`MIGRATE_DATABASE_URL` とは別に持ち、用途を混同しない
- **ログに接続文字列・鍵を出さない**: `set -x` 禁止・`echo` での展開禁止（スキーマ更新パイプライン検討 §4 と同じ規律）
- **権限は最小**: workflow の `permissions` は必要最小（案A の別リポジトリ push は PAT で行い、`GITHUB_TOKEN` は read に絞る）
- **失敗通知**: 無人実行のため、**失敗が黙って続くと最悪**。ジョブ失敗時に通知（Actions の失敗通知メール、または簡易 webhook）を出す。着手時に手段を詰める
- **復元経路は据え置き**: blob を落として `age -d -i <identity>` → 既存の `npm run db:restore`。復元手順は README が正のまま

## 6. 採用した方針

- **案A を採用**: age 暗号化 ＋ プライベート GitHub リポジトリへの週次 cron。新規クラウドアカウント不要で秘匿（暗号化＋非公開リポジトリ）と N-06②（移植可能ダンプ）を両立する最小構成
- **暗号化（age・非対称）は全案共通の前提**とし、保存先の秘匿ではなく暗号化で秘匿を担保する
- **案B・C は見送り**（§4）。オブジェクトストレージの lifecycle・OIDC の静的キーレスは、この規模では過剰。git 運用が重くなる／より堅牢な認証が要る／クラウドアカウントを持つ、のいずれかで two-way door に格上げする

- **実装は未着手**（本書は方式決定まで）。着手する場合の主な実装項目:

  - age 鍵ペアの生成（公開鍵を本リポジトリにコミット、**復号鍵はオーナー手元／パスワードマネージャに保管**）

  - `.github/workflows/db-backup.yml`（`schedule` 週次＋`workflow_dispatch`／`pg_dump`→age→push／prune／失敗通知）

- **着手条件**: 手動運用の取得漏れが実害になり始めた／週次取得の手間を恒常的に感じるとき。実運用は既に開始済み（2026-07-20）のため、条件は「負担を実感したら」で十分
- **案B・C への格上げ条件**: 案B＝git 運用が重くなった／世代管理を自動化したい。案C＝より堅牢な認証（静的キーレス）が要る、または AWS・GCP のアカウントを持った
