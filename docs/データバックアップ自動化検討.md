## 1. 動機と現状

N-06 のバックアップは `pg_dump`（カスタム形式）で取得でき、2026-07-20 に本番ダンプからの復元も実演済み（データモデル定義書 §6）。ただし**取得は手動**で、README・要件定義書 §6 とも「自動化（GitHub Actions cron）は運用の負担を見てから判断する」に留めていた。

手動運用の弱点は**取得漏れ**。取り忘れた期間はどこにも退避が無く、Neon 側の PITR/履歴保持の窓（無料枠は短い）を超えると復元不能になる。週次の定期取得を自動化し、取得漏れをなくしたい。

## 2. 結論と難所

**技術的には容易**。`pg_dump` は GitHub Actions ランナーから Neon へ到達でき、cron（`schedule`）＋手動（`workflow_dispatch`）で定期実行できる。実行自体は標準的なパターン。

本質的な難所は「取得の実行」ではなく次の1点で、**これが本検討の主題**。

### 難所: public リポジトリで、実データを含むダンプをどこへどう置くか

本リポジトリは公開（CLAUDE.md「このリポジトリは public」）。ダンプには**オーナーの生活が読み取れる実データ**が入るため、平文でリポジトリ内や公開されうる場所（public リポジトリの Actions artifact 等）に置けない（スキーマ更新パイプライン検討 §5 でも「backups の artifact 保存は不向き」と整理済み）。

この難所は**保存先の秘匿**として捉えると難しく見えるが、実際は次の2軸に分解でき、**暗号化を先に決めると保存先選びが素直になる**。

- **暗号化**: ダンプを信頼境界（＝Actions ランナー）を出る前に暗号化するか
- **保存先**: 暗号化済み blob をどこに置くか（durable であれば十分）

## 3. 暗号化設計（確定・秘匿の核）

**`age`（または gpg）の非対称暗号を使う。**

- 暗号化に使う鍵（recipient **公開鍵**）は**リポジトリにコミットしてよい**（公開鍵から平文は復元できない）。ワークフローはこの公開鍵で暗号化するだけ
- 復号鍵（identity）は**オーナーの手元／パスワードマネージャにだけ置き、CI には一切渡さない**
- 結果、ダンプが漏れても・保存先が半公開でも**復号鍵なしには中身を読めない**。「保存先が秘匿されているか」を気にする必要がなくなり、問題が「安く durable な置き場所はどこか」に単純化される

CI に渡すシークレットは **DB 接続文字列（unpooled）** と（保存先によっては）**保存先の資格情報**だけ。**復号鍵は CI に載らない**ため、鍵の漏洩面が最小になる。この暗号化設計は保存先2案に共通。

## 4. 保存先の実現方式（案B・案C を併記・採用は保留）

保存先はクラウドオブジェクトストレージを前提とし、**2案を併記**する。オーナーは AWS/GCP/R2 いずれの課金アカウントも未保有のため、どちらも「新規アカウント作成」が要る。両案の差は主に **CI 認証（静的キーを置くか／OIDC で置かないか）** と **セットアップの重さ**で、機能・コストの差は極小データ（週次で KB〜数MB）ではほぼ出ない。**採用はアカウントを作る段で確定する**（§7）。暗号化（§3）は共通なので、B↔C の乗り換えはいつでも効く two-way door。

| 案 | 保存先 | CI 認証 | 何がうれしい / 主なトレードオフ |
|---|---|---|---|
| **案B** | Cloudflare R2 / Backblaze B2 | オブジェクトストレージの静的キー（Environment 隔離） | **セットアップが軽い**（サインアップ＋キー発行）。lifecycle rule で世代管理が自動。10GB 無料枠・egress 無料。静的キーを CI（Environment）に置く点が案C との差 |
| **案C** | AWS S3 / GCP Cloud Storage | **GitHub OIDC / Workload Identity Federation（静的キーなし）** | CI に長期キーを置かない**最も堅い認証**。public リポジトリと相性が良い。Glacier / Archive クラスで長期保管も安い。**IAM ロール／WIF プールの設定が要る**（セットアップが重い） |

> 判断の目安: **セットアップの軽さ**を採るなら案B、**静的キーを CI から排除する堅牢さ**を採るなら案C。どちらも age 暗号化（§3）＋非 PR イベント限定（§5）で秘匿は担保される。

> 参考（見送った案）: 「プライベート GitHub リポジトリへ暗号化 blob を commit する」案も検討したが、オーナーがクラウドオブジェクトストレージを志向したため見送り。git は binary 保管に不向きで世代管理も自前になるため、B・C を優先する（検討ログ 2026-07-23）。

### 案B: age 暗号化 ＋ Cloudflare R2 / Backblaze B2

- **仕組み**: cron で `pg_dump` → `age -r <公開鍵>` で暗号化 → S3 互換 API でバケットへ upload。世代管理は**バケットの lifecycle rule**（N 日で失効／低頻度クラスへ移行）に任せる
- **CI 認証**: オブジェクトストレージの静的キー（アクセスキー／シークレット）を**専用 Environment のシークレット**に置く。暗号化＋非 PR イベント限定（§5）と併せて担保
- **N-06②（ロックイン回避）**: 保存物は素の `pg_dump` を暗号化しただけ。落として `age -d` → `pg_restore`（既存の `npm run db:restore`）で他の Postgres／自宅サーバへそのまま復元できる
- **セットアップ**: サインアップ＋バケット作成＋キー発行（多くは支払い方法の登録が要る）。案C より軽い

### 案C: age 暗号化 ＋ AWS S3 / GCP Cloud Storage + GitHub OIDC/WIF

- **仕組み**: cron で `pg_dump` → age 暗号化 → GitHub OIDC（AWS は IAM ロール引き受け、GCP は Workload Identity Federation）で得た**一時クレデンシャル**でアップロード。長期キーを CI に置かない。世代管理は lifecycle（S3=Glacier／GCS=Archive で長期保管も安い）
- **CI 認証**: GitHub Actions の OIDC トークン → クラウド側で一時クレデンシャルに交換。**静的キーが CI に存在しない**のが最大の利点
- **N-06②（ロックイン回避）**: 案B と同じく素の `pg_dump` の暗号化なので、他の Postgres へそのまま復元できる
- **セットアップ**: 課金アカウント新設＋ OIDC プロバイダ・IAM ロール（AWS）／WIF プール（GCP）の設定。案B より重いが、鍵管理の運用負担は下がる

## 5. ワークフロー設計（public 対応・両案で共通）

`.github/workflows/db-migrate.yml`（T-22）のパターンを流用する。ただし**承認ゲートは使わない**（下記）。

- **契機は `schedule` ＋ `workflow_dispatch` のみ**。`pull_request` では絶対に走らせない（fork PR にシークレット／OIDC を渡さないため）。scheduled workflow は default ブランチ（main）で走る＝ワークフロー本体と age 公開鍵は main に置く
- **承認ゲート（required reviewers）は付けない**: 定期実行のたびに人手承認を待つのは自動化の目的に反する。代わりに「**シークレット／OIDC を非 PR イベントにしか露出しない＋最小権限**」で担保する（db-migrate の手動 migrate とは要件が違う。あちらは人の合図が要るので承認ゲート、こちらは無人実行なので付けない）
- **DB 接続は共通**: `pg_dump` に渡す接続文字列は **unpooled** を専用シークレット（例 `BACKUP_DATABASE_URL`）に。`MIGRATE_DATABASE_URL` とは別に持ち、用途を混同しない
- **保存先認証は案で分岐**: 案B は静的キー（Environment シークレット）、案C は OIDC/WIF（`permissions: id-token: write` を付与し、クラウド側で一時クレデンシャルに交換）
- **ログに接続文字列・鍵を出さない**: `set -x` 禁止・`echo` での展開禁止（スキーマ更新パイプライン検討 §4 と同じ規律）
- **権限は最小**: workflow の `permissions` は必要最小（案C の OIDC は `id-token: write`＋`contents: read`）
- **失敗通知**: 無人実行のため、**失敗が黙って続くと最悪**。ジョブ失敗時に通知（Actions の失敗通知メール、または簡易 webhook）を出す。着手時に手段を詰める
- **復元経路は据え置き**: blob を落として `age -d -i <identity>` → 既存の `npm run db:restore`。復元手順は README が正のまま

## 6. 採用した方針

- **暗号化は age 非対称暗号で確定**（§3）。公開鍵はコミット可・復号鍵は CI に載せない。保存先の秘匿ではなく暗号化で秘匿を担保する
- **保存先は案B（R2/B2・静的キー）と案C（S3/GCS・OIDC）を併記し、採用は保留**（§4）。差は CI 認証とセットアップの重さで、機能・コストの差は極小データではほぼ無い。**クラウドの課金アカウントを作る段で B/C を確定する**
- **ワークフローの秘匿設計は確定**（§5）: `schedule`＋`workflow_dispatch` 限定・承認ゲートなし・非 PR イベント限定・最小権限・失敗通知・unpooled 接続

## 7. 残作業・将来の着手条件

- **保存先（案B/案C）の確定は保留**。クラウドの課金アカウントを作る段で、セットアップの軽さ（案B）か静的キーレスの堅牢さ（案C）かで決める
- **実装は未着手**（本書は方式決定まで）。着手する場合の主な実装項目:
  - age 鍵ペアの生成（公開鍵を本リポジトリにコミット、**復号鍵はオーナー手元／パスワードマネージャに保管**）
  - `BACKUP_DATABASE_URL`（unpooled）シークレットの登録
  - 保存先の用意: 案B＝バケット作成＋静的キーをシークレット登録／案C＝バケット作成＋ OIDC プロバイダ・IAM ロール（AWS）or WIF プール（GCP）の設定
  - lifecycle rule（世代の失効／低頻度・Archive クラスへの移行）の設定
  - `.github/workflows/db-backup.yml`（`schedule` 週次＋`workflow_dispatch`／`pg_dump`→age→upload／失敗通知）
  - README「バックアップ（N-06）」に自動化の運用（鍵・復元・世代）を追記
- **着手条件**: 手動運用の取得漏れが実害になり始めた／週次取得の手間を恒常的に感じるとき。実運用は既に開始済み（2026-07-20）のため、条件は「負担を実感したら」で十分
