- 優先度: `高` / `中` / `様子見`
- 状態: `未着手` / `進行中` / `完了` / `保留`

## T-07 統合テストの `updated_at` ミリ秒衝突によるフレーク

- 種別: 改善（テスト補強）/ 優先度: 様子見 / 状態: 未着手
- 背景: `drizzle-section-repository.int.test.ts:54`「update は名前と開始時刻を書き換え、updated_at を進める」が、更新の前後が同一ミリ秒に収まると `updatedAt` が変化せず `not.toBe` で偽陽性で落ちる。まれに再現。実装（アプリ層が `updated_at` を設定する契約）の欠陥ではなくテスト側の時刻粒度の問題（変更を stash して再現確認済み）
- 対応方針: 比較を「進む、または同値」に緩める（`toBeGreaterThanOrEqual`）。テスト名の「進める」も「巻き戻さない」意図に整合させる

## T-08 Server Action の結果型統一と定型ラッパの整理

- 種別: 改善 / 優先度: 中 / 状態: 未着手
- 背景: 構造が同一の結果型が3箇所に別名で並立している（`src/app/(daily)/actions.ts` `DailyActionResult`、`src/app/routines/actions.ts` `RoutineActionResult`、`src/app/masters/_lib/action-result.ts` `ActionResult`——いずれも `Readonly<{ ok: true } | { ok: false; message: string }>`）。加えて全 Action が「`usecase()` 呼び出し → `if (!result.ok) return 失敗` → `revalidatePath` → `return { ok: true }`」の同型で、`src/app/masters/*/actions.ts` は各5関数×3ファイルでほぼ完全一致。エラーコード→日本語の `MESSAGES` レコードも複数ファイルに散在し、`name_required` 等のキーが重複している
- 対応方針: 共通結果型 `ActionResult`（＋`createdId` 等を許す拡張）を1箇所に置き、各 Action ファイルは再エクスポートかインポートに寄せる。まず低リスクな「型の一本化」だけ先行し、`revalidatePath` 込みの定型ラッパ化は効果を見て判断する（オーナー1人のアプリで過剰抽象を避ける方針＝[アーキテクチャ定義書](./アーキテクチャ定義書.md) §1 に留意）。daily の carry-over や createdId 返却など固有処理はラッパに巻き込まない

- 背景: 依存更新（Dependabot）の検証を手動（ブランチ取得 → `npm ci` → lint/build/test）で行っていた。定期的に発生するため機械化したかった。従来の自動チェックは Vercel ビルド（`next build`＝型チェックのみ）だけで、`npm run lint` と `npm test` は走っていなかった
- 対応: `.github/workflows/ci.yml` を新設。`pull_request` と main への `push` で `npm ci` → `lint` → `build` → `test` を実行。統合テストは Postgres サービスコンテナ（`postgres:17-alpine`、DB=`hitosuji_test`）を建て、`TEST_DATABASE_URL` を渡す（マイグレーションは vitest の globalSetup が自動適用）。Node は本番に合わせて 24
- 方針: CI は**検証のみ**。Dependabot PR がグリーンでもマージ（＝main への push ＝本番デプロイ）は手動で、オーナーの合図を待つ。自動マージ・CI 必須チェック化（ブランチ保護）はしない
