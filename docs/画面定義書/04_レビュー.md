## 1. 画面の役割

日次の振り返りと期間集計を行う。Phase 1 の間は S-01 の過去日付閲覧（F-106）で代替する（要求定義書 §6.5 注記）。本書は Phase 2 着手時の詳細化に向けたアウトラインであり、現時点では実装対象ではない。

## 2. 想定する構成

```
┌────────┬─────────────────────────────────────────────────────┐
│ Hitosuji│ ◀ 2026-07-16 ▶ [日|週|月]           [CSVエクスポート] │
│ デイリー │─────────────────────────────────────────────────────│
│ ルーチン │ 先送り: 2件                                          │ ← F-502
│ マスタ  │ ── 実績ログ（日表示時）───────────────               │ ← F-501
│ レビュー │ 06:30-06:48 朝食 (見積0:20/実績0:18) 「コメント…」    │
│        │ ── モード別集計 ────  ── プロジェクト別集計 ──        │ ← F-503
│        │ 仕事 5:20 / 暮らし 2:10   ブログ運営 1:30 / …         │
└────────┴─────────────────────────────────────────────────────┘
```

## 3. 要求別の設計メモ（詳細化時のインプット）

| 要求 | メモ |
|---|---|
| F-501 | 実績ログは S-01 と同一データの読み取り専用ビュー。時刻編集は S-01 側で行う |
| F-502 | **先送り数の厳密な定義が最大の論点**。案: 「日付 D に属していた未実行タスクのうち、D の終了までに打刻されず、翌日以降へ移動された（または残置された）ものの数」。「1分でも手をつけたら先送りではない」（先送りゼロの原則）に合わせ、started_at があれば先送りに数えない。移動回数は `tasks.postponed_count`（Phase 1 から記録。データモデル定義書 §3.5）で追跡できるため、これと残置分の判定を組み合わせられるかを詳細化時に検証する |
| F-503 | 集計軸: モード / プロジェクト。期間: 日・週（月曜始まり）・月。実績時間（ended_at − started_at）の合計。棒グラフ等の視覚化は必須としない（N-05。まず数表で十分） |
| F-504 | 期間指定でtasksをCSV出力。列: 日付, タスク名, セクション, モード, プロジェクト, 見積(分), 実績(分), 開始, 終了, コメント。UTF-8 BOM付き（Excel互換） |
| F-505 | (Phase 3) モード別・タスク名別の 見積/実績 乖離率など。運用データが貯まってから設計する |

## 4. 詳細化の前提条件

- Phase 1 の運用開始後、実データでの振り返りニーズを1〜2週間観察してから詳細化する（S-01 の過去日閲覧で不足する点を洗い出す）
- F-502 の定義検証の結果、データモデル変更（履歴カラム追加）が必要な場合はデータモデル定義書を改版する
