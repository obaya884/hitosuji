## 1. 動機と現状

しばらく操作しないでいると、本番の初回応答に体感できる待ちがある。N-01 は操作の体感を 0ms に寄せる要求だが、これは楽観的更新が効く**操作**の話で、**画面を開く最初の1回**は素の応答時間がそのまま出る。

きっかけは Neon から届いた production checklist メール（2026-08-13）。「scale to zero を無効化せよ」「最小 1 CU・最大 2 CU にせよ」等の推奨が並ぶが、大半は有料プランの前提で、無料枠では実行できないか意味が無い。**唯一まともに効きそうなのが scale to zero の無効化**で、これを判断するには先に原因を確かめる必要があった。

**測らずに倒すと外す**構造がある。遅延の原因が Vercel の関数起動なら、Neon に課金しても体感は変わらない。逆も同じ。

## 2. 切り分けの原理

Vercel と Neon のコールドスタートは重なって観測されるので、**片方だけを冷やした状態**を作れれば分離できる。本アプリには都合のよい足がかりが2つある。

- **DB に触れない経路がある**: Basic 認証（`src/proxy.ts`、N-03）は資格情報が無ければ 401 を返し、ページ描画へ進まない。つまり**認証なしのリクエストは Vercel だけを通り、Neon に到達しない**
- **サスペンドの時間差**: Neon（無料枠）は5分アイドルで停止する。一方 Vercel 側は 401 を叩き続ければ温めておける

これを組み合わせて4条件を作る。

| 条件 | 作り方 | 測れるもの |
|---|---|---|
| 全部温 | 連続してリクエスト | 基準値 |
| Vercel だけ冷 | 30分以上放置 → **認証なし**で1回 | Vercel 単体のコールドスタート |
| Neon だけ冷 | 6分待つ間 30秒おきに**認証なし**で叩き続ける → 認証ありで1回 | Neon 単体のコールドスタート |
| 全部冷 | 30分以上放置 → 認証ありで1回 | 体感している遅さ |

計測値は `curl` の `time_starttransfer`（TTFB）から `time_appconnect`（TLS 確立まで）を引いた**サーバ処理時間**を使う。Vercel は最寄り（東京）で TLS を終端して `sin1`（シンガポール）の関数へ転送するため、この引き算をしても**東京→シンガポールの往復（80ms 前後）は残る**。

前提の確認は Vercel のランタイムログで行う（Hobby プランの保持は1時間なので**計測直後にしか読めない**）。

## 3. 実測結果（2026-08-13 22:06〜22:12 JST）

計測前1時間、本番へのアクセスがゼロだったことをランタイムログで確認済み。

| 計測 | 条件 | サーバ処理 |
|---|---|---|
| 2-2 / 3-2 | 全部温 | **0.25秒** |
| 0-2 | 401・Vercel温（DB に触れない） | 0.59秒 |
| 0-1 | 401・Vercel冷（DB に触れない） | 0.97秒 |
| 3-1 | Neon だけ冷 | **1.92秒** |
| 1-1 | 全部冷 | **2.30秒** |

**内訳**:

- コールドスタートの総ペナルティ = 2.30 − 0.25 = **2.05秒**
- Neon 側 = 1.92 − 0.25 = **1.67秒（約81%）**
- Vercel 側 = 2.30 − 1.92 = **0.39秒（約19%）**

**裏取り**: DB に触れない 401 経路で測った Vercel 単体のコールドスタート幅は 0.97 − 0.59 = **0.38秒**で、Vercel を温めたことによる短縮 0.386秒（1-1 と 3-1 の差）とほぼ一致した。「Neon だけ冷」の条件で狙いどおり Vercel 側の起動だけを除去できていたことを示す。

**ログ側の整合**: `pg` の接続確立時にだけ出る警告（[T-129](../案件/23_技術改善バックログ.md#t-129)）が「全部冷」と「Neon だけ冷」の2リクエストにだけ現れ、直後の温リクエストでは出なかった。DB 接続を張り直した回だけが遅い、という図式と合う。

## 4. 原因の判定

**Neon のコンピュート起動が主因**（2.05秒のうち 1.67秒）。

体感が悪い理由もここで説明がつく。無料枠の Neon は**5分アイドルで停止し、この待ち時間は変更できない**。つまり 1.67秒は「朝イチの1回」ではなく、**5分以上アプリから離れるたび**に発生する。タスクシュートの使い方（1日に何度も出入りする）とは相性が悪い。

## 5. 対策の評価

外部記事で挙がる定番の対策を、本プロジェクトの実構成に当てて判定した。

| 対策 | 判定 |
|---|---|
| **リージョン統一** | **すでに最適**。`vercel.json` が `sin1`、Neon プロジェクトが AWS Asia Pacific 1（Singapore）で一致済み。Neon に東京リージョンは無いため、日本から見てこれが現状の上限 |
| **接続プーリング（PgBouncer）** | 適用済みの前提で運用している（[32_スキーマ更新パイプライン検討.md](./32_スキーマ更新パイプライン検討.md) §5 が「マイグレーションは unpooled を使う」と書いており、通常経路は pooler という含意） |
| **ドライバを `@neondatabase/serverless` へ変更** | **効かない**。これが削るのは TCP・TLS の接続確立コストで、主因のコンピュート起動は待たされたまま。接続確立分は [T-130](../案件/23_技術改善バックログ.md#t-130) の領分 |
| **cron でウォームアップ** | Hobby プランは cron が1日1回までで不可。GitHub Actions から叩く手はあるが実行間隔が不正確 |
| **Edge Runtime への移行** | **不採用**。Vercel の現在の既定は Fluid Compute（Node.js のままインスタンスを再利用）で、Edge は互換性の問題から推奨されない方向。加えて本アプリの遅い経路は Server Component のページ描画で、Edge に載せると TCP を張れず node-postgres を捨てることになる（`src/infrastructure/db/` 全体に波及）。そもそも Vercel 側は 0.39秒しか占めていない |
| **無料枠のまま cron で Neon を温める** | **見送り**。無料枠の compute は 100 CU-hours/プロジェクト＝0.25 CU なら月400時間（1日13時間強）。日中だけ温めれば理論上は収まるが余裕がほとんど無く、**超過するとプロジェクトが停止する**。実運用のDBで踏む賭けとしては割に合わない |

**結論**: 打てる無料の手は打ち終わっている。残るのは Neon の停止そのものを止める＝有料化だけ。

## 6. 費用比較と採用案

Neon は2025年12月に従量課金へ移行し、**scale to zero の設定は Launch プラン以上**でできる（Free は5分固定・変更不可）。単価は Launch で **$0.106/CU-hour**、最低課金 $5/月。

| 案 | 内容 | 月あたりの compute | 概算（150円/ドル） |
|---|---|---|---|
| A | scale to zero を無効化（常時起動） | 0.25 CU × 730時間 = 182.5 CU-h | 約 $19.3（約2,900円） |
| **B（採用）** | サスペンドの待ち時間を1時間に延長 | 0.25 CU × 約480時間 = 120 CU-h | 約 $12.7（約1,900円） |
| C | 現状維持 | 実使用分のみ | 0円 |

**案B を採用した理由**: 無効化しなくても待ち時間は設定できる。1時間にしておけば日中の使用中はまず冷えず、寝ている間だけ落ちる。**体感は案A とほぼ同じで費用が3分の2**になる。案 B の想定 480時間は「起きている16時間は間隔が1時間未満で使う」という見積もりで、実績が出たら待ち時間の値を調整する。

**compute size は 0.25 CU のまま据え置く**。今回の遅さはコンピュートの大きさではなく起動待ちが原因で、上げると使用時間あたりの単価だけが上がる。

**副次的な効果**: Launch では**復元ウィンドウを7日まで延ばせる**（無料枠は6時間が上限で、これが伸ばせないことが [T-25](../案件/23_技術改善バックログ.md#t-25) の必要性を押し上げていた）。データ量が小さいため追加コストはほぼ無い。ただし T-25 が不要になるわけではない——7日の窓は Neon の中だけの話で、**N-06② のロックイン回避（他の Postgres へそのまま戻せる控えを外に持つ）は満たさない**。

## 7. 残作業・着手条件

1. **Neon コンソールで案B を設定する**（未実施）— Launch へアップグレード / サスペンド待ちを1時間 / compute size は 0.25 CU 据え置き / 復元ウィンドウを7日
2. **設定後に測り直す** — コンピュート起動の 1.67秒が消え、接続確立分だけが残るので、[T-130](../案件/23_技術改善バックログ.md#t-130)（`idleTimeoutMillis`）の切り分けが楽になる
3. **[T-129](../案件/23_技術改善バックログ.md#t-129) の `sslmode` を直す** — 本作業とは独立。環境変数の1語
4. **1か月ぶんの請求を見て待ち時間を調整する** — 想定より高ければ短く、冷える体感が残れば長く

**計測スクリプトはリポジトリに置いていない**（一時ファイルとして書き捨てた）。再現するなら §2 の4条件をそのまま組めばよい。定常的に測る必要が出たら `scripts/` へ置くかを別途決める。
