## 1. 動機と現状

- **T-26（git 運用ルール）**: git/ブランチ運用に明文規定がなく、実態は `main` 直コミットと PR が混在。PR のブランチ名も `claude/<説明>-<乱数>`（1ブランチを複数 PR で使い回した例あり）・`feat/<説明>`・dependabot の3系統が混在し、マージ済みリモートブランチが残置されていた。`main` への push＝本番デプロイ（Vercel）という制約の下で、変更の種類ごとの扱いを一貫させたい
- **T-06（並行開発体制）**: 単一ワークツリー・単一セッションで作業しており、別タスクが並行すると変更が交錯する（実際に、別セッション進行中の WIP を中断・除外して作業する事態が起きた＝T-06 起票の動機）。`git worktree` でタスクごとに独立したワークツリー／ブランチを持たせ、AI が複数タスクを並行実行できるようにしたい

両者は「マージ順序の調停・スキーマ変更の直列化」で不可分のため、1つの設計として本書に束ねる。

## 2. git 運用ルール（T-26）

単独作業・並行作業を問わず全作業に適用する恒常ルール。

### 2.1 リスク別ルーティング

変更の種類で入口を分ける。判断に迷ったらリスクの高い側（ブランチ＋PR）に倒す。

| 変更の種類 | 経路 |
|---|---|
| docs・軽微（typo・文言・挙動に触れない小修正） | `main` 直コミット。push（＝本番デプロイ）はオーナーの合図でまとめて行ってよい |
| コード・挙動の変更 | ブランチ → PR → CI 緑 → オーナー動作確認 → **合図でマージ**（マージ＝本番デプロイ） |
| スキーマ変更を含む | 上に加えて「本番へ migrate 適用 → マージ」の順序を厳守（[README](../../README.md)「スキーマ更新（本番マイグレーション）」が正） |

### 2.2 ブランチ命名と worktree／テストDB の対応

- ブランチ名は **`<タスクID>-<slug>`**（すべて小文字、使える文字は `a-z 0-9 -` のみ・**49文字以内**。スラッシュは使わない）。例: `t-26-git-strategy` / `fb-54-section-jump`。長さ上限は、テストDB名（`hitosuji_test_` ＋ 変換後のブランチ名）が PostgreSQL の識別子63バイト制限に収まる値
- タスクID は既存の台帳・要求の ID 体系（T-XX / FB-XX / F-XXX / N-XX）をそのまま使う。ID の無い作業は先に台帳へ起票するのが原則
- スラッシュを使わないのは、ブランチ名を **worktree ディレクトリ名**（`../hitosuji-wt/<ブランチ名>`）と**テストDB名**（`hitosuji_test_<ブランチ名の - を _ に置換>`）へ機械的に変換するため（§5.1）
- **1ブランチ＝1PR。ブランチは使い回さない**。マージ後はローカル・リモートともブランチを削除する。マージ方式は squash（main のログを線形に保つ現行実態を維持）のため `git branch -d` はマージを検出できず失敗する——マージ済みを確認のうえ `-D` で消す。GitHub の「Automatically delete head branches」を有効化してリモート側は自動削除に任せるのが望ましい
- `dependabot/*` ブランチはこの命名の対象外

### 2.3 マージ規律

- **自動マージ・CI 必須チェック化（ブランチ保護）は設けない**（T-01 の「検証のみ・手動マージ」方針の継承）。`main` への push・PR マージは常にオーナーの合図が前提で、ヘッドエージェントにも自動マージ権を与えない。ワーカーが push できるのは feature ブランチのみ
- 並行時のマージはヘッドが**マージキュー**で逐次調停する: 1本マージ → 残ブランチを rebase → CI 再走 → 次（並行度2〜3ならこれで十分。自動化しない）
- **スキーマ変更を含むブランチは常に最大1本**とし、マージキューの先頭付近に置く（§5.3）

## 3. 体制の結論と難所（T-06）

**体制は「ヘッド1＋ワーカーN」の2階層とし、統合は PR＋既存 CI（T-01）に乗せる**。worktree を切ること自体は `git worktree add` だけで済み、難所ではない。本質的な難所は次の2点で、この2点の設計が本検討の主題。

- **難所1: 共有リソースの分離** — worktree はファイルを分けるが、**DB（開発 :5432／テスト db-test :5433）・Drizzle マイグレーションのジャーナル・共有 docs（技術改善バックログ・ユーザーフィードバック・log_\*）は分かれない**。統合テストは全テーブル TRUNCATE でリセットする設計（`test-db.ts` の `truncateAll`）のため、複数 worktree が同じ db-test を同時に叩くと互いのデータを消し合う（→ §5）
- **難所2: 通信と調停の設計** — ヘッド↔ワーカー・ワーカー間のやり取りをどう処理するか。機構の選択肢は (a) サブエージェント（Agent ツール）と (b) Claude Code の Agent Teams（実験的機能）の2つ。あわせて、コンフリクト調停・マージ順序・「本番反映はオーナーの合図」規律の維持を体制に織り込む必要がある（→ §6）

## 4. 体制の全体像（ヘッド1＋ワーカーN）

並行モードへの切替は**オーナーの明示指示のみ**を契機とする（例「これとこれを並行で」）。既定は常に単独モード（メインセッションが実装・チャット差分でレビュー）で、AI が自律的に切り替える判断基準は設けない——「たまったら切り替える」型の基準はセッションをまたいで維持されないため。統合経路（ブランチ＋PR＋CI、§2）は両モードで同一なので、どちらで作っても後工程は変わらない。

```
オーナー ←対話→ ヘッドセッション（main 常駐・リポジトリ本体）
                    │ タスク分配・worktree/ブランチ作成・マージ順序調停・共有 docs 記入
                    ├─ worktree A（../hitosuji-wt/<task>）← ワーカー A
                    ├─ worktree B                         ← ワーカー B
                    └─ …
各ワーカー → feature ブランチへ push → PR → CI（T-01: lint/build/test）→ ヘッドが順序調停 → オーナー合図でマージ
```

- **ヘッド**: リポジトリ本体（main）に常駐する1セッション。タスク分割と影響範囲の見積り（`Explore` 委譲）、worktree／ブランチの作成・破棄、マージキューの管理、レビュー結果の集約、共有 docs への記入の一元化を担う。**コードは編集しない**
- **ワーカー**: worktree ごとに1つ。worktree の内側では現行 CLAUDE.md の運用をそのまま実行する（Explore/Plan → 実装 → verifier・code-quality-reviewer → spec-reviewer・test-reviewer）。worktree 内の景色は現在の単独セッションと同じ
- **挙動レベルの仕様判断は従来どおりオーナーとの対話でのみ決める**。ワーカーが仕様判断に突き当たったら手を止め、ヘッド経由でオーナーに上げる（docs 先行の最重要ルールは不変）
- 1タスク＝1 worktree＝1ブランチ＝1PR。ブランチ名は §2.2 の命名に従い、worktree ディレクトリ名と一致させる

## 5. 共有リソースの分離（難所1）

### 5.1 テストDB — worktree ごとに分離（Phase 2 実装済み）

- **unit テストは DB 不要**なので並行しても無干渉
- 統合テストの衝突源は db-test（:5433 の `hitosuji_test`）の共有。`TEST_DATABASE_URL` は環境変数で差し替え可能（`src/infrastructure/db/testing/test-db.ts`）で、globalSetup も向き先へマイグレーションを当てるだけ。**同一 db-test コンテナ内に worktree ごとの DB（`hitosuji_test_<task>`）を作り、worktree ごとに `TEST_DATABASE_URL` を変えるだけで分離が成立**する（コンテナ追加・ポート追加不要、tmpfs のまま）
- **実装（Phase 2）**: `scripts/wt-new.sh` が db-test 内に worktree 用 DB を CREATE し、worktree 直下に **`.env.worktree`**（`TEST_DATABASE_URL` 1行。Next.js の自動読み込み対象外の名前）を生成する。`vitest.config.ts` が起動時にこのファイルを読む——ただし**シェルから渡された環境変数が常に優先**（CI は `.env.worktree` が存在しないため完全に無影響）。ワーカーは何も意識せず `npm run test:int` を打てば自分の DB に向く
- worktree 内の統合テストは従来どおり直列（`fileParallelism: false`）。worktree 間は DB が別なので同時実行できる
- `wt-new.sh` を使わない簡易並行（手動 `git worktree add`）の場合は、ローカル検証を lint・build・`test:unit` までとし、統合テストは PR の CI に委ねる（Phase 1 の運用）

### 5.2 開発DB・dev サーバ

実機の動作確認はヘッド側（本体ワークツリー）でブランチを checkout して行う運用にすれば、開発 DB（:5432）もポート 3000 も分離不要。このため `wt-new.sh` は `.env.local` を worktree へコピーしない（`test:unit` は env 不要、`test:int` は `.env.worktree` で足りる）。並行 dev が本当に必要になったら PORT と DB 名の割当を検討する。

### 5.3 スキーマ変更（Drizzle マイグレーション）は並行不可

マイグレーションはジャーナル＋連番で管理され、複数ブランチで生成すると必ず衝突する。**「スキーマ変更を含むタスクは常に最大1本、かつマージキューの先頭付近に置く」を規約**にする（§2.3）。

### 5.4 共有 docs はヘッドが一元記入

`docs/案件/23_技術改善バックログ.md`・`docs/案件/21_ユーザーフィードバック.md`・各 `log_*.md` は最大の衝突源（T-06 起票の動機となった交錯もこれ）。**記入はヘッドに一元化**し、ワーカーが触ってよい docs は自タスクの仕様として事前に確定した範囲のみとする。

## 6. 通信と調停の設計（難所2）

### 6.1 機構の比較 — サブエージェント vs Agent Teams

公式ドキュメント（code.claude.com/docs の agent-teams / sub-agents）調査の要点:

| 観点 | サブエージェント（Agent ツール） | Agent Teams |
|---|---|---|
| ステータス | 安定・全プラットフォーム | **実験的**（要環境変数）・**CLI のみ**（web/リモートセッション不可） |
| 通信 | ヘッドへの報告のみ。**SendMessage で完了後も往復継続が可能** | リード↔メイト＋メイト同士の直接通信、共有タスクリスト（依存関係・self-claim） |
| worktree | **isolation: worktree が組み込み** | 組み込みなし（作業ディレクトリはリードと同じ。指示で誘導） |
| 入れ子エージェント | **可能（5階層まで）**＝ワーカーが自分の verifier 等を起動できる | in-process メイトは**バックグラウンドのサブエージェント起動不可**（split pane なら可、ただし tmux 必須） |
| オーナーへの質問 | AskUserQuestion 不可 → ヘッド経由で中継 | 同様（permission プロンプトもリードに集約） |
| 既知の問題 | — | `/resume` でメイトが復元されない、タスク状態のラグ、1セッション1チーム |
| コスト | 低〜中 | 高（メイト数に比例） |

### 6.2 選定 — サブエージェント方式を採る（Agent Teams は再検討条件付きで見送り）

**Phase 1〜2 は「バックグラウンド・サブエージェント（worktree 分離）＋ SendMessage 継続」**とする。機能の優劣ではなく、本体制がそもそも「濃い通信」を必要としない設計であることが理由。

1. **通信は細く設計してある**: 影響ファイルが重なるタスクは最初から並行させず（予防が主・調停が従）、統合は PR＋CI という成果物を媒介にする。ワーカー間のやり取りは設計上ほぼゼロが正常で、Agent Teams の差別化点（メイト間直接通信・self-claim）は並行度2〜3では出番がない。**ワーカー同士が直接調整を始めたら「タスク分割が間違っていた」シグナル**として扱い、統合か直列化に倒す
2. **必要な能力はサブエージェントで揃う**: worktree 分離は組み込み、入れ子起動でワーカーが自分の worktree 内で verifier / code-quality-reviewer を回せる（「worktree 内は現行 CLAUDE.md のまま」が成立）。SendMessage 継続で「仕様質問 → オーナー確認 → 回答して続行」の往復もできる。一方 Agent Teams は in-process メイトがバックグラウンド起動できず、CLAUDE.md の「verifier と code-quality-reviewer を並列バックグラウンド起動」と正面衝突する（回避には tmux が必要）
3. **実験的機能への依存は運用に合わない**: CLI 限定のためリモートセッションと併用できず、`/resume` でメイトが消える問題は docs 主導・長時間タスクの運用と相性が悪い

**Agent Teams の再検討条件**（いずれかが揃ったら）: 並行度が常時4以上になり共有タスクリストの自律分配が欲しい／ワーカーが数時間単位で常駐しアイドル通知・随時割り込みが要る／機能が experimental を外れ `/resume` 問題が解消し worktree 連携が公式サポートされる。

### 6.3 通信プロトコル — 定型の成果物を基本、メッセージは例外処理に限定

- **ヘッド → ワーカー（起票時）**: 起動プロンプトで「タスクカード」を渡す。内容＝タスクID／ブランチ名／確定済み仕様の参照（docs の該当節）／触ってよいファイル範囲・触ってはいけない共有 docs／完了条件（lint・build・unit 緑＋push＋報告書式）。ワーカーはヘッドの会話文脈を持たないため、**仕様はすべて docs 参照で自己完結させる**（「仕様は docs が正」の強制にもなる）
- **ワーカー → ヘッド（3種類に限定）**:
  1. **完了報告**（定型）: ブランチ名・変更ファイル一覧・検証結果・仕様上の注意点。ヘッドはこれを受けて PR 作成 → CI 確認 → マージキューへ
  2. **仕様質問**（ブロッカー）: 手を止めてターンを終え質問を返す。ヘッドがオーナーに確認 → 必要なら docs を先に直す → SendMessage で回答を返して続行
  3. **中断報告**: 影響範囲が事前見積りを超えた場合。ヘッドがタスクの分割・直列化を再判断
- **ワーカー ↔ ワーカー**: 直接通信は設けない。タスク間の接点は必ずヘッド経由（実体はマージキューでの rebase 調停＝§2.3）

## 7. 運用手順（Phase 1〜2）

並行作業1件あたりのヘッドの一連。ワーカーをサブエージェントにする場合も、オーナーが worktree で別セッションを開いてワーカーにする場合も同じ。

1. タスク分割と影響範囲の見積り（`Explore` 委譲）。**影響ファイルが重なるタスクは並行させない**（直列化する）
2. `git fetch` で起点（main）を最新化してから `npm run wt:new -- <ブランチ名>` — worktree（`../hitosuji-wt/<ブランチ名>`）＋ブランチ＋`npm ci`＋テストDB＋`.env.worktree` を一括準備
3. ワーカーを起動し、タスクカード（§6.3）を渡す。作業ディレクトリは手順2の worktree を指定する
4. 完了報告を受領 → PR 作成 → CI 緑を確認
5. マージキューで調停: オーナー動作確認（ヘッド側でブランチを checkout）→ **合図でマージ**（squash）→ 残ブランチを rebase → CI 再走 → 次
6. `npm run wt:rm -- <ブランチ名>` — worktree・ローカルブランチ・テストDB を後片付け。リモートブランチも削除（§2.2）

## 8. CLAUDE.md への反映（2026-07-25 実施済み）

採用時の改訂点として挙げていた4点は CLAUDE.md へ反映済み。

1. 「コードの編集は常にメインセッションが行う」→ 単独モード／並行モードの条件分岐に改訂（ヘッドは編集しない／ワーカーは自分の worktree 内で編集する）
2. **オーナーのレビュー導線**: ワーカーの編集はヘッドのチャットに差分表示されないため、並行モードでは **PR の diff がレビューの正**。動作確認はヘッド側でブランチを checkout して現行どおり
3. **実装完了後のフロー**（レビュー → 動作確認 → push 待ち）は並行モードでは PR 単位に読み替え
4. アーキテクチャ定義書は改訂不要（コード配置・依存方向・テスト戦略は変わらない）
