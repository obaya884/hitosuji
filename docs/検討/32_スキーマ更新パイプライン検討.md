## 1. 動機と現状

現状の本番マイグレーションは**手元での手動実行**（CLAUDE.md「本番マイグレーションの手順」）。

1. Neon から接続文字列（unpooled）を取得し `.env.migrate` に置く
2. `set -a; . ./.env.migrate; set +a; npm run db:migrate`
3. 成功を確認して `.env.migrate` を削除し push（＝デプロイ）

これを**リモート上で完結**させたい。接続情報はローカルの `.env.migrate` ではなく**リポジトリ／Environment シークレット**に置く想定。

## 2. 結論

**技術的には可能**。`drizzle-kit migrate` は `DATABASE_URL` を与えれば動き（`drizzle.config.ts` は env を読むだけ）、Neon は GitHub Actions ランナーから到達できる。実行自体は標準的なパターン。

ただし本質的な難所は「migrate の実行」ではなく次の2点で、**この2点の設計が本検討の主題**。

### 難所1: Vercel 自動デプロイとの順序保証

`vercel.json` があり、Vercel は main への push で自動デプロイする。CLAUDE.md の「**必ず migrate → push（デプロイ）の順**」は、新コードが未作成テーブルを参照して本番が壊れるのを防ぐ規律。リモートで migrate するなら **migrate 完了までデプロイを待たせる**仕組みが要る。無いと GitHub Actions の migrate と Vercel の deploy が競争して逆順になり得る。

### 難所2: public リポジトリでのシークレット露出

本リポジトリは公開（CLAUDE.md「このリポジトリは public」）＝誰でも fork して PR を出せる。接続情報をシークレットに置くのは正しい場所だが、**fork PR のワークフローにシークレットを渡さない**設計が必須。

## 3. 実現方式（A を採用。B・C は将来の選択肢）

扱う課題が「実行の場所」→「順序の自動保証」→「順序依存の除去」と上がっていく（A は低リスクで即効、C は最も堅牢だが運用コストが高い）。**個人開発の規模では A（実行のリモート化）で必要十分**と判断し、A を採用した。スキーマ更新のある PR はラベル CI（T-21）＋注意コメントで実行漏れに気づける運用にしてあり、B・C の順序自動保証・ゼロダウンタイムまでは求めない。**B・C は運用が変わったとき用の将来の選択肢として記録に留める**（現時点では過剰。いずれも後から着手できる two-way door）。

| 案 | 何を解決するか | 仕組み | 主なトレードオフ |
|---|---|---|---|
| **A** | 実行をリモート化 | `workflow_dispatch`（手動ボタン）で `migrate` を実行（退避は Neon PITR 依拠）。デプロイは従来どおり | 順序は**人間が担保**（現行と同じ）。パイプラインとしての自動保証はまだ無い |
| **B** | 順序を機械保証 | main への push で `migrate → 成功時にデプロイ発火`。Vercel 自動デプロイは無効化して一本化 | 「マージ＝即・自動で本番反映」になる。慎重運用から一歩踏み込む |
| **C** | 順序依存を除去 | マイグレーションを常に後方互換（expand/contract）にし、旧コードでも新スキーマで動く形にする | パイプラインの保証でなく**運用規律**。破壊的変更が複数リリースに伸びる |

### 案A: 手動トリガーで migrate をリモート実行（deploy は従来どおり）

- **仕組み**: `workflow_dispatch` の「Run workflow」ボタンで `migrate` ジョブを回す（自動 backup ステップは持たず、退避は Neon PITR に依拠＝§5）。Vercel デプロイは従来どおりマージ／push で別途行う
- **順序保証**: 新規マイグレーションを持つ **PR ブランチから** Run workflow で migrate → 成功後にマージ（＝デプロイ）、の順で回す。人間が順序を担保する（＝現行手順の"実行場所"だけをローカルからリモートへ移す）。**この順序のため Environment の Deployment branches を main 限定にはしない**（下の前提設定を参照）
- **位置づけ**: ローカルの `.env.migrate` 手順を、Environment シークレット＋ボタンに置き換えるだけの**最小の一歩**。ボタン＝オーナーの合図なので「デプロイはオーナーの合図」規律を保てる
- **主な実装項目**: `workflow_dispatch` ジョブ / 専用 Environment（`db-migrate`）にシークレット配置＋承認ゲート / migrate 前の退避点（§5）
- **実装済み（2026-07-23）**: `.github/workflows/db-migrate.yml`。`workflow_dispatch`（入力 `confirm` に `migrate` と打たせる誤爆防止付き）＋ `environment: db-migrate` の承認ゲートで `npm run db:migrate` を実行する。接続文字列は `MIGRATE_DATABASE_URL`（unpooled）を `DATABASE_URL` env に渡す。**次の GitHub 側設定が済むまで動かない**:
  - Settings → Environments → **`db-migrate`** を新規作成し **Required reviewers** にオーナーを設定（＝承認ゲート）。**Vercel が使う "Production" 環境とは分ける**（migrate の承認ゲートをデプロイ flow に相乗りさせない）
  - **Deployment branches は `main` 限定にしない**。案A は「migrate → 手動マージ（＝デプロイ）」の順のため、新規マイグレーションを持つ **PR ブランチから dispatch する**必要がある（main 限定にすると先にマージ＝デプロイが要る前提になり順序が逆転する）。ブランチ制限は、デプロイをパイプラインが握る**案B**で導入する。案A のセキュリティは write 権限＋承認ゲートで担保する
  - 同 Environment に Secret **`MIGRATE_DATABASE_URL`** = Neon の接続文字列（**Pooled を外した unpooled**）を登録
  - 「Run workflow」ボタンは本ワークフローが **default ブランチ（main）にマージされてから** Actions タブに出る（GitHub の仕様）

### 案B: マージ契機で migrate → deploy を自動化（見送り・将来の選択肢）

> 個人開発の規模では過剰につき見送り。順序の自動保証が要るようになったら着手する。以下は将来の設計メモ。

- **仕組み**: main への push（＝マージ）で `migrate → 成功時に Vercel デプロイ発火`。**Vercel の git 自動デプロイは無効化**（Ignored Build Step もしくは git 連携解除）し、このパイプラインに一本化する。デプロイは Deploy Hook か Vercel CLI で明示発火
- **順序保証**: パイプラインが migrate 成功後にのみ deploy を叩くので、**順序が機械的に保証**される（難所1が構造的に解消）
- **トレードオフ**: 「マージ＝即・自動で本番反映」になる。現行の「デプロイはオーナーの合図」を、**マージ操作そのものが合図**と再定義することになる。誤マージの影響が即本番に出る
- **主な実装項目**: Vercel 自動デプロイの無効化 / Deploy Hook のシークレット化 / migrate 失敗時は deploy を発火しない分岐 / 結果通知

### 案C: 後方互換マイグレーション（expand/contract）で順序依存を消す（見送り・将来の選択肢）

> 個人開発の規模では過剰につき見送り。破壊的変更でダウンタイムが問題になったら運用規律として重ねる。以下は将来の設計メモ。

- **仕組み**: マイグレーションを**常に後方互換（加算的）**にする。列追加は nullable ないし default 付き、NOT NULL 化・リネーム・削除は「①追加 → デプロイ → ②旧参照を消すデプロイ → ③削除」の複数リリースに分割する
- **効果**: migrate と deploy の**順序に依存しなくなる**（旧コードが新スキーマで動く）。案 B の順序保証が緩くても壊れず、ゼロダウンタイム更新に近づく。B の上に載せる最終形
- **トレードオフ**: パイプラインの保証ではなく**運用規律**。破壊的変更が2〜3リリースに伸び手間が増える。**単一ユーザーアプリにはしばしば過剰**

## 4. セキュリティ設計（public 対応・どの案でも必須）

- DB 接続情報は **migrate 専用の GitHub Environment（`db-migrate`）のシークレット**に置き、**required reviewers（承認ゲート）**を付ける。migrate ジョブをその environment に紐付ければ、承認しない限りシークレットにアクセスできない（誤発火・不正発火の両方に効く）。Vercel が使う "Production" 環境と分けることで、migrate の承認ゲートがデプロイ flow に相乗りしない
- migrate ジョブは **`pull_request` イベントでは絶対に走らせない**。`workflow_dispatch`（案A）か `push: main`（案B）のみにし、**fork PR にシークレットを渡さない**
- 接続文字列は Neon の **unpooled** を使う（現行手順どおり。マイグレーションは pooler 経由だと advisory lock 等で不都合が出やすい）
- **ログに接続文字列を出さない**: `set -x` 禁止・`echo` での展開禁止。`drizzle-kit migrate`・`pg_dump` は接続文字列を標準出力に出さないが、ワークフローで不用意に展開しない
- 可能なら Neon 側に **DDL 専用ロール**を分け、アプリ実行時ロールと分離する
- Deploy Hook URL（案B）も**シークレット扱い**。値をログ・コミットに残さない

## 5. ロールバック安全

- 既存 `scripts/db-backup.sh`（`pg_dump` カスタム形式）を migrate 前に実行できる。ただし **backups には実データ（オーナーの生活が読める内容）が入る**ため、public リポジトリの **artifact として保存するのは不向き**（保存しない、または保持先・保持期間を厳しく管理する）
- より安全なのは **Neon のブランチ／PITR** を migrate 前の退避点にすること。migrate 前にブランチを切る、または復元ポイントを控える
- migrate 失敗時はパイプラインを**失敗で止め、デプロイを発火しない**（案B）

## 6. 採用した方針

- **案A を採用**（実装済み）: migrate を `workflow_dispatch` ＋ Environment 承認ゲートでリモート化（deploy は従来どおり）。順序リスクは現行と同じ＝増えない。ローカル `.env.migrate` を手放せる
- あわせて、スキーマ更新のある PR に**ラベル（T-21）＋ migrate 実行を促す注意コメント**を出し、README に運用を明記して事故を防ぐ
- **案B・C は見送り**（§3）。個人開発の規模では順序の自動保証・ゼロダウンタイムは過剰。必要になれば後から着手できる（two-way door）

## 7. 残作業・将来の着手条件

- **案A は実装済み**（2026-07-23）。GitHub 側設定（`db-migrate` Environment・`MIGRATE_DATABASE_URL`・required reviewers）を済ませれば「Run workflow」ボタンから本番へ migrate できる
- **運用の明瞭化**（本スコープ）: スキーマ更新 PR への注意コメント（label workflow 拡張）と README への運用記載
- **案B・C の将来の着手条件**: 案B は「マージ＝即・自動で本番反映」への移行判断が要る。**順序の自動保証やゼロダウンタイムが必要になった／スキーマ変更の頻度が大きく上がった**ときに案 B → C を再検討する（それまでは見送り）。着手時に詰める論点は §3 の各案メモ（Vercel 自動デプロイ無効化の手段・Deploy Hook 運用・Neon の DDL 専用ロール分離）
