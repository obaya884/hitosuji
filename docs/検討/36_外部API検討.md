## 1. 動機と範囲

Claude Code や自作スクリプトから hitosuji のデータを読みたい（その日の予定・実行ログ・集計を AI に渡して振り返りや計画に使う等）。いまの入口は画面（Server Component）と Server Action だけで、どちらも外から呼べる形ではない。

範囲は次で確定（2026-10-17 オーナー回答）。

| 項目 | 決定 |
|---|---|
| 操作 | **読み取りのみ**。打刻・タスク追加などの書き込みは対象外 |
| 呼び手 | **Claude Code・自作スクリプト／プログラム**。claude.ai のカスタムコネクタは対象外 |

この2点で、当初挙げた論点のうち次が不要になった。

- 打刻時刻の出どころ（クライアント時刻原則との整合）
- 実行中タスク最大1件の DB 保証（画面と API の同時開始）
- 開いている画面への反映・楽観的更新との衝突
- 再送による重複作成（Idempotency-Key）
- OAuth（claude.ai コネクタが要求するもの。Claude Code・スクリプトは任意のヘッダを送れる）

## 2. 入口の形

| 案 | 内容 | 評価 |
|---|---|---|
| **A. REST（JSON）Route Handler** | `src/app/api/v1/...` に GET を置く | 採用。curl・fetch で呼べ、Claude Code からも Bash で叩ける |
| B. MCP サーバ | 同じ Next 上に MCP の route を置く | 見送り。Claude Code 専用の便利さはあるが、自作スクリプトからは REST の方が素直。必要になれば A の上に薄く足せる |

Claude Code からの使い勝手は、REST を叩く手順を書いたスキル（またはプロンプト）で補う。

## 3. 認証

いまの `src/proxy.ts` は静的資産を除く全パスに Basic 認証をかけている（N-03）。API を同じ Basic 認証で守ることもできるが、採らない。

- **画面と同じ資格情報を機械に配ることになる**——スクリプトや Claude Code の設定に置いた値が漏れると画面にも入れる
- **API だけを止められない**——漏洩時のローテーションが画面のログインまで巻き込む

**採用案: `/api/` 配下だけ Bearer トークンで認証する**。

- `proxy.ts` でパスを分岐する。`/api/` 配下は `Authorization: Bearer <token>` を照合し、Basic 認証は見ない。それ以外は従来どおり Basic 認証
- トークンは新しい環境変数（例 `API_TOKEN`）。**呼び手ごとに分けず1本**、正本は**平文で持つ**（ハッシュで持たない。Vercel の Sensitive 指定で読み出せないため、ハッシュ化の効果が小さい）。照合は `crypto.timingSafeEqual`（長さの差で例外にならないよう、両辺をハッシュしてから比べる）
- 認証を要求するかは既存と同じく `VERCEL_ENV` で決める（ローカル開発は素通し）。デプロイ環境で未設定なら 500（N-03 ③と同じ倒し方）
- 失敗時は 401（`WWW-Authenticate: Bearer`）。応答本文に設定状態を書かない
- 値の控えは Basic 認証と同じく `.env.credentials`。**リポジトリには値も本番 URL も書かない**（スキルやスクリプトは URL とトークンを環境変数から読む）

読み取り専用でも、漏れれば**オーナーの生活が読める全データ**が出る。トークンは十分長いランダム値にし、漏洩時は `vercel env rm` → `add` → 再デプロイで差し替える。

## 4. 何を返すか

既存の読み取りユースケースをそのまま使える。

| エンドポイント案 | 中身 | 使うユースケース |
|---|---|---|
| `GET /api/v1/days/{date}` | その日のタスク一覧（セクション別・打刻・見積・モード・プロジェクト） | `listDailyList` |
| `GET /api/v1/days/{date}/review` | 実行ログ・合計実績・モード別／プロジェクト別集計・先送り | `listDailyReview` |
| `GET /api/v1/sections` | セクション（ID→名前と時間帯の解決用） | `listSections` |
| `GET /api/v1/projects` | プロジェクト（ID→名前の解決用） | `listProjects` |
| `GET /api/v1/modes` | モード（ID→名前の解決用） | `listModes` |
| `GET /api/v1/routines` | ルーチンの定義（繰り返しルール・見積・開始想定時刻・モード・プロジェクト・有効/無効） | `listRoutines` |

マスタは一括で返さず、種類ごとに分ける。呼び手は要るものだけを取れる。

- **マスタ3本はアーカイブ済みも返し**、アーカイブかどうかを各項目に持たせる。過去日のタスクはアーカイブ済みのマスタを参照しうるので、ID から引けなくなるのを避ける。物理削除の可否（`deletableIds`）は画面の都合なので返さない
- **ルーチンは無効化中も返し**、有効かどうかを各項目に持たせる。並びは `listRoutines` と同じ開始想定時刻の昇順。返すのは定義であって、ある日に展開されるかの判定結果ではない（§4.1）

`{date}` に `today` を許し、サーバ側で日界（F-116）を踏まえて解く（`resolveToday`）。呼び手が日界を知らなくても「今日」を取れる。

**複数日の範囲取得（週・月）は v1 に含めない**。いまのリポジトリは1日単位（`listByDate`）なので、呼び手が日ごとに呼べば済む。頻繁に要るとわかったら範囲取得のリポジトリメソッドを足す。

### 4.1 表示時の書き込みを API では行わない

デイリー画面は、表示のたびに**ルーチン展開**（F-301）と**繰り下げ**（F-113）を DB へ書き込んでから一覧を取る（`src/app/(daily)/page.tsx`）。一方レビュー画面は読み取り専用として、これらを行わない（画面定義書04 §1）。

**API はレビュー画面に倣い、保存されている状態をそのまま返す**（GET で DB を書き換えない）。

- 理由: 読み取りのつもりの呼び出しが並び順を変えるのは驚きが大きい。繰り下げは「いま」を基準に動くので、スクリプトの呼び出しで並びが動くことになる
- 引き換え: その日まだ画面を開いていなければ、**今日以降のルーチン由来のタスクがまだ無い**ことがある。また未実行タスクの位置は最後に画面を開いた時点のまま
- 将来、未展開のルーチンも見たくなったら「展開したらこうなる」を書き込まずに計算して返す（`routinesToExpand` は domain の純関数なので組める）

### 4.2 応答の形

ドメイン型をそのまま JSON にせず、**API 用の DTO を presentation 側で組む**。内部の型を変えるたびに外部の契約が変わるのを避けるため。

- **応答は常にオブジェクトで包む**（`{ "routines": [...] }` のように。配列を裸で返さず、項目を足しても呼び手が壊れないようにする）
- モード・プロジェクト・セクション・バンドルへの参照は `{ "id", "name" }` の組で返し、未設定は `null`（呼び手がマスタの各エンドポイントを引かずに読める）
- 時刻は ISO 8601（オフセット付き）、論理日付は `YYYY-MM-DD`、時間帯は `HH:MM`、実績・見積は分
- 内部の値の持ち方を外へ出さない: 見積の未設定（内部は `0`）は `null`、ルーチンの曜日（内部はビットマスク）は `["mon", "wed"]` のような曜日名の配列、並び（`sortOrder`）は返さず配列の順で表す。分割元・当初の日付など画面の操作にしか使わない列も返さない
- 状態は導出して明示する: タスクの `status`（`unstarted` / `running` / `done`）と、完了タスクの `actualMinutes`。セクションの `endTime` も導出して返す（アーカイブ済みは `null`）
- ルーチンの繰り返しは `recurrence` に種類ごとの判別共用体で持たせる（`{ "type": "daily" }` / `{ "type": "weekly", "weekdays", "weekInterval" }` / `{ "type": "monthly", "monthDay" }` / `{ "type": "interval", "intervalDays" }`）
- **画面の警告は返さない**（放置された実行中タスク F-209、過去日の未実施件数 F-124）。画面で気づかせるための表示であり、API の読み取り対象ではない

各エンドポイントの応答の骨格:

| エンドポイント | 骨格 |
|---|---|
| `days/{date}` | `date`・`progress`（`done` / `total`）・`sections[]`（`section`〔未設定の組は `null`〕・`totalEstimateMinutes`・`tasks[]`） |
| `days/{date}/review` | `date`・`totalActualMinutes`・`log[]`（タスクと同じ形を開始順）・`byMode[]` / `byProject[]`（参照・`minutes`・`percent`）・`postponed[]`（集計対象外の日は `null`。対象の範囲は実装時に確かめて API 定義書へ書く） |
| `sections` | `id`・`name`・`startTime`・`endTime`・`isDayStart`・`archived` |
| `projects` | `id`・`name`・`archived` |
| `modes` | `id`・`name`・`color`・`archived` |
| `routines` | `id`・`name`・`estimateMinutes`・`scheduledStartTime`・`mode`・`project`・`bundle`・`url`・`recurrence`・`startDate`・`endDate`・`active` |

タスク1件の項目は `id`・`name`・`status`・`estimateMinutes`・`startedAt`・`endedAt`・`actualMinutes`・`mode`・`project`・`bundle`・`url`・`comment`・`highlighted`・`routineId`・`postponedCount`。
- エラーは `{ "error": "<コード>" }`（例 `invalid_date`）。UI 向けの日本語文言は返さない
- キャッシュさせない（Next 16 の Route Handler の既定挙動は実装時に `node_modules/next/dist/docs/` で確認する）

### 4.3 操作の契約を OpenAPI で配る

呼び手（とくに AI）が会話や推測ではなく**機械可読な契約**を頼りに API を扱えるよう、OpenAPI 3.1 の文書を API 自身が返す。

- `GET /api/v1/openapi.json` で返す。認証は他の API と同じ Bearer（呼び手は既にトークンを持っている。public リポジトリなので中身自体は秘密でないが、到達できる URL を外へ知らせないため）
- `servers` には本番 URL を書かない（相対の `/` だけにする。CLAUDE.md「このリポジトリは public」）
- Claude Code には「まず `openapi.json` を読んでから呼ぶ」作法を渡す（§5 のスキル）

契約として各操作に明示するもの:

| 観点 | OpenAPI での表し方 |
|---|---|
| 何を読むか（どのデータか） | `summary` / `description`。保存されている状態をそのまま返す（§4.1）ことも書く |
| 入力 | `parameters`（`date` は `YYYY-MM-DD` か `today`） |
| 出力 | `responses.200` の JSON Schema（§4.2 の DTO） |
| 権限 | `securitySchemes`（bearer）。全操作が読み取り専用であることを `description` に書く |
| 失敗時の扱い | `400`（`invalid_date`）・`401`・`500` をエラーコードの `enum` 付きで定義し、呼び手がどう振る舞うべきか（再試行してよいか等）を書く |

**契約と実装が食い違わない仕組みを先に決める**。OpenAPI を手書きして実装と別々に保守すると、改訂のたびにずれる（本プロジェクトが docs で何度も踏んだ事故と同じ構造）。

| 案 | 内容 | 評価 |
|---|---|---|
| A. 手書きの OpenAPI＋契約テスト | 仕様を TS の定数で書き、統合テストで実応答をその Schema で検証する | 依存は検証器のみ。ただし DTO の型と Schema を二重に書く |
| **B. スキーマを1か所に書いて両方を導出** | DTO を zod 4 で定義し、TS 型（`z.infer`）と JSON Schema（`z.toJSONSchema`）を同じ定義から得る。paths は数本なので手で組む | 採用候補。二重定義が無く、応答の実行時検証にも使える。依存が1つ増える |
| C. コードからの自動生成ツール | ルート定義から OpenAPI を生成するライブラリに乗る | 見送り。GET 数本の API には仕組みが大きい |

B でも「実応答が Schema に合うか」の契約テストは置く（導出元が同じでも、route が DTO を通さずに返す誤りは防げないため）。

### 4.4 人間向けの API ドキュメント（`/api-docs`）

同じ OpenAPI 文書を、オーナーがブラウザで読める参照ページとしても出す。説明を手で別に書かないので、契約とページがずれない。

- **置き場所は画面側の `/api-docs`**（`/api/` 配下に置かない）。認証は画面と同じ Basic 認証になり、ブラウザでそのまま開ける。機械は Bearer で `openapi.json`、人間は Basic で `/api-docs` と入口を分ける。GitHub Pages などでの公開はしない（API の存在を外へ知らせることになるため）
- **表示には Scalar（`@scalar/api-reference`）を使う**。CDN から版を固定して読み込み、npm の依存は増やさない。OpenAPI 文書はサーバ側でページに埋め込んで渡す（`content`）ので、仕様の取得口を別に設けない
- **試行機能は使う**。`servers` は相対の `/` なので、リクエストは同じオリジンの `/api/v1/` へ飛び、外部プロキシは要らない。Bearer トークンはページで入力し、ブラウザに保存しない（`persistAuth` は既定の無効のまま）
- **組み込みの AI チャット（`agent`）と MCP 連携は無効にする**。OpenAPI 文書やトークンを外部へ渡す経路を作らない
- **CI で `redocly lint` を回し**、OpenAPI 文書の書き方の誤りを機械的に検出する（`npx @redocly/cli` を CI でだけ使う）

表示ツールの比較（2026-11-08 時点。いずれも MIT か Apache-2.0 で、直近2週間以内に更新あり）:

| 候補 | 試行機能 | 仕様の渡し方 | 評価 |
|---|---|---|---|
| **Scalar** | あり（Bearer の入力・事前入力） | JSON を直接渡せる | 採用。読みやすさと試行を両立する。AI チャット・MCP 連携は設定で切る |
| Redoc | なし（試行は有償のホスト版のみ） | URL で指定 | 見送り。読み物としては最も簡潔だが試行できず、URL 指定のため仕様の取得口が別に要る |
| Swagger UI | あり | JSON を直接渡せる | 見送り。最も普及しているが見た目が古い |
| Stoplight Elements / RapiDoc | あり | Web Component に渡す | 見送り。Scalar を上回る利点が今回の用途に無い |

## 5. 実装に要るもの

1. **docs 先行**: 要求定義書 §6.6 に新しい ID（例 F-603「外部プログラムからデータを読み取れる」）、N-03 に「機械向けの認証」を含める改訂。要件定義書に方式の要約。契約（エンドポイント・DTO・エラーコード）は新しい仕様文書 `docs/仕様/18_API定義書.md` に置く
2. **認証の分岐**: `proxy.ts` に `/api/` の Bearer 照合を足す。ユニットテストで「API に Basic を送っても通らない」「画面に Bearer を送っても通らない」を押さえる
3. **Route Handler**: §4 の GET 6本と `openapi.json`。あわせて画面側に `/api-docs`（§4.4）。合成（`resolveToday`→ユースケース）は短いのでページと同じく各 route に書く。ページ側から合成を共有層へ切り出す作業は、**書き込みをしない今回は不要**
4. **入力検証**: `{date}` は既存の `isValidLogicalDate` で足りる。スキーマ定義には §4.3 案B なら zod 4 を入れる
5. **テスト**: route の統合テスト（`*.int.test.ts`）。実応答が OpenAPI の Schema に合うかの契約テストを含める
6. **Claude Code 用のスキル**（任意）: URL とトークンを環境変数から読み、まず `openapi.json` を取得してから叩く手順。public リポジトリに置くなら値は書かない

## 6. 運用面の注意

- **DB の起動**: 呼び出しのたびに Neon が起きる（[34](./34_初回応答の遅延とNeonプラン検討.md)）。高頻度のポーリングは避ける（読むのは振り返り・計画のときだけ、が想定）
- **レート制限**: トークン漏洩時の被害上限として、Vercel Firewall で `/api/` に上限をかけるかを検討（Hobby プランで使える範囲は要確認）
- **読ませる内容は AI への入力になる**: タスク名・コメント・URL はオーナー自身が書いたものだが、Claude Code に渡す以上はプロンプトの一部として扱われる点だけ意識しておく

## 7. オーナー裁定（2026-10-17 すべて承認）

1. 返すものは §4 の GET 6本（タスク一覧・レビュー・セクション・プロジェクト・モード・ルーチン）とする（2026-11-08 改訂。当初はマスタ一括の3本）
2. API では表示時の書き込み（ルーチン展開・繰り下げ）をしない（§4.1）
3. 認証は `/api/` 配下だけ Bearer に分ける（§3）
4. 契約は zod 4 から型と JSON Schema を導出して作る（§4.3 案B）
5. 人間向けの参照ページを画面側の `/api-docs` に置き、表示には Scalar を使う（§4.4。2026-11-08 追加）
