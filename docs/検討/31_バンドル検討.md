## 1. 動機（オーナーの出発点）

- A→B→C の順で実行すると良い流れが作りやすい、というタスクの並びを**確かに実行する**ための機能
- タスクの流れを「バンドル」として**視覚的に示す**ことで集中を生む

関連する既存要求: F-113（リストが時間の流れに追随）・F-114（消化進捗）・F-301〜（ルーチン）・F-204（中断）。ハイライト（F-118）とは別軸（あちらは単体タスクの強調、こちらは複数タスクの束ね）。

## 2. 現時点の合意事項

対話（2026-07-22）で次まで合意した。**まだ確定＝要求化ではない**が、見せ方（§3）とデータモデル（§4）はこの線で確定扱い。

| 論点 | 合意 |
|---|---|
| 正体 | 使い回せるテンプレート＝**ルーチンの集合**。当日タスクを手動で束ねるアドホック②は**当面スコープ外**（後から tasks.bundle_id 流用で足せる。スキーマ変更なし）。非ルーチンのタスクセットを手動で一括登録する③は**検討メモ段階**（§4） |
| 順序の扱い | **集合モデル（順序を持たない）**。ドミソもソミドも同じ和音、という捉え方。並びは scheduled_start_time が決める。順序を app で担保しない代わり、後から順序モデルへ昇格できる（two-way door。§6） |
| 展開の主 | **メンバー各自のスケジュールで展開**（案Y）。バンドル自身はスケジュールを持たない → スケジュールの二重化が起きない |
| 位置づけ | バンドルは**完全にプレゼンテーション層のオーバーレイ**。メンバーは通常タスクのままで、F-104（終了予定）・F-110（残り時間）・F-114（進捗）等の読み取りはバンドルを知らなくてよい |
| 順序の担保 | ロック（強制）はしない。崩れたら警告するが、集合モデルなので対象は「中断」「合間に別タスク開始」の2つ。**「飛ばして実行」は判定しない**（詳細は §5-1） |
| 多重所属 | **1タスク＝最大1バンドルで確定**。`routines.bundle_id`（FK1本）で1ルーチンは最大1バンドルにしか属さない（→ 展開時に1タスク1バンドルが自動成立） |

### 運用ルール（前提。アプリでは強制せず運用で守る）

- **メンバールーチンの開始想定時刻は、バンドル順に昇順で付ける**。これで①展開時の並びが意図した流れになり、②scheduled_start_time に順序が潜在するので、後から順序モデルへ昇格するときに自動バックフィルできる（escape hatch を開けておく）
- **バンドルには同じ繰り返しのルーチンだけを入れる**（周期タイプ＋パラメータ＋有効期間まで一致）。これでメンバーが常に同じ日に揃って展開され、スケジュール差による「欠け」が起きない。ハード制約にしない理由: 登録時の検証は軽いが、メンバールーチンの繰り返し編集（F-303）で不変条件が壊れ、編集時の始末（ブロック／警告／外す）が恒常的に重い。利用者1人で運用の実効性が高く、軽量オーバーレイ路線も崩さないため運用で担保する（2026-07-22 決定）

### 却下した案

- **案X（バンドルがスケジュールを持ち一括展開）**: ②当日タスク（スケジュールなし）に適用できない／ルーチンとスケジュール概念が二重化し二重展開の裁定が要る
- **固めて動かす（F-113例外）／案P（連続sort_order）・案Q（描画時グルーピング再配置）**: 見せ方を「途切れ許容の"道"」（§3）にしたことで、メンバーを特別扱いせず通常タスクのまま扱えるようになり不要に
- **順序モデル（bundle_members join＋bundle_position）**: 順序を app で担保しない集合モデルに倒したため不要に。後から足し算マイグレーションで昇格できる（§6）

## 3. 見せ方（確定線: 左ガターの"道"）

- **左ガター（打刻アイコンの列）を、塗りのある縦線＝"道"で、縦に隣り合う同一バンドルのメンバー行をつなぐ**。純粋な描画オーバーレイ（bundle_id と隣接だけで引ける。順序は使わない）
- **途切れは許容**: セクションヘッダーをまたぐ／間に非メンバー行が入ると、そこで素直に途切れる（どちらも同じ原則）
- バンドルメンバーは**特別扱いしない**（F-113 で実行セクションへ普通に動く）
- **帰結**: 実行を別々の時間に進めるほどメンバーが散り、道は分断されて短くなる。立て続けにこなす"良い流れ"のときほど道が長く残る、とも言える
- 道は「同じバンドルの束ね」の表現であり、**方向・順番は示さない**（集合モデル）
- N-05 適合: 追加する装飾は左ガターの縦線1本に限定する

## 4. データモデル（確定線）

既存スキーマ（データモデル定義書 §3）への追加。**既存の並び・採番・読み取りロジックは無改修**（バンドルはオーバーレイのため）。join テーブルは持たず、bundles マスタ＋ FK 2本で表す。

### 新規テーブル

**bundles（バンドル定義＝マスタ）**

| カラム | 型 | 制約 | 説明 |
|---|---|---|---|
| id | serial | PK | |
| name | text | NOT NULL | 例: 朝の立上げ。50文字以内（アプリ層で検証） |
| is_archived | boolean | NOT NULL DEFAULT false | マスタ流儀。参照0件なら物理削除可（F-405） |

### 既存テーブルへの追加

**routines に追加**（テンプレートのメンバーシップ）

| カラム | 型 | 制約 | 説明 |
|---|---|---|---|
| bundle_id | integer | FK → bundles, NULL可 | このルーチンが属するバンドル。1ルーチン=最大1バンドル |

**tasks に追加**（当日インスタンスのメンバーシップ）

| カラム | 型 | 制約 | 説明 |
|---|---|---|---|
| bundle_id | integer | FK → bundles, NULL可 | この日このタスクが属するバンドル。非バンドルは NULL |

### 展開ロジック（データモデル定義書 §4.1 への追記）

- ルーチン展開で生成するタスクの routine に bundle_id があれば、その値を生成タスクの bundle_id へ写す
- バンドル自身の展開判定は不要（メンバー各自のスケジュールで出る＝案Y）

### 中断（F-204）との接続

- 中断で作られる再開タスク T'（`split_parent_id = T`）は、**元タスク T の `bundle_id` も引き継ぐ**（データモデル定義書 §4.2 共通処理に追記）。引き継がないと、中断したメンバーがバンドルから抜けてバンドルが永遠に完了しなくなるため実質必須
- 完了判定は「全メンバータスクが完了」。中断で1メンバーが T と T' に分割されても両方が bundle_id を持つので、残り T' が完了した時点で自然にバンドル完了になる（集合モデルなのでメンバータスク数が増えるだけ）

### アドホック束ね（②）— 当面スコープ外

- 当日タスクを手で束ねる機能は**一旦落とす**（2026-07-22）。テンプレート版（①）を運用してから要否を判断する
- 復活は容易: `tasks.bundle_id` を手動セットする形（＋アドホック用の bundles 行）で足せる。**スキーマ変更は不要**なので two-way door

### 非ルーチンのタスクセット一括登録（③）— 検討メモ（未決・2026-07-30 起票）

- ルーチンにはならないが、追加するときは必ずセットで追加する一連のタスクを、バンドルとして保存しておき**手動で一括登録**したい（例: 荷物受け取り・荷物開封・段ボール処分。トリガはスケジュールでなく「荷物が届く」等の出来事）
- ①（ルーチン集合・スケジュール展開）とも②（既存の当日タスクを手で束ねる）とも異なる第3の形: **展開の主が「オーナーの明示操作」**になる
- 論点（未検分）:
  - **メンバー定義の置き場所**: ルーチンはスケジュール（開始想定時刻・繰り返し）を前提とするため、そのままでは持てない。少なくとも (a) スケジュールなしルーチン（手動展開専用）を許す / (b) バンドル側にテンプレート行（bundle_items 等の新テーブル）を持つ、の2案
  - **一括登録時の配置**: 挿入位置（カーソル位置か末尾か）・開始想定時刻の扱い
  - 登録後は `tasks.bundle_id` を付与するだけで既存設計に乗る見込み（道・警告・完了判定は無改修）
- ①の確定設計（案Y・オーバーレイ・集合モデル）は変えない。①を運用してから、②とあわせて要否・形を判断する

## 5. 検分ポイント（すべて確定）

運用ルール化により未決はなくなった。以下はすべて確定事項。

- **展開時の初期配置** = 各ルーチンの scheduled_start_time どおり（特別扱いなし）。運用ルール（時刻＝バンドル順）で並びを保つ。「散らばったタスクをバンドル指定することは運用上ない」「崩れ判定は時系列なので散っても前提は壊れない」ことから、これで足りると確認（2026-07-22）
- **警告（崩れ通知）**（2026-07-22 確定）:
  - **トリガー**: バンドルが進行中（1つ以上開始・全メンバー未完了）で、かつ**直前に実行したタスク（最新の打刻）がそのバンドルのメンバー**のとき、**非メンバーのタスクを開始した**ら鳴らす（＝メンバー→他タスクの遷移点でのみ）。一度離れると黙り、またメンバーを開始すると再武装される（**B案**。放置バンドルでの多重の鳴きを防ぐ）
  - **鳴らさないもの**: 明示的中断（§4.2-a）で止めただけ（他タスク未開始）／同じバンドルの別メンバーを開始／残り T' を再開
  - **出し方**: 非ブロッキングのトースト（情報のみ・1回）。事前確認（ブロック）は不採用（打刻速度 C-2/N-01 を守るため）
  - **判定**: 打刻の時系列・クライアント側の導出のみ。「崩れた」状態はカラムに持たない（設計原則）。道の途切れ（視覚）は警告トリガーにしない
  - **「飛ばして実行」は判定しない**（集合モデルのため）
- **「一部しか揃わない日」の見せ方** = **道を在るぶんだけ描く（明示なし）**（2026-07-22 確定）。運用ルール「同周期のルーチンで揃える」により (あ) スケジュール差の欠けは起きず、残る欠けは (い) 意図的スキップ（F-304）のみ。意図的なので明示の価値が薄く、道が短くなること自体がゆるい signal になる

### 順序モデルへの昇格（two-way door）

集合モデルで始めるが、運用して「順序を app で担保したい」となったら安く昇格できる。破壊を伴わない足し算のマイグレーション:

- `routines`（必要なら `tasks`）に `bundle_position`（NULL可）を足す
- 既存バンドルの position は **scheduled_start_time 昇順から自動バックフィル**（運用ルールを守っていれば順序が潜在しているため）
- 警告に「飛ばして実行」の判定を足す。道の描画・展開・読み取りは無変更

この昇格可能性を保つため、集合モデルでも運用ルール（メンバーの時刻＝バンドル順）は維持する。
