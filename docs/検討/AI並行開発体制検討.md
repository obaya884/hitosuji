## 1. 動機と現状

現状は単一ワークツリー・単一セッションで作業しており、別タスクが並行すると変更が交錯する（実際に、別セッション進行中の WIP を中断・除外して作業する事態が起きた＝T-06 起票の動機）。`git worktree` でタスクごとに独立したワークツリー／ブランチを持たせ、AI が複数タスクを並行実行できるようにしたい。

## 2. 結論と難所

**体制は「ヘッド1＋ワーカーN」の2階層とし、統合は PR＋既存 CI（T-01）に乗せる**。worktree を切ること自体は `git worktree add` だけで済み、難所ではない。本質的な難所は次の2点で、**この2点の設計が本検討の主題**。

### 難所1: 共有リソースの分離

worktree はファイルを分けるが、**DB（開発 :5432／テスト db-test :5433）・Drizzle マイグレーションのジャーナル・共有 docs（技術改善バックログ・ユーザーフィードバック・log_\*）は分かれない**。統合テストは全テーブル TRUNCATE でリセットする設計（`test-db.ts` の `truncateAll`）のため、複数 worktree が同じ db-test を同時に叩くと互いのデータを消し合う。

### 難所2: 通信と調停の設計

ヘッド↔ワーカー・ワーカー間のやり取りをどう処理するか。機構の選択肢は (a) サブエージェント（Agent ツール）と (b) Claude Code の Agent Teams（実験的機能）の2つ。あわせて、コンフリクト調停・マージ順序・「本番反映はオーナーの合図」規律の維持を体制に織り込む必要がある。

## 3. 体制の全体像（ヘッド1＋ワーカーN）

```
オーナー ←対話→ ヘッドセッション（main 常駐・リポジトリ本体）
                    │ タスク分配・worktree/ブランチ作成・マージ順序調停・共有 docs 記入
                    ├─ worktree A（../hitosuji-wt/<task>）← ワーカー A
                    ├─ worktree B                         ← ワーカー B
                    └─ …
各ワーカー → feature ブランチへ push → PR → CI（T-01: lint/build/test）→ ヘッドが順序調停 → オーナー合図でマージ
```

- **ヘッド**: リポジトリ本体（main）に常駐する1セッション。タスク分割と影響範囲の見積り（`Explore` 委譲）、worktree／ブランチの作成・破棄、マージキューの管理、レビュー結果の集約、共有 docs への記入の一元化を担う。**コードは編集しない**
- **ワーカー**: worktree ごとに1つ。worktree の内側では現行 CLAUDE.md の運用をそのまま実行する（Explore/Plan → 実装 → verifier・code-quality-reviewer → spec-reviewer・test-reviewer）。worktree 内の景色は現在の単独セッションと同じ
- **挙動レベルの仕様判断は従来どおりオーナーとの対話でのみ決める**。ワーカーが仕様判断に突き当たったら手を止め、ヘッド経由でオーナーに上げる（docs 先行の最重要ルールは不変）
- 1タスク＝1 worktree＝1ブランチ＝1PR。ブランチ名はタスクID起点（例 `t-xx-...`）で worktree ディレクトリ名と一致させる

## 4. 共有リソースの分離（難所1）

### 4.1 テストDB — 段階導入（Phase 1 は CI に委ねる）

- **unit テストは DB 不要**なので並行しても無干渉
- 統合テストの衝突源は db-test（:5433 の `hitosuji_test`）の共有。ただし `TEST_DATABASE_URL` は既に環境変数で差し替え可能（`src/infrastructure/db/testing/test-db.ts`）で、globalSetup も向き先へマイグレーションを当てるだけ。**同一 db-test コンテナ内に worktree ごとの DB（`hitosuji_test_<task>` 等）を作り、worktree ごとに `TEST_DATABASE_URL` を変えるだけで分離が成立**する（コンテナ追加・ポート追加不要、tmpfs のまま）
- **Phase 1（整備ゼロ）**: ワーカーのローカル検証は lint・build・`test:unit` まで。統合テストは PR の CI（T-01。独立した Postgres サービスコンテナで走る）に委ねる
- **Phase 2（並行度が上がったら）**: worktree セットアップスクリプトが `CREATE DATABASE` と `TEST_DATABASE_URL` 注入を行い、worktree 内でも `test:int` を完走可能にする

### 4.2 開発DB・dev サーバ

実機の動作確認はヘッド側（本体ワークツリー）でブランチを checkout して行う運用にすれば、開発 DB（:5432）もポート 3000 も分離不要。並行 dev が本当に必要になったら PORT と DB 名の割当を Phase 2 に含める。

### 4.3 スキーマ変更（Drizzle マイグレーション）は並行不可

マイグレーションはジャーナル＋連番で管理され、複数ブランチで生成すると必ず衝突する。**「スキーマ変更を含むタスクは常に最大1本、かつマージキューの先頭付近に置く」を規約**にする。

### 4.4 共有 docs はヘッドが一元記入

`docs/案件/技術改善バックログ.md`・`docs/案件/ユーザーフィードバック.md`・各 `log_*.md` は最大の衝突源（T-06 起票の動機となった交錯もこれ）。**記入はヘッドに一元化**し、ワーカーが触ってよい docs は自タスクの仕様として事前に確定した範囲のみとする。

## 5. 通信と調停の設計（難所2）

### 5.1 機構の比較 — サブエージェント vs Agent Teams

公式ドキュメント（code.claude.com/docs の agent-teams / sub-agents）調査の要点:

| 観点 | サブエージェント（Agent ツール） | Agent Teams |
|---|---|---|
| ステータス | 安定・全プラットフォーム | **実験的**（要環境変数）・**CLI のみ**（web/リモートセッション不可） |
| 通信 | ヘッドへの報告のみ。**SendMessage で完了後も往復継続が可能** | リード↔メイト＋メイト同士の直接通信、共有タスクリスト（依存関係・self-claim） |
| worktree | **isolation: worktree が組み込み** | 組み込みなし（作業ディレクトリはリードと同じ。指示で誘導） |
| 入れ子エージェント | **可能（5階層まで）**＝ワーカーが自分の verifier 等を起動できる | in-process メイトは**バックグラウンドのサブエージェント起動不可**（split pane なら可、ただし tmux 必須） |
| オーナーへの質問 | AskUserQuestion 不可 → ヘッド経由で中継 | 同様（permission プロンプトもリードに集約） |
| 既知の問題 | — | `/resume` でメイトが復元されない、タスク状態のラグ、1セッション1チーム |
| コスト | 低〜中 | 高（メイト数に比例） |

### 5.2 選定 — サブエージェント方式を採る（Agent Teams は再検討条件付きで見送り）

**Phase 1〜2 は「バックグラウンド・サブエージェント（worktree 分離）＋ SendMessage 継続」**とする。機能の優劣ではなく、本体制がそもそも「濃い通信」を必要としない設計であることが理由。

1. **通信は細く設計してある**: 影響ファイルが重なるタスクは最初から並行させず（予防が主・調停が従）、統合は PR＋CI という成果物を媒介にする。ワーカー間のやり取りは設計上ほぼゼロが正常で、Agent Teams の差別化点（メイト間直接通信・self-claim）は並行度2〜3では出番がない。**ワーカー同士が直接調整を始めたら「タスク分割が間違っていた」シグナル**として扱い、統合か直列化に倒す
2. **必要な能力はサブエージェントで揃う**: worktree 分離は組み込み、入れ子起動でワーカーが自分の worktree 内で verifier / code-quality-reviewer を回せる（「worktree 内は現行 CLAUDE.md のまま」が成立）。SendMessage 継続で「仕様質問 → オーナー確認 → 回答して続行」の往復もできる。一方 Agent Teams は in-process メイトがバックグラウンド起動できず、CLAUDE.md の「verifier と code-quality-reviewer を並列バックグラウンド起動」と正面衝突する（回避には tmux が必要）
3. **実験的機能への依存は運用に合わない**: CLI 限定のためリモートセッションと併用できず、`/resume` でメイトが消える問題は docs 主導・長時間タスクの運用と相性が悪い

**Agent Teams の再検討条件**（いずれかが揃ったら）: 並行度が常時4以上になり共有タスクリストの自律分配が欲しい／ワーカーが数時間単位で常駐しアイドル通知・随時割り込みが要る／機能が experimental を外れ `/resume` 問題が解消し worktree 連携が公式サポートされる。

### 5.3 通信プロトコル — 定型の成果物を基本、メッセージは例外処理に限定

- **ヘッド → ワーカー（起票時）**: 起動プロンプトで「タスクカード」を渡す。内容＝タスクID／ブランチ名／確定済み仕様の参照（docs の該当節）／触ってよいファイル範囲・触ってはいけない共有 docs／完了条件（lint・build・unit 緑＋push＋報告書式）。ワーカーはヘッドの会話文脈を持たないため、**仕様はすべて docs 参照で自己完結させる**（「仕様は docs が正」の強制にもなる）
- **ワーカー → ヘッド（3種類に限定）**:
  1. **完了報告**（定型）: ブランチ名・変更ファイル一覧・検証結果・仕様上の注意点。ヘッドはこれを受けて PR 作成 → CI 確認 → マージキューへ
  2. **仕様質問**（ブロッカー）: 手を止めてターンを終え質問を返す。ヘッドがオーナーに確認 → 必要なら docs を先に直す → SendMessage で回答を返して続行
  3. **中断報告**: 影響範囲が事前見積りを超えた場合。ヘッドがタスクの分割・直列化を再判断
- **ワーカー ↔ ワーカー**: 直接通信は設けない。タスク間の接点は必ずヘッド経由（実体はマージキューでの rebase 調停）

### 5.4 マージ順序の調停

ヘッドがマージキューを持つ。1本マージ → 残ブランチを rebase → CI 再走 → 次、の逐次処理（並行度2〜3ならこれで十分。自動化しない）。**main への push（＝本番デプロイ）・PR マージは従来どおりオーナーの合図が前提**で、ヘッドにも自動マージ権を与えない（T-01 の「検証のみ・手動マージ」方針を継承）。ワーカーが push できるのは feature ブランチのみ。

## 6. 既存ルールとの差分（採用時に CLAUDE.md を先に改訂する点）

1. **「コードの編集は常にメインセッションが行う」** → worktree 前提に改訂（ヘッドは編集しない／ワーカーは自分の worktree 内で編集する）
2. **オーナーのレビュー導線**: サブエージェントの編集はヘッドのチャットに差分表示されないため、「Edit ツールの差分をチャットでレビュー」に代わり **PR の diff がレビューの正**になる。動作確認はヘッド側 worktree でブランチを checkout して現行どおり
3. **実装完了後のフロー**（レビュー → 動作確認 → push 待ち）は PR 単位に読み替え
4. アーキテクチャ定義書は改訂不要の見込み（コード配置・依存方向・テスト戦略は変わらない）

## 7. 導入ステップと見送る事項

| 段階 | 内容 | 前提整備 |
|---|---|---|
| Phase 1 | worktree 運用手順の文書化＋運用開始（並行度2、ワーカーはローカル unit まで・int は CI 任せ） | ほぼゼロ（CLAUDE.md 改訂と手順書のみ） |
| Phase 2 | `scripts/wt-new.sh` / `wt-rm.sh`（worktree＋ブランチ作成、`npm ci`、テストDB作成、`TEST_DATABASE_URL` 注入、後片付け） | スクリプト2本＋permissions 追記 |
| Phase 3 | ヘッド運用の型化（分配・キュー・レビュー集約の定型をスキル化するか判断）。Agent Teams の再検討（§5.2 の条件） | Phase 1–2 の運用実績を見てから |

**見送る事項**: ヘッドからのワーカー自動 spawn（tmux 等の凝った仕組み。シングルオーナー・並行度2〜3ではオーナーがセッションを開くだけで足りる）／自動マージ・ブランチ保護（T-01 で見送った方針を維持）／worktree ごとの docker compose 複製（同一インスタンス内の DB 分離で足りる）。いずれも過剰抽象回避（アーキテクチャ定義書 §1）と同じ判断軸。
