## 1. 判定の物差し

### 1.1 削る対象の分類（各表の「分類」列）

| 番号 | 分類 | 典型 |
|---|---|---|
| 1 | 実装のコピー | 期待値をテスト内で実装と同じ式から再計算している。実装が間違っていても同じ間違いをする |
| 2 | 偽物・ヘルパーの自己検証 | インメモリリポジトリの patch の性質や、テスト補助関数そのものを検証している |
| 3 | 型・ライブラリ・定数の再確認 | TypeScript の型・React・Drizzle・Postgres の保証、定数の値の再掲、「そういう分岐は書いていない」ことの主張 |
| 4 | 他テストとの重複 | 同じ分岐を別段（domain ⇔ usecases ⇔ component ⇔ int）・別ファイル・同ファイルで二重に守っている |
| 5 | 内部実装への過度な依存 | クラス名・DOM 構造・呼び出しの不在など、リファクタで壊れるが挙動は変わらない主張 |
| 6 | 過剰なケース分け | 同一分岐を通る入力違いの複数ケース、境界でない値の羅列 |

### 1.2 確信度

- **高**: 実装を読んで分岐が存在しない・別テストが同じ主張を持つことを確認済み。機械的に削ってよい
- **中**: 守っている退行は存在するが実害が薄い、または統合で同じ保証が残せる。着手時にオーナー裁定で決める

### 1.3 全体を貫く 4 つのパターン

1. **domain 純関数の分岐を上位段で再列挙**（最多）。usecases・コンポーネント・盤面が、選択規則・並び順・打刻編集の判定・キーボード除外規則を入力違いにもう一度通している。上位段に要るのは「配線している」1 件だけ
2. **マスタ 3 画面が共通部品の配線を 3 回ずつ検証**。Esc・保存中の抑止・新規行の閉じ/取消/失敗は共通コンポーネント側のテストが実体を持つ
3. **統合段が Postgres・Drizzle の既定動作を確認**。FK の `references()`、UPDATE が他列を触らない、unique index の NULL 扱い、`defaultNow()` で何をしても緑になる `updated_at`。「基本形」と「付帯更新つき」の対でトランザクションを二重に張っているものが 4 組
4. **「そういう分岐は書いていない」ことの主張**。無関係な prop や状態を変えても結果が同じ、という型のテストが各段に散在する

### 5.0 実施記録（2026-09-17・ブランチ `t-150-usecases`）

**63ケース削除（usecases 287 → 224、proxy も4ケース減）・604行減。本番コードは無変更**。節の見立て（domain の再演／偽物の性質／`not_found` の二重）はおおむね当たっていた——的中率は §8〜§10 より高く、domain・統合段に近い。

### 11.2 監査の的中率は段が上がるほど落ちる

監査は全文を**静的に読んで**「同じ主張が他にもある」を重複と判定した。実測すると、その判定は段が上がるほど外れる。

| 段 | 高確信の的中 |
|---|---|
| domain・統合段・usecases | ほぼ的中（それでも §5 は2件を削除後に復帰させた） |
| §8 daily-board | 約45% |
| §10 の最大項目（マスタ3画面） | **0%（全件却下）** |

原因は1つに揃っている——**「子の段が同じ主張を持つ」ことは「親が子を配線している」ことを何も言わない**。子コンポーネントのテストを壊す変異では親のテストは落ちず、親が渡す値を変える変異では親のテストだけが落ちる。上位段は唯一の網であって重複ではない。振り分けの物差しは §8.1 が正。
