## 1. 本書の位置づけ

要求定義書の要求（F-XXX / N-XX）を、実装可能な要件（機能要件・方式・画面・データ）に落とし込む。画面の詳細仕様は画面定義書に、データ構造はデータモデル定義書に分割し、本書は全体方針・要件一覧・トレーサビリティを担う。

## 2. システム方式

### 2.1 全体構成

```
[ブラウザ (私用PC / 業務PC)]
        │ HTTPS + Basic認証
        ▼
[Webアプリ: Next.js (App Router, TypeScript)]  ← Vercel (無料枠) にデプロイ
        │ SQL (Drizzle ORM)
        ▼
[DB: Neon (マネージドPostgreSQL, 無料枠)]
```

### 2.2 技術スタック選定

| レイヤ | 採用 | 選定理由（対応する非機能要求） |
|---|---|---|
| フレームワーク | Next.js (App Router) + TypeScript | フロント/APIを1リポジトリで完結でき個人開発の維持コストが低い（§9 制約）。情報量が多くAI支援と相性が良い |
| UI | React + Tailwind CSS | 装飾を排したシンプルなリストUI（N-05）を最小工数で構築。コンポーネントライブラリは原則使わない |
| データ取得/更新 | Server Actions + SWR（楽観的更新） | 打刻・追加操作の体感即応（N-01）。操作は即UIに反映し、裏で永続化する |
| ORM | Drizzle ORM | 標準SQLに近くロックインが薄い（N-06②）。マイグレーションをコードで管理 |
| DB | Neon (PostgreSQL) | 無料枠で十分（N-07）。`pg_dump` による標準形式バックアップ（N-06①）。素のPostgresなので他DBaaS/自宅サーバへ移行可能（N-06②） |
| ホスティング | Vercel 無料枠 | Next.jsと親和性が高くデプロイが自動化される（N-02, N-07） |
| 認証 | Basic認証（`src/proxy.ts` で実装、資格情報は環境変数） | シングルユーザーの簡易認証で十分（N-03）。ログイン画面の実装が不要 |

**コールドスタート**: Vercel関数とNeonのスケールトゥゼロにより初回アクセスに遅延が出る。2026-07-19 の実測は初回 1.4秒 / ウォーム 0.2〜0.4秒で、**許容できる水準と判断した**（N-01 は高頻度操作の即応が本質）。実運用で不快になれば、①Neonのautosuspend時間延長、②cron ping、③別構成への移行、の順で対処する。

### 2.2.1 コード構成・テスト戦略

レイヤー構成（クリーンアーキテクチャ）・関数型DDDの規約・テスト戦略（古典学派・テストピラミッド）は[アーキテクチャ定義書](./アーキテクチャ定義書.md)が正。

### 2.3 リポジトリ・環境

- 単一リポジトリ `hitosuji`（本ディレクトリ）。Gitで管理し、mainブランチへのpushでVercelに自動デプロイ
- 環境は production のみ（個人利用のため staging は設けない。ローカル開発環境で代替）
- DBマイグレーションは Drizzle Kit で管理し、適用はデプロイ前に手動実行
- **本番とローカルはファビコンで見分けられるようにする**（同じ画面を2つのタブで開くため）
- **ローカルDBには本番のマスタ・ルーチンだけを流し込める**ようにする（タスク（ログ）は持ち込まない）。手段はバックアップ（N-06）のダンプの部分リストア

## 5. 機能要件

要求ID単位の実現方針。UI詳細は画面定義書、データ仕様はデータモデル定義書を参照。

### 5.1 デイリータスクリスト（S-01）

| 要求ID | 要件 |
|---|---|
| F-101 | タスクは日付（`task_date`）に属し、日内の表示順（`sort_order`）を持つ。リストはセクション順 → sort_order 順で表示する |
| F-102 | タスク追加は画面トップの**常設クイック追加欄**から（タスク名のみを入力して Enter。欄はクリアされ連続追加できる。配置先などの詳細は S-01 §3.4）。編集はインライン、並び替えはドラッグ＆ドロップおよびショートカット、削除（打刻済みは確認あり）を提供する |
| F-103 | 見積もり時間は分単位の整数。入力UIは分直接入力（例: `25`）を基本とする。追加時は未設定（0分）で作成でき、未設定タスクは終了予定時刻に含まれないことをリスト上で視覚表示する（S-01 §3.3） |
| F-104 | 終了予定時刻 = 現在時刻 + 実行中タスクの残り見積もり + 未実行タスクの見積もり合計。クライアントで毎分および操作の都度再計算し、画面上部に常時表示する。24:00超過時は翌日表記（例: 25:30）とし警告色にする |
| F-105 | タスクは1つのセクションに属する（未指定も可）。セクションはリストのグループ見出しとして表示する |
| F-110 | セクション見出しに「配置タスクの見積もり合計 / セクション枠の長さ」と過不足（超過分は警告色）を表示する |
| F-106 | 日付ナビゲーション（前日/翌日/今日/日付指定）で任意の日付のリストを表示・編集できる。過去日は実績の修正、未来日はプランの仕込みが目的 |
| F-107 | 未実行タスクを翌日（または指定日）へ移動できる。`task_date` の付け替えで実現し、ログは発生しない。先送り時に `postponed_count` をインクリメントして記録し、先送り数集計（F-502）に備える |
| F-108 | （未実装）タスク名入力時に過去のタスク名をインクリメンタル補完し、選択時に直近実績の見積もり・モード・プロジェクト・セクションを引き継ぐ |
| F-109 | （未実装）カレンダー俯瞰表示。着手時に詳細化 |
| F-112 | （未実装）モード/プロジェクト/セクションの選択ポップオーバーを矢印キー＋Enter で操作できるようにする。現状は M/P/S でポップオーバーを開き、候補はクリックで選ぶ |
| F-113 | **当日のタスクの自動セクション移動**。リストは上から「実行済みのログ → 実行中 → これからの予定」の順に保たれる（C-7）。開始したタスクは開始時刻を含むセクションへ移り、やり残した未実行タスクは「現在位置」の直後へ繰り下がる。**開始時刻を後から修正したとき（F-203）も、修正後の時刻を含むセクションへ移す**（実行中・完了のいずれでも）。発火は打刻時・打刻の修正時・デイリー表示時で、対象は表示日が今日のときのみ。詳細は画面定義書01 §4.2、採番はデータモデル定義書 §4.4 |
| F-114 | **タスク消化の進捗を表示する**。実施済み（完了）件数／全件数と、その比率のプログレスバー。件数ベースで数える（見積もり時間の消化は F-110 が担う）。表示箇所はセクション見出しと画面上部のサマリ行の2か所。詳細は画面定義書01 §3.1・§3.2 |
| F-115 | 削除したタスクは直後に取り消せる。未実行タスクは確認なしで削除し取り消し手段（トースト内のボタン／`U` キー）を出す、打刻済みタスクは削除前に確認する。ルーチン由来タスクの削除はスキップ記録を伴い、取り消すとスキップも解除される（F-304）。詳細は画面定義書01 O-8 |
| F-111 | 選択タスク（状態不問）を複製し、未実行タスクとして**未実施のトップ**に挿入する。挿入位置・引き継ぐ属性は画面定義書01 O-11 が正。`routine_id` は展開の冪等制約 `uq_tasks_routine_date` に抵触するため必ず NULL、`postponed_count` は 0 とする |

### 5.2 実行・ログ（S-01）

| 要求ID | 要件 |
|---|---|
| F-201 | 各タスク行の開始/終了ボタンまたはショートカット1操作で `started_at` / `ended_at` に現在時刻を打刻する。実行中にできるタスクは同時に1つ。実行中タスク A がある状態で別タスク B を開始した場合は**割り込み**として扱い、①A を現在時刻で終了 ②A の再開タスク（残り見積もり。F-204 と同じ生成規則）を **B の直下**に自動生成 ③B を開始状態にする、を1操作・1トランザクションで行う |
| F-202 | 完了タスクは「実績時間（ended - started）」と見積もりを並記し、超過分を警告色で表示する |
| F-203 | 開始・終了時刻はインライン編集で `HH:MM` を直接修正できる。整合性チェック（開始 ≦ 終了）を行う |
| F-204 | 中断操作: 実行中タスクを現在時刻で終了し、同名・同属性の新タスクを直後の位置に自動生成する。新タスクの見積もり = max(元見積もり − 実績, 1分)。生成タスクは `split_parent_id` で元タスクに紐づける |
| F-205 | 実行中タスクの経過時間を1秒〜1分粒度でリアルタイム表示する（クライアントタイマー。サーバ通信はしない） |
| F-206 | （未実装）タスクごとに1行コメントを付与できる |
| F-207 | （未実装）タスクごとの長文ノート。着手時に詳細化 |
| F-208 | （未実装）完了済みタスクで Enter を押したときに「複製して開始」をまとめて行う。現状は完了タスクへの打刻操作を無効とし、Y（複製）→ Enter（開始）の2操作で代替する |
| F-209 | 表示日より前の日付に実行中（`started_at` あり・`ended_at` なし）のタスクが残っている場合、当日リストの上部に警告バナーを出し、該当日へのリンクを置く。詳細は画面定義書01 §8 |

### 5.3 ルーチン（S-02）

| 要求ID | 要件 |
|---|---|
| F-301 | 繰り返しルール: 毎日 / 週次（曜日複数指定）/ 月次（日指定）/ n日ごと。展開はデイリーリストの**表示のたび**にサーバ側で実行し（対象は**当日以降の日付のみ**。過去日は展開しない）、未展開のルーチンのみタスク生成する。`(routine_id, task_date)` のユニーク制約で冪等にする（データモデル定義書 §4.1） |
| F-302 | ルーチンは名前・見積もり・**開始想定時刻**・モード・プロジェクトを持つ。展開時は開始想定時刻の昇順にタスクを生成し、開始想定時刻を含むセクションへ配置する（**セクション・並び順はルーチンのデータとして持たず導出**）。開始想定時刻は並び決め用であり、実行を固定する予約時刻ではない |
| F-303 | 一覧での確認・編集・有効/無効トグル・削除ができる。無効化したルーチンは以後展開されない（既存タスクには影響しない） |
| F-304 | **特定日スキップ**: 展開されたタスクを削除したとき、その (routine_id, task_date) をスキップとして記録し、以後その日は再展開しない（データモデル定義書 §3.6・§4.1）。削除を取り消すとスキップも解除される。ルーチン本体・他の日の展開には影響しない。**個別変更（その日だけ見積もりや時刻を変える）は未実装**（展開済みタスクを直接編集すれば足りるため、専用機能の要否は運用で見極める） |
| F-305 | ログからのルーチン化。S-01 の行メニューから、選択タスクの属性を引き継いだルーチンを作る。入力させるのは繰り返し種別と開始想定時刻のみ。詳細は画面定義書01 §4.1 |
| F-306 | ルーチン一覧を列見出しのクリックで並べ替えられる。並べ替えはクライアント側で行う（一覧は全件保持しており再取得は不要）。対象の軸・既定値・第2キーなどの詳細は画面定義書02 §3.1 |

**展開済みタスクとルーチンの関係**: ルーチン編集は未来の展開分にのみ反映される。展開済みタスクは独立したレコードであり遡って変化しない（ログの不変性を優先）。

## 6. 非機能要件の実現方式

| ID | 実現方式 |
|---|---|
| N-01 | 楽観的更新（操作は即UI反映→非同期永続化）。打刻・追加・並び替えは体感 0ms を目標、サーバ確定失敗時はトースト表示とロールバック。1日分のデータのみ取得しペイロードを最小化。**適用範囲は S-01 の高頻度操作**（打刻・追加・編集・並び替え）とし、低頻度の S-02 ルーチン管理・S-03 マスタ管理は対象外（保存完了を待って反映。画面定義書02 §1 / 画面定義書03 §1）。S-01 でも中断・複製・先送りは生成タスクの採番をサーバが決めるため対象外（画面定義書01 §4） |

| N-03 | `src/proxy.ts` で全リクエストに Basic認証を要求。資格情報は環境変数（Vercel の環境変数機能）で管理。HTTPS は Vercel 標準 |
| N-04 | S-01 の全主要操作にショートカットを割当（画面定義書01 §6 が正）。共通規約は画面定義書00 §3 |
| N-05 | 装飾のないテーブル型リスト。モーダルは最小限とし、インライン編集を基本とする |
| N-06 | Neon（素のPostgres）+ Drizzle（標準SQL）でロックイン回避。バックアップは `pg_dump` を使い、手順は README を正とする。取得は当面手動（週次目安）とし、自動化（GitHub Actions cron）は運用の負担を見てから判断する |
| N-07 | Vercel Hobby（無料）+ Neon Free（無料）で運用費 0円/月。独自ドメインは任意 |
| N-08 | `tasks(task_date)` インデックスにより日付単位取得はログ総量に依存しない。タスク名の検索インデックスは補完（F-108）の導入時に追加する。**実効性の確認はログが蓄積してから行う（未実施）** |
| N-09 | （未実装）レスポンシブ崩れ防止のみ対応 |
| N-11 | 操作の結果はトーストで通知する（取り消し可能な操作には取り消しボタンを添える）。モーダルで操作の流れを止めない。表示時間・閉じ方は画面定義書00 §2.2 |
