## 1. 本書の位置づけ

要求定義書の要求（F-XXX / N-XX）を、実装可能な要件（機能要件・方式・画面・データ）に落とし込む。画面の詳細仕様は画面定義書に、データ構造はデータモデル定義書に分割し、本書は全体方針・要件一覧・トレーサビリティを担う。

## 2. システム方式

### 2.1 全体構成

```
[ブラウザ (私用PC / 業務PC)]
        │ HTTPS + Basic認証
        ▼
[Webアプリ: Next.js (App Router, TypeScript)]  ← Vercel (無料枠) にデプロイ
        │ SQL (Drizzle ORM)
        ▼
[DB: Neon (マネージドPostgreSQL, 無料枠)]
```

### 2.2 技術スタック選定

| レイヤ | 採用 | 選定理由（対応する非機能要求） |
|---|---|---|
| フレームワーク | Next.js (App Router) + TypeScript | フロント/APIを1リポジトリで完結でき個人開発の維持コストが低い（§9 制約）。情報量が多くAI支援と相性が良い |
| UI | React + Tailwind CSS | 装飾を排したシンプルなリストUI（N-05）を最小工数で構築。コンポーネントライブラリは原則使わない |
| データ取得/更新 | Server Actions + SWR（楽観的更新） | 打刻・追加操作の体感即応（N-01）。操作は即UIに反映し、裏で永続化する |
| ORM | Drizzle ORM | 標準SQLに近くロックインが薄い（N-06②）。マイグレーションをコードで管理 |
| DB | Neon (PostgreSQL) | 無料枠で十分（N-07）。`pg_dump` による標準形式バックアップ（N-06①）。素のPostgresなので他DBaaS/自宅サーバへ移行可能（N-06②） |
| ホスティング | Vercel 無料枠 | Next.jsと親和性が高くデプロイが自動化される（N-02, N-07） |
| 認証 | Basic認証（Next.js middleware で実装、資格情報は環境変数） | シングルユーザーの簡易認証で十分（N-03）。ログイン画面の実装が不要 |

**留意点（コールドスタート）**: Vercel関数とNeonのスケールトゥゼロにより、朝一番のアクセスで1〜2秒程度の初回遅延が発生しうる。N-01は「高頻度操作の即応」が本質であり、初回1回の遅延は許容とする。実測して不快であれば、①Neonのautosuspend時間延長、②cron ping、③Cloudflare Workers + D1構成への移行、の順で対処する。

### 2.2.1 コード構成・テスト戦略

レイヤー構成（クリーンアーキテクチャ）・関数型DDDの規約・テスト戦略（古典学派・テストピラミッド）は[アーキテクチャ定義書](./アーキテクチャ定義書.md)が正。

### 2.3 リポジトリ・環境

- 単一リポジトリ `hitosuji`（本ディレクトリ）。Gitで管理し、mainブランチへのpushでVercelに自動デプロイ
- 環境は production のみ（個人利用のため staging は設けない。ローカル開発環境で代替）
- DBマイグレーションは Drizzle Kit で管理し、適用はデプロイ前に手動実行
- **本番とローカルはファビコンで見分けられるようにする**（2026-07-20 / FB-17。同じ画面を2つのタブで開くため、タブだけでどちらを触っているか分かる必要がある。判定は `VERCEL_ENV`）
- **ローカルDBには本番のマスタ・ルーチンだけを流し込める**ようにする（2026-07-20 / FB-18。タスク（ログ）は持ち込まない — ルーチン展開で生成されるうえ、実データを開発中に増やす必要がないため）。手段はバックアップ（N-06）のダンプの部分リストア

## 5. 機能要件

要求ID単位の実現方針。UI詳細は画面定義書、データ仕様はデータモデル定義書を参照。

### 5.1 デイリータスクリスト（S-01）

| 要求ID | 要件 |
|---|---|
| F-101 | タスクは日付（`task_date`）に属し、日内の表示順（`sort_order`）を持つ。リストはセクション順 → sort_order 順で表示する |
| F-102 | タスク追加は画面トップの**常設クイック追加欄**から（タスク名のみを入力して Enter。欄はクリアされ連続追加できる。配置先などの詳細は S-01 §3.4）。編集はインライン、並び替えはドラッグ＆ドロップおよびショートカット、削除（打刻済みは確認あり）を提供する |
| F-103 | 見積もり時間は分単位の整数。入力UIは分直接入力（例: `25`）を基本とする。追加時は未設定（0分）で作成でき、未設定タスクは終了予定時刻に含まれないことをリスト上で視覚表示する（S-01 §3.3） |
| F-104 | 終了予定時刻 = 現在時刻 + 実行中タスクの残り見積もり + 未実行タスクの見積もり合計。クライアントで毎分および操作の都度再計算し、画面上部に常時表示する。24:00超過時は翌日表記（例: 25:30）とし警告色にする |
| F-105 | タスクは1つのセクションに属する（未指定も可）。セクションはリストのグループ見出しとして表示する |
| F-110 | セクション見出しに「配置タスクの見積もり合計 / セクション枠の長さ」と過不足（超過分は警告色）を表示する |
| F-106 | 日付ナビゲーション（前日/翌日/今日/日付指定）で任意の日付のリストを表示・編集できる。過去日は実績の修正、未来日はプランの仕込みが目的 |
| F-107 | 未実行タスクを翌日（または指定日）へ移動できる。`task_date` の付け替えで実現し、ログは発生しない。先送り時に `postponed_count` をインクリメントして記録し、Phase 2 の先送り数集計（F-502）に備える（MVPでは表示しない） |
| F-108 | (Phase 3) タスク名入力時に過去のタスク名をインクリメンタル補完し、選択時に直近実績の見積もり・モード・プロジェクト・セクションを引き継ぐ |
| F-109 | (Phase 3) カレンダー俯瞰表示。Phase 3 着手時に詳細化 |
| F-114 | (Phase 2) **タスク消化の進捗を表示する**。実施済み（完了）件数／全件数と、その比率のプログレスバー。件数ベースで数える（見積もり時間の消化は F-110 が担う）。表示箇所は (a) セクション見出し（未分類グループにも表示。詳細は画面定義書01 §3.2。2026-07-20 確定。FB-06）と (b) 画面上部のサマリ行（表示日1日の全タスクが対象。詳細は画面定義書01 §3.1。2026-07-21 確定。FB-22） |
| F-113 | (Phase 2) **当日の未実行タスクの自動セクション移動**。対象は表示日が今日のときの (a)開始操作をしたタスク自身 と (b)未実行タスク（完了タスク・開始済みの実行中タスクは動かさない）。(a) タスクを開始したら、**そのタスクを**開始時刻を含むセクションの末尾へ移す（未分類からも移る。`started_at` の書き込みと同一トランザクション）。(b) 「現在位置」（実行中タスクの直後、なければ現在時刻を含むセクションの未実行の先頭）より前にある**セクション設定済みの**未実行タスクを、相対順序を保ったまま現在位置の直後へ繰り下げる。発火は打刻時とデイリー表示時。取り消しUIは設けず、手動の並び替えで戻せる。詳細は画面定義書01 §4.2 / データモデル定義書 §4.4（2026-07-20 確定） |
| F-112 | (Phase 3) モード/プロジェクト/セクションの選択ポップオーバーを矢印キー＋Enter で操作できるようにする。Phase 1 は M/P/S でポップオーバーを開き、候補はクリックで選ぶ |
| F-111 | 選択タスク（状態不問）を複製し、未実行タスクとして**未実施のトップ**に挿入する。挿入位置 = 実行中タスクがあればその直後、なければ表示順で最初の未実行タスクの直前、いずれもなければリスト末尾。名前・見積もり（満額）・モード・プロジェクトを引き継ぎ、`section_id` は挿入位置のセクションに従う（割り込み再開タスクと同じ規則）。`routine_id`・`split_parent_id`・コメントは引き継がない（routine_id の複製は展開の冪等制約 `uq_tasks_routine_date` に抵触するため必ず NULL）。`postponed_count` は 0 |

### 5.2 実行・ログ（S-01）

| 要求ID | 要件 |
|---|---|
| F-201 | 各タスク行の開始/終了ボタンまたはショートカット1操作で `started_at` / `ended_at` に現在時刻を打刻する。実行中にできるタスクは同時に1つ。実行中タスク A がある状態で別タスク B を開始した場合は**割り込み**として扱い、①A を現在時刻で終了 ②A の再開タスク（残り見積もり。F-204 と同じ生成規則）を **B の直下**に自動生成 ③B を開始状態にする、を1操作・1トランザクションで行う |
| F-202 | 完了タスクは「実績時間（ended - started）」と見積もりを並記し、超過分を警告色で表示する |
| F-203 | 開始・終了時刻はインライン編集で `HH:MM` を直接修正できる。整合性チェック（開始 ≦ 終了）を行う |
| F-204 | 中断操作: 実行中タスクを現在時刻で終了し、同名・同属性の新タスクを直後の位置に自動生成する。新タスクの見積もり = max(元見積もり − 実績, 1分)。生成タスクは `split_parent_id` で元タスクに紐づける |
| F-205 | 実行中タスクの経過時間を1秒〜1分粒度でリアルタイム表示する（クライアントタイマー。サーバ通信はしない） |
| F-206 | (Phase 3) タスクごとに1行コメントを付与できる |
| F-207 | (Phase 3) タスクごとの長文ノート。Phase 3 着手時に詳細化 |
| F-208 | (Phase 3) 完了済みタスクで Enter を押したときに「複製して開始」をまとめて行う。Phase 1 では完了タスクへの打刻操作は無効で、Y（複製）→ Enter（開始）の2操作で代替する |

### 5.3 ルーチン（S-02）

| 要求ID | 要件 |
|---|---|
| F-301 | 繰り返しルール: 毎日 / 週次（曜日複数指定）/ 月次（日指定）/ n日ごと。展開はデイリーリストの**表示のたび**にサーバ側で実行し（対象は**当日以降の日付のみ**。過去日は展開しない）、未展開のルーチンのみタスク生成する。`(routine_id, task_date)` のユニーク制約で冪等にする（データモデル定義書 §4.1） |
| F-302 | ルーチンは名前・見積もり・**開始想定時刻**・モード・プロジェクトを持つ。展開時は開始想定時刻の昇順にタスクを生成し、開始想定時刻を含むセクションへ配置する（**セクション・並び順はルーチンのデータとして持たず導出**）。開始想定時刻は並び決め用であり、実行を固定する予約時刻ではない |
| F-303 | 一覧での確認・編集・有効/無効トグル・削除ができる。無効化したルーチンは以後展開されない（既存タスクには影響しない） |
| F-304 | **特定日スキップは Phase 1 で実装する**。展開されたタスクを削除したとき、その (routine_id, task_date) をスキップとして記録し、以後その日は再展開しない（データモデル定義書 §3.6・§4.1）。削除を取り消すとスキップも解除される。ルーチン本体・他の日の展開には影響しない。**個別変更（その日だけ見積もりや時刻を変える）は Phase 3**（展開済みタスクを直接編集すれば足りるため、専用機能の要否は運用で見極める） |
| F-305 | (Phase 2) ログからのルーチン化。S-01 の行メニューから、選択タスクの名前・見積もり・モード・プロジェクトを引き継いだルーチンを作る。入力させるのは繰り返し種別と開始想定時刻のみ（既定: 毎日／元タスクの開始打刻時刻）。**開始日は翌日**（当日の二重展開を防ぐ）、見積もり0分のタスクは実績を見積もりに転用し、実績もなければ作成しない。ルーチン由来タスクからは作成できない。詳細は画面定義書01 §4.1（2026-07-20 確定） |
| F-306 | (Phase 2) 一覧の列見出しクリックで並べ替える（名前 / モード / プロジェクト / 繰り返し / 開始想定。見積は対象外）。同じ見出しの再クリックで降順。既定は開始想定の昇順で、**選んだ並び順は記憶しない**。第2キーは常に名前の自然順、モード・プロジェクト未設定の行は昇順・降順とも末尾。並べ替えはクライアント側で行う（一覧は全件保持しており再取得は不要）。詳細は画面定義書02 §3.1（2026-07-20 確定） |

**展開済みタスクとルーチンの関係**: ルーチン編集は未来の展開分にのみ反映される。展開済みタスクは独立したレコードであり遡って変化しない（ログの不変性を優先）。

## 6. 非機能要件の実現方式

| ID | 実現方式 |
