# ユーザーフィードバック管理簿

- 作成日: 2026-07-20
- 目的: 実運用で得たオーナーの気づきを一元管理し、今後の開発の入力にする
- 運用ルールをなぜそう定めたかは本書に書かず、[log_21_ユーザーフィードバック.md](./log_21_ユーザーフィードバック.md) へ日付順に積む（CLAUDE.md「書き方の規約」）

## 運用ルール

1. 気づきはまず本書に**起票**する（粒度はバラバラで良い。会話で出たものは AI が転記する）
2. 起票時に**分類**する: `不具合` / `改善（軽微）` / `改善（要仕様整理）` / `要求（優先度変更含む）` / `開発環境`。分類は[一覧](#一覧)のどの節に置くかで表す（列としては持たない）
3. **1エントリ ＝ 一覧の1行 ＋ [詳細](#詳細)の1節**。一覧は索引に徹し、`ID / 起票日 / タイトル / 詳細 / 状態` の5列だけを持つ
   - **タイトル**は内容を一文に要約する。体言止めにせず「〜が〜する」まで書き、読んで何の話か分かる粒度にする（目安40字前後）
   - **詳細**列には `[詳細](#fb-xx)` のリンクだけを置く。本文は[詳細](#詳細)の `### FB-XX` 節に書く（**見出しは ID のみ**。タイトルを重ねると改題のたびにアンカーが壊れ、一覧との二重管理にもなる）
   - **分類と状態を詳細節に書かない**。分類は節の位置、状態は一覧の状態列が正（二重に持つと必ず食い違う）
   - 詳細節の並び順は一覧と同じにする
4. 詳細節は**決まった項目を決まった順に**並べる。該当しない項目は省く（空欄で残さない）

   | 項目 | いつ書くか |
   |---|---|
   | 現象 | **必須**。何が起きるか・何が読み取れないかを書く |
   | 原因 | 実装上・文書上の所在が分かっているとき |
   | 対応方針 | 方針が既に定まっているとき（`改善（軽微）`は基本ここまでで閉じる） |
   | 詰める点 | オーナーと決める論点。`改善（要仕様整理）`は**必須**。①②③ で並べる |
   | 発見 | どの作業で気づいたか（後から経緯をたどるため） |
   | 関連 | 他の FB・T との関係や参照すべき文書。**一緒に処理すべきなら「一緒に決める」まで書く** |

5. 対応するときは通常の開発ルールに従う — **挙動レベルの変更は該当仕様書を先に更新**し（[guide_21_ユーザーフィードバック.md](./guide_21_ユーザーフィードバック.md)）、本書には対応結果と参照先だけを残す
6. 状態は `未対応` / `対応中` / `対応済み` / `見送り` の4つ。対応済み・見送りには日付と理由（または反映先）を書く
7. **対応済み・見送りになったエントリは、状態更新と同じコミットで[closed_21_ユーザーフィードバック.md](./closed_21_ユーザーフィードバック.md)へ移す**（本書には未対応・対応中だけを残す）。**一覧の行と詳細節はセットで移す** — `npm run ledger:move -- FB-XX` が両方を移す

## 詳細

### FB-68

- 現象: 未打刻タスク（`started_at` が NULL）で `B` または `F` を押すと、時刻入力欄が現れないまま**すべてのショートカットが無効になる**。`Esc` すら効かず、マウスで別のセルを開いて閉じるか再読み込みするまでキーボードが戻らない
- 原因: `use-daily-shortcuts.ts` の `case "b"/"f"` は打刻状態を見ずに `editing` を立てるが、`daily-list.tsx` の時刻入力欄は `task.startedAt !== null &&` の内側にあり**未打刻タスクでは描画されない**。一方フックは `if (editing !== null) return;` で**全ショートカットを止める**（[画面定義書01](../仕様/13_画面定義書/01_デイリーリスト.md) §6 / [共通](../仕様/13_画面定義書/00_共通.md) §3）。`editing` を解除できるのは `onEndEdit`（入力欄の blur・`Esc` かポップオーバーの `onClose`）だけなので、**発火源が存在しないまま無効状態が固定される**
- 対応方針: `requestEdit("startedAt"/"endedAt")` の側で打刻の有無を見て、無ければ `editing` を立てない（あわせて `daily-list.tsx` の `initialValue` の到達不能分岐2つも消える）
- 発見: T-39 第2バッチ②のテスト作成時。レビューでの「`initialValue` の `""` 側は到達可能では」という指摘をワーカーが検算し、到達不能＝**死んだ枝がガードの裏返しとして生じている**ことから判明した
- 関連: [FB-58](#fb-58) と修正箇所が同じ（`requestEdit` が打刻の有無を見ていない）ので**一緒に決めて一緒に直す**。ただし FB-58 は「入力欄は出るので `Esc` で戻れる」＝仕様の穴、本件は「戻れない」＝不具合で、害の大きさが違う

### FB-64

- 現象: 通信断・タイムアウト・サーバ 500 で Server Action が reject したとき、トーストもロールバックも出ない。オフラインで打刻すると**画面上は成功したように見えたまま保存されていない**状態になりうる
- 原因: [画面定義書01](../仕様/13_画面定義書/01_デイリーリスト.md) §8 は「永続化失敗（ネットワーク等）→ トースト『保存に失敗しました』＋UIロールバック」と定めるが、`daily-board.tsx` の `run` / `runSelectingCreated` / `operate` / `routinize` のいずれにも `try/catch` が無く、**Promise の拒否は transition の外へ抜ける**。実装が扱っているのは `ActionResult` が `{ ok: false }` を返す業務的失敗だけで、通信断の経路は素通りしている（N-01 の楽観的更新は「失敗したら戻す」が対で初めて成立する）
  - **同型がマスタ管理にもある** — `masters/_lib/use-master-action.ts` も `startTransition` 内で `await action()` するだけで catch が無く、reject すると unhandled rejection になり `isPending` の戻りとエラー表示が不定になる（こちらは楽観的更新をしないぶんロールバックは不要だが、失敗が何も表示されない点は同じ）
- 対応方針: 共通の失敗処理を通す形（各画面の実行関数に集約するか、`ActionResult` へ落とす薄いラッパを噛ませるか）を決めてから docs 反映
- 発見: T-39 第2バッチ③のテスト作成時。`{ok:false}` の失敗は12件のテストで固定できたが、reject 経路は実装が無いため書けなかった
- 関連: [T-42](./23_技術改善バックログ.md#t-42)（未知のエラーコードでメッセージが `undefined` になる）と同じ「失敗がユーザーに伝わらない」系で、どちらも `actions.ts` 周辺を触るため**一緒に着手すると効率的**

### FB-72

- 現象: 同じドメインエラーコードに**画面ごとの別文言**が当たっている。①`ended_before_started` — 打刻修正のクライアント側は「終了時刻は開始時刻より後にしてください」、サーバ側は「終了時刻が開始時刻より前になります」 ②`invalid_start_time` — ルーチン管理側は「開始想定時刻を HH:MM 形式で入力してください」、デイリー側は「開始想定時刻を HH:MM で入力してください」。どちらの経路を通るかで表示が変わるが、ユーザーから見れば同じ失敗
- 原因: 辞書が画面ごと・クライアント／サーバごとに分かれて写されている（[T-49](./23_技術改善バックログ.md#t-49)）。写した時点では一致していても、片方だけ直すと静かに割れる
- オーナー判断（2026-07-26）: ①は「**終了時刻は開始時刻より後にしてください**」に寄せる——**どう直せばよいかを告げる形**で、他の文言（「名前を入力してください」「見積もりは1分以上の整数で入力してください」）の指示形と揃うため。②は「**開始想定時刻を HH:MM 形式で入力してください**」に寄せる——「形式」が入ることで HH:MM が書式の例示だと読み取れるため。いずれも**サーバ側・デイリー側の文言が変わる**（＝表示が変わる）
- 反映先: 文言カタログは画面定義書に持たせない。**集約後の辞書と、その対応表を固定するテストを単一の正とする**（[T-49](./23_技術改善バックログ.md#t-49) が「良い形」と評価する `masters/_lib/action-result.ts` ＋ `action-result.test.ts` の先例に揃える）。画面定義書へ全文言を書くと「同じ規則を2か所に書かない」規約に反し、改訂のたびに食い違う
- 対応: T-49（辞書の集約）の中で実装する。**T-49 は本判断が無いと着手できない**——1本の辞書へ集約する以上、どちらかに寄せざるを得ないため
- 関連: [T-49](./23_技術改善バックログ.md#t-49)（実装の器） / [FB-71](#fb-71)（同じ辞書群の別の穴。**一緒に片付けるのが早い**）

### FB-56

- 現象: 同じ結果になるルーチンの作り方が2通りある（繰り返し種別「毎日」と「週次＋全曜日」）。一覧の要約表示も「毎日」と「週次(月・火・水・木・金・土・日)」に分かれる。全曜日が選択された場合は**「毎日」として DB 登録**し、表示もすべて毎日に寄せたい
- 対応方針: 保存時に正規化する。ただし**`week_interval` が2以上のときは寄せられない** — `隔週(全曜日)` は「2週おきに、その週は7日連続」という別の意味で、間隔の概念を持たない `recurrence_type = daily` には表現できない（`3週ごと(全曜日)` も同様）
- 詰める点: ①正規化の条件を `週次 かつ 全曜日 かつ week_interval ∈ {NULL, 1}` に限定してよいか ②`weekdays` と `week_interval` を NULL に落とすか値を残すか ③正規化する場所（保存時に domain の入力検証か usecase へ寄せれば表示側は無変更で「毎日」と出るため `describeRecurrence` に分岐が増えない）④フォームで7つめの曜日にチェックが入った瞬間に種別を「毎日」へ切り替えるか、黙って保存時に正規化するか（後者は編集フォームを開き直したとき曜日チェックが消えて驚きが出る）⑤既存データに `週次＋全曜日＋week_interval=1` の行があるか、あればバックフィルするか次の保存時に寄るのを待つか
- 発見: FB-53 の動作確認時にオーナーが発見（FB-53 自体は列挙のまま実装済み・確認済み）
- 関連: **スキーマは無変更の見込みだが書き込む値の規則が変わる**ため、[データモデル定義書](../仕様/14_データモデル定義書.md) §3.4（`weekdays` の意味づけ）と §4.1（展開判定）の確認が必要

### FB-57

- 現象: 「未設定」を表す**語**が UI 内で4通りに割れている — セルの表記は薄色の `-`（FB-55 で統一済み）／デイリーの選択ポップオーバーの候補は「モードなし」「プロジェクトなし」／ルーチン編集フォームのセレクトは「なし」／レビュー集計のグループ行は「（未設定）」
- 原因: [共通](../仕様/13_画面定義書/00_共通.md) §2.4 は**セルの表記だけを規定し、選択肢・グループ行の文言を規定していない**ため、同じ意味の語が画面と部品で割れたまま増える
- 対応方針: FB-55 と同種の食い違いなので対処も同じ形 — **上位文書で語を確定 → 各画面定義書はそこを参照 → その規定に沿って全画面を点検・整備**
- 詰める点: ①規定する範囲（セルの記号・選択肢の文言・集計のグループ行ラベル・`aria-label` の読み上げ語のどこまでを §2.4 に含めるか）②選択肢の語を「なし」と「未設定」のどちらに揃えるか（「モードなし」のように属性名を冠するかも含む。冠すると候補一覧で語が長くなる一方、ポップオーバー単体では何の「なし」か読み取れる）③グループ行の「（未設定）」を選択肢の語と揃えるか、行ラベルとして別扱いのまま残すか（§2.4 は現状「別」としている）④点検の網羅（デイリー・ルーチン一覧/編集フォーム・レビュー・マスタ管理を一度に洗い出す）
- 発見: FB-55 のレビューで `code-quality-reviewer` が発見

### FB-69

- 現象: 実行中タスク A がある状態で B を開始する割り込み（F-201）では、**非同期区間中に画面上「実行中タスクが2件」に見えうる**（「実行中は全体で最大1件」という不変条件はサーバ側では守られている）。この振る舞いが N-01 から読み取れない
- 原因: [要件定義書](../仕様/12_要件定義書.md) §6 の N-01 が楽観的更新から除外しているのは「中断 O-4・複製 O-11・先送り O-7」の3つで、**開始（O-2）は列挙されていない**＝打刻として全面的に楽観更新の対象と読める。しかし割り込みは **A の自動終了と A の再開タスク生成というサーバ採番を伴う副作用**を持ち、この点で O-11・O-14 と同型。実装は `case "start"` で **B 自身の `startedAt` だけを楽観的に反映し、A の終了・再開タスクの生成はサーバ確定後**にしており、根拠はコード内コメントにしかない
- 詰める点: ①docs 側に寄せる — N-01 の除外一覧に「開始（O-2）の割り込み時、相手タスクの終了・再開タスク生成の反映」を足すか、O-2 の行に「相手タスクの反映はサーバ確定後」と明記する ②実装側に寄せる — O-11 / O-14 と同様に全面除外にするか、逆に相手タスクの終了までクライアントで先取り反映する
- 発見: T-39 第2バッチの最終 `spec-reviewer`。テストは「画面側で2アクションに分解しない」というサーバ側トランザクションの正しさを固定しているが、**クライアント表示が一時的に旧状態を保持する点は N-01 の記述から読み取れない**

### FB-58

- 現象: 実行中タスク（`started_at` あり・`ended_at` なし）で `F` を押すと**空欄の終了時刻入力欄**が開き、そこへ入力すると実質的に「終了時刻だけ先に決める」ことになる
- 原因: [画面定義書01](../仕様/13_画面定義書/01_デイリーリスト.md) §6 は `B`/`F` を「開始時刻 / 終了時刻のインライン修正」としか書かず、実行中に使えるのが意図かどうか読み取れない（`B` は開始済みなら常に意味を持つので同列に扱えない）
- 詰める点: ①実行中は `F` を無効にするか、押せるが「終了時刻を入れたら完了扱いにする」か、現状どおり空欄編集を許すか ②無効にするなら未実行タスクの `B` も同じ扱いにするか（未実行で開始時刻だけ入るのも同型の状態）③打刻から状態を導出する設計（`ended_at` を入れた瞬間に完了になる）との整合
- 発見: T-39 第2バッチ②のテスト作成時。到達可能な状態のためテストは現実装を固定してある
- 関連: [FB-68](#fb-68)（未打刻タスクの `B`／`F` でキーボードがデッドロックする不具合）と修正箇所が同じ（`requestEdit` が打刻の有無を見ていない）ので**一緒に決めて一緒に直す**

### FB-59

- 現象: マスタ管理のカラーピッカーが[共通](../仕様/13_画面定義書/00_共通.md) §2.1 のポップオーバー規約を満たしていない。§2.1 は候補選択に「`J`/`K` で移動して Enter 確定・Esc 取消（開くと現在値をハイライト）」、表示位置に「下に入りきらず上の余白が広いときだけ上向きへ反転」を定めるが、実装はクリック選択と Esc／外側クリックのみで、位置も常に下（`use-flip-up` 未使用）
- 原因: §2.1 が候補選択の詳細を S-01 §6（F-112）へ委譲しているため、**マスタ側のポップオーバーにも同じ規約が及ぶのかが読み取れない**。これが問題の本体
