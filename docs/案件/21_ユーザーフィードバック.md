# ユーザーフィードバック管理簿

- 作成日: 2026-07-20
- 目的: 実運用で得たオーナーの気づきを一元管理し、今後の開発の入力にする
- 運用ルールをなぜそう定めたかは本書に書かず、[log_21_ユーザーフィードバック.md](./log_21_ユーザーフィードバック.md) へ日付順に積む（CLAUDE.md「書き方の規約」）

## 運用ルール

1. 気づきはまず本書に**起票**する（粒度はバラバラで良い。会話で出たものは AI が転記する）
2. 起票時に**分類**する: `不具合` / `改善（軽微）` / `改善（要仕様整理）` / `要求（優先度変更含む）` / `開発環境`。分類は[一覧](#一覧)のどの節に置くかで表す（列としては持たない）
3. **1エントリ ＝ 一覧の1行 ＋ [詳細](#詳細)の1節**。一覧は索引に徹し、`ID / 起票日 / タイトル / 詳細 / 状態` の5列だけを持つ
   - **タイトル**は内容を一文に要約する。体言止めにせず「〜が〜する」まで書き、読んで何の話か分かる粒度にする（目安40字前後）
   - **詳細**列には `[詳細](#fb-xx)` のリンクだけを置く。本文は[詳細](#詳細)の `### FB-XX` 節に書く（**見出しは ID のみ**。タイトルを重ねると改題のたびにアンカーが壊れ、一覧との二重管理にもなる）
   - **分類と状態を詳細節に書かない**。分類は節の位置、状態は一覧の状態列が正（二重に持つと必ず食い違う）
   - 詳細節の並び順は一覧と同じにする
4. 詳細節は**決まった項目を決まった順に**並べる。該当しない項目は省く（空欄で残さない）

   | 項目 | いつ書くか |
   |---|---|
   | 現象 | **必須**。何が起きるか・何が読み取れないかを書く |
   | 原因 | 実装上・文書上の所在が分かっているとき |
   | 対応方針 | 方針が既に定まっているとき（`改善（軽微）`は基本ここまでで閉じる） |
   | 詰める点 | オーナーと決める論点。`改善（要仕様整理）`は**必須**。①②③ で並べる |
   | 発見 | どの作業で気づいたか（後から経緯をたどるため） |
   | 関連 | 他の FB・T との関係や参照すべき文書。**一緒に処理すべきなら「一緒に決める」まで書く** |

5. 対応するときは通常の開発ルールに従う — **挙動レベルの変更は該当仕様書を先に更新**し（[guide_21_ユーザーフィードバック.md](./guide_21_ユーザーフィードバック.md)）、本書には対応結果と参照先だけを残す
6. 状態は `未対応` / `対応中` / `対応済み` / `見送り` の4つ。対応済み・見送りには日付と理由（または反映先）を書く
7. **対応済み・見送りになったエントリは、状態更新と同じコミットで[closed_21_ユーザーフィードバック.md](./closed_21_ユーザーフィードバック.md)へ移す**（本書には未対応・対応中だけを残す）。**一覧の行と詳細節はセットで移す** — `npm run ledger:move -- FB-XX` が両方を移す

## 詳細

### FB-77

- 現象: セクション見出し行が通常のタスク行と同じく流れるため、タスク件数の多い日にスクロールすると**いま見えているタスクがどのセクションに属するか**が分からなくなり、見出しに載る合計/枠・残り時間（F-110）・進捗（F-114）・現在セクションの強調（F-121）も読めなくなる。[画面定義書01](../仕様/13_画面定義書/01_デイリーリスト.md) §2 で sticky なのは画面上部（h1・日付ナビ＋サマリ・クイック追加欄）だけで、**セクション見出しをスティッキーにしたい**
- 実装上の所在: `daily-list.tsx` は `<table>` をセクションごとの `<tbody>` に分け、見出しは `GroupHeading` の1行（`<td colSpan={8}>`）。見出しセルへ `position: sticky` ＋上部固定領域ぶんのオフセット（`daily-board.tsx` が ResizeObserver で測る `stickyHeight`）を与えれば、**sticky の封じ込め範囲が `<tbody>` になるため「そのセクションが流れ終わると次の見出しに押し出される」挙動が素で得られる**（`<tr>` 自体には sticky が効かないためセル側に付ける）。帯色 `band` / `band-now` は不透明なので下の行は透けない
- オーナー判断（2026-07-27）: **「未分類」グループの見出しも同じく固定する**（時間帯の枠は持たないが、1グループとして扱いを揃える）
- 詰める点: ①**列見出し行**（タスク / プロジェクト / モード / …）を固定するかは**着手時に UI を再検討して決める**。現行 §2 は「列見出し行は固定しない」と明記しているため、固定するなら条項の書き換えになる。固定しないままなら、スクロール中はセクション見出しが列見出しの位置に重なる ②**選択行のスクロール追従（§5）のオフセットにセクション見出しの高さを足す**必要がある（現在は `scrollMarginTop = stickyHeight` のみ。足さないと追従した行が貼り付いた見出しの裏に隠れ、§2 の「固定領域の高さを避けて停止する」を満たさなくなる）。見出し高を定数で置くか測るか ③貼り付いている見出しが**現在セクションでないとき**、`band-now`（F-121）との対比で「いまの時間帯」を誤読しないか ④重なり順（上部固定領域は `z-10`）——貼り付いた見出しが選択ポップオーバー・行メニューの上に出ないか ⑤要求軸の判定（[guide 手順1](./guide_21_ユーザーフィードバック.md)）は着手時に行う。「見出しの情報をスクロール中も読める」ことが F-105/110/114/121 の範囲に収まるか、新しい要求 ID を起こすか
- 発見: 2026-07-27、オーナーの実運用での気づき
- 関連: [画面定義書01](../仕様/13_画面定義書/01_デイリーリスト.md) §2（上部の sticky。[FB-22](./closed_21_ユーザーフィードバック.md#旧書式の記録2026-07-26-以前) で導入）・§3.2（見出し行の内容）・§5（選択行の追従）

### FB-79

- 現象: 実行中タスクを「本当は 10:30 に終わっていた」と後から締めたい場面で、いまは `Enter`（現在時刻で終了打刻）→ `F`（終了時刻を修正）の2手が要る。終了時刻を直接入れて完了させる入口は無い（[画面定義書01](../仕様/13_画面定義書/01_デイリーリスト.md) §3.3 / §6。`F` は完了した行でのみ開く）
- 経緯: [FB-58](./closed_21_ユーザーフィードバック.md#fb-58) の詰める点①で挙がった3案のうち「押せるが、終了時刻を入れたら完了扱いにする」案。FB-68 / FB-58 の対応（2026-07-27）では**打刻済みの時刻だけを修正できる**規則を採り、実行中の `F` は無効にした。残った本案だけを切り離して検討する
- 詰める点: ①そもそも必要か（`Enter` → `F` の2手で足り、終了忘れは F-209 の警告バナーが拾う）②入れるなら入口をどうするか（`F` に載せる／別キー／行メニュー）。`F` に載せると同じキーが「修正」と「完了」の2つの意味を持つ ③打刻から状態を導出する設計（[データモデル定義書](../仕様/14_データモデル定義書.md) §3.5）との整合——`ended_at` を入れた瞬間に完了になる規則自体は変わらないが、**終了打刻の入口が `Enter`・打刻ボタン以外に増える**ことの是非 ④開始 ≦ 終了の検証は既存のまま使えるか
- 発見: FB-68 対応時のオーナー判断（2026-07-27）。「別途検討 FB で積む」

### FB-82

- 現象: デイリー画面はマウスとキーボードを**等価な2経路**として持つ（[画面定義書01](../仕様/13_画面定義書/01_デイリーリスト.md) §5）。同じ操作に入口が2つあるぶん、結線もテストの観点も二重になり、**片方の経路にしか存在しない状態**も生まれる。実例: 打刻ボタンが行ごとにあるため「選択している行」と「打刻する行」が食い違う状態を作れ、F-211 の「送り先が無いときの選択」がその状態について長く未定義のままだった（2026-08-02 に「打刻した行へ送る」で確定）。キーボードだけなら操作対象は常に選択行なので、この食い違い自体が起きない
- 見積もりの材料（2026-08-02 実測。[T-101](./closed_23_技術改善バックログ.md#t-101) の分割時に数えた）: 盤面テスト114件の入口は **キー起点68 / マウス起点29 / 両方8 / 入口なし9**。マウス経路を落とすと**29件が丸ごと消え、8件が縮む**。ファイルでは `row-operations`（行メニューの導線）と `optimistic`・`punch`（打刻ボタン起点）に集中する。実装側では打刻ボタン・行メニュー・⭐・ポップオーバーの候補クリックが対象
- 詰める点: ①**どこまで寄せるか**（マウスでの打刻ボタンを残すか・選択だけマウス可にするか・現状維持で条項の書き方だけ変えるか）②**削れる実装とテストの量を先に見積もる**——上の実測が出発点。「簡潔になるなら」が採用理由なので、効果が小さければ採らない ③オーナーの実運用でマウスに手が伸びる場面があるか（打刻ボタンは1クリックで済む導線でもある）④寄せる場合、§5 の「マウス操作とキーボード操作は等価」と N-04（キーボード完結）の関係をどう書き換えるか ⑤キーを増やす場合の追加コストは [T-98](./closed_23_技術改善バックログ.md#t-98) で下がっている（キー定義は1つの表が正になり、ディスパッチャとの一致は両方向のテストが見る）
- 発見: T-96（テストのクリック道具の統一）で、クリック経路のテストが持つ観点の多さと、選択と打刻の食い違いによる仕様の穴に気づいた（2026-08-02）
- 関連: [画面定義書01](../仕様/13_画面定義書/01_デイリーリスト.md) §5（選択モデル・等価性）・§6（ショートカット）/ F-211 / N-04 / [T-98](./closed_23_技術改善バックログ.md#t-98)（キー定義を1つの表へ集約済み）

### FB-84

- 現象: 終了予定時刻（F-104）・予想開始時刻（F-120）の**折返し表記が二桁の大きい時刻になり、時計として読み取りにくい**。折返しの起点は論理日の暦日 0:00 なので、日界（F-116）が 00:00 以外だと論理日の後半（暦日をまたいだ側）が 24:00 超で表される。日界 05:00 なら論理日の終わりは翌 05:00 ＝ `29:00` まで伸びる
- 原因: 仕様どおりの表示で、実装の誤りではない。**折返しの時計数字を暦日 0:00 起点のままにする**と定めてある（[データモデル定義書](../仕様/14_データモデル定義書.md) §4.3 の日界の項 / [画面定義書01](../仕様/13_画面定義書/01_デイリーリスト.md) §3.2・§3.3）。超過警告だけが日界基準という非対称もそこに書かれている
- オーナーの構え（2026-08-03）: **本番運用で実際に困らなければ据え置いてよい**。単一利用者のアプリなので、読みにくさが実害になるかは本人の使用感がすべて。しばらく使ってみて判断する（＝着手トリガは「実運用で読み間違えた・迷った」こと）
- 詰める点: ①そもそも直すか（上のとおり据え置きも正当な結論）②直すなら折返しの起点を日界へ移すか——移すと日界 05:00 での 06:00 が `01:00` になり、**暦日の時計と数字が一致しなくなる**（現行が暦日起点を採っている理由がこれ）③24:00 超だけ別の見せ方にするか（`翌 02:00` のような接頭辞・弱色など。桁を増やさずに「翌日」を伝えられるか）④終了予定の超過警告（予定終了が次の日界を越えると出る）との関係——表記を変えるなら警告の基準と食い違わないか
- 発見: 2026-08-03、[FB-83](./closed_21_ユーザーフィードバック.md#fb-83) の動作確認中。深夜の再現条件を昼間に作るため日界を一時的に午後へずらしたところ `30:38` と表示された。**日界を昼にするのは検証用の設定**なのでその値自体は通常運用では出ないが、通常の設定でも 25:00〜29:00 は日常的に出ることに気づいた
- 関連: F-104（終了予定）/ F-120（予想開始）/ F-116（日界）

### FB-88

- 現象: **過去日のログを後から作る**のに、打刻（`Enter`）→ 時刻の修正（`B`/`F`）の2手が要る。過去日のリストで `Enter` を押すと `started_at` には**実時刻（＝今）**が入るので、その論理日の外にある打刻がいったん出来上がり、それを修正で引き戻すことになる。未打刻のタスクに時刻を直接入れる道は無い（[画面定義書01](../仕様/13_画面定義書/01_デイリーリスト.md) §3.3「修正できるのは打刻済みの時刻だけ」）
- オーナーの案（2026-08-03）: **未打刻タスクにも `B`/`F` での時刻編集を許す**。そうすれば過去日の実績を1手で入れられる。ただし**仕様をかなり複雑にしそうなので慎重に検討したい**（本人の言）
- 経緯: 「打刻済みの時刻だけ編集できる」は [FB-68](./closed_21_ユーザーフィードバック.md#fb-68) / [FB-58](./closed_21_ユーザーフィードバック.md#fb-58) の対応（2026-07-27）で確定した規則で、未打刻タスクで `B`/`F` を押すとキーボードが固定される不具合を、キーとクリックの受け付け条件を揃えて塞いだもの。**この案はその決定を部分的に巻き戻す**ことになるので、当時の理由（描画側のガードと編集開始側の条件を同じ規則に保つ）を崩さない形が要る
- 詰める点: ①**状態の導出との整合**——タスクの状態は打刻から導出する（[データモデル定義書](../仕様/14_データモデル定義書.md) §3.5）ので、「開始時刻だけを入れた」時点でそのタスクは実行中になる。実行中は全体で最大1件という不変条件（F-201）に、過去日の入力が割り込むのをどう扱うか ②**入力の順序**——開始だけ入れて放置できるのか、開始と終了を1回の操作で入れさせるのか ③[FB-79](#fb-79)（実行中タスクに終了時刻を入れて完了させる入口）と**同じ問いの裏返し**なので、**2件は一緒に決める** ④今日のリストでも同じ入口を出すか、過去日だけに限るか（限ると「表示日で操作が変わる」を新たに導入することになる）⑤入れた時刻に対する検証（[FB-83](./closed_21_ユーザーフィードバック.md#fb-83) で決めた論理日基準の解釈・未来禁止をそのまま適用できるか）⑥入力したログの配置は自動セクション移動（規則 c）に委ねられる——[FB-87](./closed_21_ユーザーフィードバック.md#fb-87) で対象日の制限が外れ過去日でも効くようになったが、それが働くのは**開始時刻を修正したとき**なので、未打刻タスクへの直接入力を新しい契機として規則へ足すのか、修正と同じ経路に乗せるのかを決める必要がある
- 発見: 2026-08-03、[FB-87](./closed_21_ユーザーフィードバック.md#fb-87) を話す中でオーナーから
- 関連: [FB-79](#fb-79)（**一緒に決める**）/ [FB-87](./closed_21_ユーザーフィードバック.md#fb-87)（入れたログの配置）/ [完了記録](./closed_21_ユーザーフィードバック.md) FB-68・FB-58（現行規則を決めた側）/ F-201 / F-203 / [T-114](./23_技術改善バックログ.md#t-114)
