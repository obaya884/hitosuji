未実装要求を**決定状態（レーン）＋熟度タグ＋着手トリガ**で管理する。フェーズ（リリース波）は MVP 完了で役割を終えたため用いない。挙動レベルの仕様判断が発生したら**先に**要件定義書群へ反映し、本書は一行の要約に留める。**個別FBの内容・反映先はFB管理簿、判断の経緯は各定義書の決定ログ、実装の変遷は git が正**。

## 書式

**1エントリ ＝ レーンの表の1行**。台帳21・23 と違い索引と詳細に分けない——1エントリが1行に収まる粒度で、分けると参照が増えるだけになる（詳しく書きたくなったら、それは要件定義書へ書く合図）。列は次の6つで、**すべて埋める**。

| 列 | 中身 |
|---|---|
| ID | `F-XXX` / `N-XX`（要求定義書 §6 の採番） |
| タイトル | 要求の名前。要求定義書の表記に合わせる |
| 熟度 | **着手時にオーナーの仕様判断が要るか**を、参照先 docs の実体で判定する（下表）。**決定状態（レーン）とは直交する軸** |
| 内容 | 何を作るかの一行要約。無ければ `-` |
| トリガ | **着手条件（監視項目は観察の閾値）。ここを空にしない**——トリガの無いエントリは次の選出（`next-task`）で永久に拾われない |
| 参照 | 反映先の条項・検討ドキュメント |

### 熟度の判定

| 熟度 | 条件（**参照先を開いて確かめる**） | 着手したらどこから始まるか |
|---|---|---|
| 仕様済 | 画面定義書（＋必要ならデータモデル定義書）に**操作仕様の実体**がある。その条項だけを読んで実装の判断が全部つく | 実装 |
| 設計済 | 検討ドキュメントに方式がある。画面への展開はこれから | 画面定義書への展開判断 |
| 列済 | データ列だけ用意済み。UI は白紙 | UI の仕様判断 |
| 未詰め | 要求文しかない | FB 相当の仕様判断（オーナーとの対話） |
| `-` | 未評価 | 不明。次に触るとき判定する |

**画面定義書に1行あることと、その1行で実装できることは違う。** `（未実装 / F-XXX）` が付いた条項は要求文の言い換えなので**仕様済ではない**（`ledger:check` が検出する）。実績として、完了した4件はすべて着手時に FB（要仕様整理）で UI を決めており、うち F-117 は起票時から仕様済だったが実際には開き方・週の起点・月移動の範囲・カレンダー内のキー操作を着手時に決めている（[log_22](./log_22_要件バックログ.md) 2026-07-26）。

- **セル内に `|` を書かない**（`ledger:check` が列を数えられなくなる）
- レーンは `確定・着手待ち` / `候補・見極め中` / `監視項目` の3つ。**状態は行に持たず、どの表に置くかで表す**
- **見送りの出口**: 候補を見極めた結果やらないと決めたら、要求定義書 §8 スコープ外＋§10 決定ログへ落とす（F-109・F-207 と同じ扱い）
- **完了したエントリは[closed_22_要件バックログ.md](./closed_22_要件バックログ.md)へ移す**。移す際は1行を `## F-XXX タイトル（完了日）`＋対応・反映先の節に展開する（完了記録は「何をどう決めて何に反映したか」を残す文書で、バックログの一行要約とは持つべき情報が違うため書式が異なる。この変換は機械化していない）

## 現況

MVP 完了、2026-07-20 実運用開始。以後は継続運用モードで、案件は運用の気づきから随時流入する。未着手の要求は下記3レーンで管理し、着手条件（トリガ）が来たものから取りかかる。実運用そのものは区切りのない継続活動のため、気づきは随時[FB管理簿](./21_ユーザーフィードバック.md)へ起票する。
