### T-48

- 背景: `daily-board.tsx` の `applyOptimisticAction` / `pendingUndoMessage` / `optimisticTask`（同ファイル 92〜187行）は**純関数**で、[アーキテクチャ定義書](../仕様/15_アーキテクチャ定義書.md) §8 の「presentation はまず純粋ロジックを `.ts` へ切り出してユニットテスト」に照らすと切り出す対象。`test-reviewer` の指摘
- 効果: 12種の楽観アクションの組合せを**ユニット段で安く網羅**でき、コンポーネント段（jsdom・描画あり）は代表経路だけで済む。現状は 60件のコンポーネントテストがこの組合せを担っており、実行時間と読みやすさの両方で割高
- 注意: 現在 `daily-board.tsx` は Stmts 97.47% / Lines 100% まで来ているので、**切り出しはカバレッジを埋めるためではなく段を適正化するための作業**。切り出し後もコンポーネント段の代表テストは残す（結線が壊れたら気づけなくなるため）
- 着手条件: `daily-board.tsx` を別件で触るとき、または楽観アクションの種類を増やすとき（そこで組合せが増えると段の割高さが効いてくる）
- 関連: [アーキテクチャ定義書](../仕様/15_アーキテクチャ定義書.md) §8 / `(daily)/_lib/popover-scroll.ts`・`_lib/flip-up.ts`（同じ流儀の先例） / T-39 第2バッチ③
- 結果（2026-07-26）: **2ファイルへ分けた**——`_lib/optimistic.ts`（`OptimisticAction` 型・`applyOptimisticAction`・`optimisticTask`）と `_lib/undo.ts`（`UndoTarget` / `PendingUndo` 型・`pendingUndoMessage`）。1ファイルにまとめなかったのは、前者が「グループ列をどう変えるか」、後者が「保留を何で持ちどう伝えるか」で関心が別だから（`_lib` の既存2ファイルも1関心1ファイル）。ユニットテストを追加し、`daily-board.tsx` は 650 → 541行。**T-48 が割高と見ていたコンポーネントテストは1件も削っていない**——上の「注意」のとおり、あれらが見ているのは組合せではなく Server Action との結線（楽観反映 → 確定 or ロールバック → トースト）で、ユニット段では代替できない（`test-reviewer` も据え置きを妥当と判定）。同じコミットで1件だけ減っているのは、直前の FB-65 で私が足した重複テストを上位互換の既存テストへ統合したもので、T-48 の対象ではない。エラー文言辞書（`PUNCH_EDIT_MESSAGES`）は [T-49](../案件/23_技術改善バックログ.md#t-49) の守備範囲なので手を付けていない

### T-66

- 背景: CLAUDE.md「サブエージェント運用」は**どのエージェントをどの契機で起動するか**を定めているが、**`general-purpose` をどう使うか**（そもそも起動するか・どのモデルで・どこまで読ませるか）は定めていない。結果、読み取り中心の調査まで全ツール持ちの `general-purpose` に投げており、これは `model` 未指定なのでセッションモデル（opus）を継承する
- 顕在化した経路: 2026-07-26 に消費の内訳を確認したところ、直近24hで **`general-purpose` が単独 33%**、レビュー系5本の合計は 11%（test-reviewer 5 / code-quality-reviewer 3 / spec-reviewer 1 / verifier 1 / refactor-scout 1）だった。あわせて「99% が subagent-heavy セッション」「77% が8時間以上のセッション」「72% が 150k コンテキスト超」も出ている
- 実害: 週・5時間の利用枠を実装以外で先に使い切る。T-39 第2バッチ以降サブエージェントの並列起動を常用するようになったため、放置すると悪化する
- 対応方針: ①読み取り中心の調査は `Explore`（読み取り専用・結論だけ返す）を既定にし、`general-purpose` は**編集を伴う自己完結タスクに限る** ②`general-purpose` を機械的な作業に使うときは起動時に `sonnet` を明示する ③タスクの切れ目で文脈を切る（150k 超が消費の7割）
- 見送った案: **レビュー系5本を sonnet へ落とす**。opus 指定の3本を全部落としても 9% しか動かず、節約が小さすぎて品質との取引が成立しない。とくに `test-reviewer`（レビュー中最大の 5%）は「実装をどう壊しても緑のままではないか」という反実仮想の推論が本体で、**見逃しが「指摘なし」と区別できない**沈黙する失敗になる。判断の経緯は[決定ログ](./log_23_技術改善バックログ.md)
- 対応: CLAUDE.md「サブエージェント運用」に **§起動のコスト**を新設し、上の4点を明文化した（2026-07-26）

### T-67

- 背景: `verifier` は5本のサブエージェントで唯一 `Bash` による書き込み・実行の権限を持つ。2026-07-26 に**2度**、自分に課した制約を破って作業ツリーを壊した——①変異テストのために `git stash` → `git reset --hard` し、stash を戻さず終了（メインセッションの未コミット25ファイルが一時的に消失。`git stash pop` で復旧）②同日、変異を「Edit で1か所」ではなくスクリプトで一括適用し、停止時に戻さず `src/app/_testing/next-navigation.ts` に残した。**いずれも引き金は変異テスト（コードを壊してテストが落ちるか確かめる）を依頼したこと**
- 実害: メインセッションの未コミット作業の消失。①は気づかなければ数十ファイルを失っていた。②はツリーが汚れたまま次の作業に入る
- 対応方針: **`verifier` の責務から変異テストを外す**。禁止条項を積み増しても、破れる能力が残っている限り同じ事故が起きる（①のあとに条項を足したうえで②が起きた）。変異テストが要るときはメインセッションが Edit で行う——差分がチャットに出るので、戻し忘れもオーナーから見える（CLAUDE.md「規約」のスクリプト一括置換禁止と同じ理由）
- 優先度の根拠: 失うのが未コミットの作業で、復旧手段が `git reflog` / `git stash list` を思いつけるかに依存する。実際に2回踏んでいる
- 対応: `.claude/agents/verifier.md` の制約を「ファイルを一切書き換えない／変異テストは引き受けない」に置き換え、CLAUDE.md「規約」の Edit 必須ルールに変異テストの手順を追記した（2026-07-26）
- 積み残し: 委譲先そのものを作るかは [T-68](./23_技術改善バックログ.md#t-68) で検討する（本 T は安全側に倒しただけで、置き場を見つけたわけではない）

### T-40

- 背景: `scripts/wt-new.sh` は dev ポートを **worktree 作成時点で 3001 から空きを探して** `.env.worktree` の `DEV_PORT` に焼き込む。dev サーバを立てずに worktree を続けて作ると全部が同じ 3001 になり、後から2つで `npm run dev` すると衝突する。2026-07-26 の T-39 第2バッチで worktree を6つ作り、**6つすべてが 3001** になって顕在化した——T-34 が言う「固有ポート」は、作成時点で他の dev サーバが動いていた場合にだけ固有になる
- 実害の程度: ワーカーは lint / build / test で完結し dev サーバを使わないため、並行実装そのものは妨げない。効くのは**オーナーが複数ブランチの画面を同時に確認したいとき**（片方を止めれば回避できる）
- 対応方針の候補（着手時に決める）:
  - **ブランチ名のハッシュから決める**（例 `3001 + hash % 90`）— 作成順に依存せず冪等で、`.env.worktree` へ焼き込む今の形をそのまま使える。衝突確率は残るが同時に扱う worktree が数個なら実用上足りる
  - **起動時に探す**（`scripts/dev.sh` が `DEV_PORT` を起点に空きを探す）— 実際に衝突しない保証は得られるが、表示ポートが起動のたびに変わり `wt:new` が案内した URL と食い違う
  - 併用（作成時はハッシュで焼き、起動時に埋まっていたらずらす）が素直かもしれない
- 着手条件: 2つ以上の worktree で dev サーバを同時に立てたくなったとき
- 関連: **[T-46](#t-46)（同じ `scripts/wt-new.sh` を触るので一緒に着手すると早い）** / [完了記録](./closed_23_技術改善バックログ.md) T-34（dev サーバの並列化） / T-37（ワーカーからの実機確認が絡む） / [定義書16](../仕様/16_git運用と並行開発体制定義書.md) §2
- 結果（2026-07-26）: 候補2案（ハッシュ／起動時探索）はどちらも採らず、**既に `.env.worktree` に焼かれている割り当て済みポートを読んで避ける**形にした——衝突を確率ではなく事実として避けられ、`wt:new` が案内した URL も嘘にならない。`wt-new.sh` は 3001 から順に「他 worktree に割り当て済み」でも「使用中」でもない番号を選ぶ（3100 まで埋まっていればエラーで止める）。`dev.sh` は変更なし（割り当て外のプロセスが番号を掴んでいる場合の警告として今の形のまま残す）。あわせて `.env.worktree` の書き出しを `npm ci` の**前**へ移した——後だと選択から記録までの間に数分の窓ができ、`wt:new` を2本並行で走らせたときに互いの割り当てを見られず同じ番号を選ぶ（`code-quality-reviewer` の指摘）。判断の経緯は[定義書16の決定ログ](../仕様/log_16_git運用と並行開発体制定義書.md)、仕様は[定義書16](../仕様/16_git運用と並行開発体制定義書.md) §3.2

### T-46

- 背景: `wt-new.sh` の起点は既定でローカル `main`。**ローカルが origin より進んでいても検査せず worktree を作る**ため、未 push のコミットがそのまま全ブランチに複製される。2026-07-26 の T-39 第2バッチで実際に踏んだ——docs コミット1本（§8 の改訂）が未 push のまま6ブランチの起点になり、**6つの PR すべてに同じ docs 変更が写り込んだ**（GitHub は `origin/main` と比較するため）。ローカルで `main...branch` を見ると差分が出ないので、**ヘッドの検査では気づけずオーナーが PR 画面で発見した**
- 実害: 内容の巻き戻りは起きない（git は3方向マージなので、ブランチが変更していないファイルを古い版へ戻さない）。効くのは①PR の差分が汚れてレビューしづらい ②同じコミットが N 本の PR に重複して乗る ③マージ後にローカル main を rebase する際、既に適用済みのコミットの扱いで履歴が濁る
- 対応方針: `wt-new.sh` の起点解決時に `git rev-list --count origin/<base>..<base>` を見て、**0 でなければ警告して中断**する（`--allow-unpushed` 等で明示的に上書きできる逃げ道は残す）。スクリプト冒頭の「起点を最新にしたい場合は実行前に fetch / pull しておくこと」というコメントは**人間向けの注意で機械的な担保が無い**のが原因なので、そこを検査に変える

- 着手条件: 次に並行開発をするとき（同じ手順を踏むため）。単独モードでは worktree を作らないので急がない
- 関連: **[T-40](#t-40)（同じ `scripts/wt-new.sh` を触るので一緒に着手すると早い）** / [完了記録](./closed_23_技術改善バックログ.md) T-06・T-31〜36（worktree ツール一式） / [定義書16](../仕様/16_git運用と並行開発体制定義書.md) §5 手順2
- 結果（2026-07-26）: `wt-new.sh` が起点解決の前に `git rev-list --count origin/<起点>..<起点>` を見て、0 でなければ**未 push のコミットを一覧表示して中断**する（`--allow-unpushed` で上書き可）。あわせて検討事項だった fetch は**既定で実行**に決めた（`--no-fetch` で省略可）——`origin/<起点>` が古いと検査そのものが意味を失うため。`origin/<起点>` が存在しない起点も同じ扱いで止める。**逆向き（起点が `origin` より遅れている）は警告のみで続行**する（`npm ci` の出力に流されるため最後の案内でも再掲）。手順の記述（[定義書16](../仕様/16_git運用と並行開発体制定義書.md) §5 手順2）から「実行前に fetch しておく」という人間向けの注意が消え、スクリプトの担保に置き換わった。中断と警告で扱いを分けた理由は[定義書16の決定ログ](../仕様/log_16_git運用と並行開発体制定義書.md)

## T-35 並行タスク間のファイル衝突を機械判定する（2026-07-26）

- 種別: ツール整備 / 優先度: 中
- 背景: 並行度4本以上を目標にした（[定義書16](../仕様/16_git運用と並行開発体制定義書.md) §2）が、タスク分割時の衝突判定が**ヘッドの目視**に依っている。2026-07-25 の並行4本では `Explore` の調査で FB-48 と FB-51 が `daily-list.tsx` の同じ関数（`TaskRow` 内の10行以内）で衝突することを見つけて直列化できたが、本数が増えれば見落とす。見落とすと「自動マージは通るが意味的に壊れる」形になり、CI では検出できない
- 対応: `npm run wt:overlap`（`scripts/wt-overlap.sh`）を新設。稼働中の worktree のブランチ（または引数指定のブランチ）を総当たりし、`git diff --name-only <base>...<branch>` の積集合を出す。空のペアは「中間 rebase を省略してよい」、空でないペアは重なるファイルを列挙する。**積集合が空のペアには `git merge-tree` を重ねて掛ける**——ディレクトリとファイルの取り違えなど、ファイル名の突き合わせだけでは見逃す衝突があるため（§1.3 が両方を求めている理由）。終了コードは 0＝重なりなし / 1＝重なりあり / 2＝判定できなかった
- 当初あった方針①（着手前に変更予定ファイルを宣言させて交差を取る）は**作らない**。宣言という不確実な入力を機械化するより、各ブランチに最初のコミットが乗った時点で②を掛け直して実差分で検算するほうが確実なため。着手前の見積りは `Explore` の目視のままとし、この検算を §5 手順1 に明記した
- 結果: 挙動不変（開発ツールのみ）。使い捨てブランチで実測し、同一ファイルの重なり・交わらないペア・ディレクトリとファイルの衝突（積集合は空だが merge-tree が検出）・同一ブランチの重複指定・規約外のブランチ名・日本語パス・異常系の終了コードを確認した
- 残す注意: **意味的な衝突（別ファイルだが前提が壊れる）は原理的に検出できない**。分割の妥当性そのものは人が見る。この但し書きはスクリプトのヘッダと §1.3 の両方に置いた
- 関連: [定義書16](../仕様/16_git運用と並行開発体制定義書.md) §1.3・§5（判定の正）/ 本書 T-34・T-36（同じ `scripts/` 配下の整備）

## T-32 `wt:rm` が worktree ディレクトリを消し残す（2026-07-25）

- 種別: ツール整備 / 優先度: 中
- 背景: `git worktree remove` が "Directory not empty" で落ちることがあり、**実測で7本中4本が失敗**（当初「再現性が不定」と書いたが失敗率はほぼ半分）。失敗すると手前のテストDB削除と registration 解除までは通っているためディレクトリだけが残り、ローカルブランチの削除も手作業になる。残骸は `node_modules` を欠いた状態でエディタの型チェック対象に残り続け大量の偽エラーを出す
- 対応: **`--force` を無条件に付ける形は採らない**（dirty 判定の防護を迂回しないという既存判断の維持）。代わりに ①`node_modules`・`.next` を先に削除する（ファイル数の大半を占め、gitignore 対象なので clean 判定に影響しない）②失敗したら2秒待って再試行 ③それでも失敗したら登録解除＋明示削除へフォールバック（dirty の防護はスクリプト自身の `git status --porcelain` が既に果たしているため、ここで git の安全装置を迂回しても防護は落ちない）。あわせてブランチ削除を、`git branch -d` 失敗時に**リモートブランチの不在**（GitHub のマージ時自動削除）を確認して `-D` する形にし、squash マージ運用でも一連で通り切るようにした。`.env.local` のリンクは実体を消さないよう `-L` で確かめてから外す
- 結果: 挙動不変（開発ツールのみ）。worktree の作成 → 削除を通しで実行し、テストDB・ブランチ・ディレクトリまで残骸ゼロで完走
