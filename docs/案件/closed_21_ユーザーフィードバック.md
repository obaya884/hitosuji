### FB-60

- 現象: ボタンにフォーカスがある状態では `Enter` を押しても打刻されない。意図的な除外だが、条項のどこにも書かれていない
- 原因: 実装は `target.tagName === "BUTTON"` のとき打刻しない（打刻ボタンをクリックした直後に `Enter` が二重発火するのを防ぐため。根拠はコードコメントだけ）。[共通](../仕様/13_画面定義書/00_共通.md) §3 の除外規則は「テキスト入力中」までしか書かず、[画面定義書01](../仕様/13_画面定義書/01_デイリーリスト.md) §6 の一覧からも読み取れない
- 対応方針: **挙動は妥当で変更不要**。docs 側に1行足すだけで閉じる
- 発見: T-39 第2バッチ①のテスト作成時（テストは現実装を条項として固定済み）
- 関連: [FB-61](#fb-61)・[FB-65](#fb-65) と同じく「実装は正しく docs の条項が足りない」型なので、**3件まとめて1回の docs 改訂で閉じられる**

### FB-61

- 現象: `?` の説明が文書間で食い違う。画面定義書01 §6 の表は「ショートカット一覧の**表示**」、画面に出る文言（`shortcut-help.tsx`）と実装は「表示・**非表示**」のトグル
- 対応方針: 実装と画面文言が一致しているので、§6 の表記をトグルに寄せれば閉じる
- 発見: T-39 第2バッチ①
- 関連: [FB-60](#fb-60)・[FB-65](#fb-65) とまとめて処理可（同じ「実装は正しく docs が足りない」型）

### FB-65

- 現象: 「元に戻す」の有効期限が明文化されていない。実装では undo トーストを × で閉じるか5秒で自動消去されると保留（`pendingUndo`）も破棄され、以後 `U` を押しても取り消せない＝**トーストの寿命がそのまま取り消せる期限**。[画面定義書01](../仕様/13_画面定義書/01_デイリーリスト.md) O-8 / O-13 は「トーストのボタン、または続けての `U`」としか書かず期限が読み取れない
- 対応方針: 実装の挙動としては妥当（保留を無期限に持つと何を戻すのか曖昧になる）なので、**docs 側に1行足すだけで閉じる見込み**。[共通](../仕様/13_画面定義書/00_共通.md) §2.2 が undo トーストを5秒と定めているので、そこと結ぶ形が自然
- 発見: T-39 第2バッチ③（テストは現実装を固定済み）
- 関連: [FB-60](#fb-60)・[FB-61](#fb-61) とまとめて処理可

### FB-66

- 現象: [共通](../仕様/13_画面定義書/00_共通.md) §2.3「保存中は同じ行の他のセルは編集できない」がデイリーに存在しない。マスタ管理の各テーブルは `isPending` でセルを止めるが、`daily-board.tsx` の `editing` は「いまどのセルを編集しているか」だけを持ち保存中フラグが無いため、**保存の完了を待たずに同じ行の別セルを開ける**
- 原因: デイリーは楽観的更新（N-01）で即座に画面へ反映するため、マスタ（保存完了を待って反映）とは前提が違い、§2.3 をそのまま当てるのが正しいかも自明でない
- 詰める点: ①§2.3 が楽観的更新の画面にも及ぶのか（及ぶなら保存中フラグの導入が要る／及ばないなら §2.3 に適用範囲を書く）②同時編集で実際に壊れる組み合わせがあるか（例: 見積もりを保存中に開始時刻を編集）
- 発見: T-39 第2バッチ②③
- 関連: [FB-63](#fb-63) と同じ条項の話なので**一緒に決めるのが早い**

### FB-63

- 現象: 保存中の編集抑止が画面ごとに不揃い（[共通](../仕様/13_画面定義書/00_共通.md) §2.3 の適用範囲）。マスタ管理では、プロジェクト一覧の名前セルだけ `disabled={isPending}` が無く（モード・セクションには有る）、保存中に同じセルを開き直せる＝古い値を再送しうる。**同型がルーチン一覧にもある** — `routines-table.tsx` は有効トグルと削除に `disabled={isPending}` があるのに「編集」ボタンだけ無い（画面定義書02 §1 は N-01 対象外＝保存完了まで待つと定めている）
- 原因: 行内の編集可能セルが1つなので §2.3「保存中は同じ行の**他の**セルは編集できない」には形式上抵触しないが、条項の趣旨（保存中は編集を止める）からは外れる
- オーナー判断（2026-07-26）: [共通](../仕様/13_画面定義書/00_共通.md) §2.3 を**「保存中は同じ行は編集できない（他のセルも、同じセルの開き直しも）」**へ改め、あわせて**適用は保存完了を待って反映する画面に限る**と明記した。行内の編集可能セルが1つでも止めるのは、条項の目的が「古い値での上書きを防ぐ」ことであり、同じセルの開き直しでも同じ事故が起きるため。デイリー（楽観的更新）は適用外なので、本件の対象は**マスタ管理とルーチン管理の抜け2件だけ**に確定した
- 対応: プロジェクト一覧の名前セルと `routines-table.tsx` の「編集」ボタンに `disabled={isPending}` を足す。実装を3テーブルへ足すなら [T-44](./23_技術改善バックログ.md#t-44)（部品の抽出）を先にする方が早い
- 発見: T-39 第2バッチ④⑤（テストは現状を「FB-63 で検討中」と明示して固定済み。実装に合わせて更新が要る）
- 関連: FB-66（同じ条項の裏面。デイリーが適用外と確定したことで本件が独立した） / [T-44](./closed_23_技術改善バックログ.md#t-44)
- **対応（2026-07-27・T-44 の #66 に同梱）**: プロジェクト一覧の名前セルは部品抽出（`MasterEditableCell`）で自動的に揃い、ルーチン管理は「編集」ボタン・新規/編集フォームの保存と取消・フォーム内の選択（繰り返し種別・曜日・モード/プロジェクト）を `disabled={isPending}` で止めた。**調査の過程で §2.3 自体を2度改訂している**——①開いたままの入力欄からの再確定・新規追加行の連打と取消 ②新規作成フォーム・「保存中に始める操作」・送信せず表示だけを変える選択。当初「マスタ管理とルーチン管理の抜け2件だけ」と見立てた範囲は、**部品を1か所へ集めたことで同型の穴がまとめて見えた結果、条項ごと広がった**
- 派生: [FB-76](./21_ユーザーフィードバック.md#fb-76)（無効化されるボタンが増えたのに、無効であることが見た目で伝わらない）

### FB-72

- 現象: 同じドメインエラーコードに**画面ごとの別文言**が当たっている。①`ended_before_started` — 打刻修正のクライアント側は「終了時刻は開始時刻より後にしてください」、サーバ側は「終了時刻が開始時刻より前になります」 ②`invalid_start_time` — ルーチン管理側は「開始想定時刻を HH:MM 形式で入力してください」、デイリー側は「開始想定時刻を HH:MM で入力してください」。どちらの経路を通るかで表示が変わるが、ユーザーから見れば同じ失敗
- 原因: 辞書が画面ごと・クライアント／サーバごとに分かれて写されている（[T-49](./23_技術改善バックログ.md#t-49)）。写した時点では一致していても、片方だけ直すと静かに割れる
- オーナー判断（2026-07-26）: ①は「**終了時刻は開始時刻より後にしてください**」に寄せる——**どう直せばよいかを告げる形**で、他の文言（「名前を入力してください」「見積もりは1分以上の整数で入力してください」）の指示形と揃うため。②は「**開始想定時刻を HH:MM 形式で入力してください**」に寄せる——「形式」が入ることで HH:MM が書式の例示だと読み取れるため。いずれも**サーバ側・デイリー側の文言が変わる**（＝表示が変わる）
- 反映先: 文言カタログは画面定義書に持たせない。**集約後の辞書と、その対応表を固定するテストを単一の正とする**（[T-49](./23_技術改善バックログ.md#t-49) が「良い形」と評価する `masters/_lib/action-result.ts` ＋ `action-result.test.ts` の先例に揃える）。画面定義書へ全文言を書くと「同じ規則を2か所に書かない」規約に反し、改訂のたびに食い違う
- 対応: T-49（辞書の集約）の中で実装する。**T-49 は本判断が無いと着手できない**——1本の辞書へ集約する以上、どちらかに寄せざるを得ないため
- 関連: [T-49](./23_技術改善バックログ.md#t-49)（実装の器） / [FB-71](#fb-71)（同じ辞書群の別の穴。**一緒に片付けるのが早い**）

### FB-68

- 現象: 未打刻タスク（`started_at` が NULL）で `B` または `F` を押すと、時刻入力欄が現れないまま**すべてのショートカットが無効になる**。`Esc` すら効かず、マウスで別のセルを開いて閉じるか再読み込みするまでキーボードが戻らない
- 原因: `use-daily-shortcuts.ts` の `case "b"/"f"` は打刻状態を見ずに `editing` を立てるが、`daily-list.tsx` の時刻入力欄は `task.startedAt !== null &&` の内側にあり**未打刻タスクでは描画されない**。一方フックは `if (editing !== null) return;` で**全ショートカットを止める**（[画面定義書01](../仕様/13_画面定義書/01_デイリーリスト.md) §6 / [共通](../仕様/13_画面定義書/00_共通.md) §3）。`editing` を解除できるのは `onEndEdit`（入力欄の blur・`Esc` かポップオーバーの `onClose`）だけなので、**発火源が存在しないまま無効状態が固定される**
- 対応方針: `requestEdit("startedAt"/"endedAt")` の側で打刻の有無を見て、無ければ `editing` を立てない（あわせて `daily-list.tsx` の `initialValue` の到達不能分岐2つも消える）
- 発見: T-39 第2バッチ②のテスト作成時。レビューでの「`initialValue` の `""` 側は到達可能では」という指摘をワーカーが検算し、到達不能＝**死んだ枝がガードの裏返しとして生じている**ことから判明した
- 関連: [FB-58](#fb-58) と修正箇所が同じ（`requestEdit` が打刻の有無を見ていない）ので**一緒に決めて一緒に直す**。ただし FB-58 は「入力欄は出るので `Esc` で戻れる」＝仕様の穴、本件は「戻れない」＝不具合で、害の大きさが違う

### FB-58

- 現象: 実行中タスク（`started_at` あり・`ended_at` なし）で `F` を押すと**空欄の終了時刻入力欄**が開き、そこへ入力すると実質的に「終了時刻だけ先に決める」ことになる
- 原因: [画面定義書01](../仕様/13_画面定義書/01_デイリーリスト.md) §6 は `B`/`F` を「開始時刻 / 終了時刻のインライン修正」としか書かず、実行中に使えるのが意図かどうか読み取れない（`B` は開始済みなら常に意味を持つので同列に扱えない）
- 詰める点: ①実行中は `F` を無効にするか、押せるが「終了時刻を入れたら完了扱いにする」か、現状どおり空欄編集を許すか ②無効にするなら未実行タスクの `B` も同じ扱いにするか（未実行で開始時刻だけ入るのも同型の状態）③打刻から状態を導出する設計（`ended_at` を入れた瞬間に完了になる）との整合
- 発見: T-39 第2バッチ②のテスト作成時。到達可能な状態のためテストは現実装を固定してある
- 関連: [FB-68](#fb-68)（未打刻タスクの `B`／`F` でキーボードがデッドロックする不具合）と修正箇所が同じ（`requestEdit` が打刻の有無を見ていない）ので**一緒に決めて一緒に直す**

### FB-78

- 現象: 未分類グループはリスト**先頭**に置かれる（[画面定義書01](../仕様/13_画面定義書/01_デイリーリスト.md) §3.2）ため、そこに未実行タスクが1件でもあると `C`（現在地へジャンプ）が常にその先頭タスクを選ぶ。打刻ループの最中に押しても「いまの時間帯の次にやるタスク」へ戻れず、**まだトリアージしていないインボックスへ飛ぶ**
- 原因: 「現在地」の規則（§5 = 実行中タスク、なければ**表示順で最初の未実行**）がフラットな表示順の先頭一致で、セクションを見ていない（`domain/task/selection.ts` の `currentTaskId` は `orderedTasks` しか受け取らない）。§4.2 規則 b は現在位置より前の未実行を現在位置の直後へ繰り下げるが、**未分類はその対象外**（インボックスは時刻経過で動かさない）なので、未分類の未実行は常に現在セクションより前に居座る
- オーナー要望（2026-07-28）: 現在地の探索を**現在セクション → 未分類 の順**に処理する。**終了打刻後の自動選択（F-211）の送り先も同じ順に揃える**（`C`・初期選択と規則を分けない）
- 詰める点: ①**探索順の完全な定義** — 現在セクション・未分類のどちらにも未実行が無いときにどうするか（以降のセクションを表示順にたどる＝現行の全体探索へ落とすか、選択を動かさないか）。現在セクションより前のセクションに未実行が残る状態も、規則 b が発火する前（表示・打刻の間）には起こりうる ②**「現在セクション」の定義をどちらに合わせるか** — §4.3 の「現在時刻を含むセクション」（時刻だけで決まる）か、§4.2 の「現在位置」（実行中タスクがあればその直後）か。§4.3 は両者を**あえて揃えていない**と明記しているので、どちらを引くかを書く必要がある ③**表示日が今日でないとき** — 現在セクションが定義できない（残り時間 F-110・F-121・§4.3 と同じ規律）ので、従来どおり表示順で最初の未実行に落とすか ④**F-211 の書き換え範囲** — 送り先を揃える（上のオーナー要望）ので、[要件定義書](../仕様/12_要件定義書.md) §5 F-211 の本文「送り先は表示順で最初の未実行タスクになる」と §5 の該当行も書き換わる。ただし F-211 は**楽観的更新の適用前スナップショット**を見る（`selectionAfterFinish` は実行中を無視して未実行だけを見る）ため、同じ探索順を共有しつつ「実行中を優先しない」差だけを残す形になる ⑤実行中タスクを最優先する部分（実行中があればそれを選ぶ）は不変でよいか ⑥要求軸の判定（[guide 手順1](./guide_21_ユーザーフィードバック.md)）は着手時に行う。N-04（キーボードで主要操作が完結）・F-211 の範囲に収まるか、新しい要求 ID を起こすか

### FB-80

- 現象: デイリーのセクション見出しの残り時間（F-110）が、**現在時刻より後に始まるセクション**で明らかにおかしい値になる。とくにその日の最後のセクションは、**枠の長さより大きい残り**が出ることがある
- 原因: [データモデル定義書](../仕様/14_データモデル定義書.md) §4.3 の式 `(セクション終了時刻 − now) − そのセクションの未完了見積もり` が、**そのセクションが始まる前の時間まで空きとして数えている**。現在時刻を含むセクションでは正しいが、まだ始まっていないセクションは常に「開始時刻 − 現在時刻」のぶんだけ過大になる。有効セクションは24時間を敷き詰める（§3.1）ため最後の枠は次の日界まで伸びており、そこで過大分と枠の長さが同時に最大になって最も壊れて見える。実装（`domain/task/projection.ts` の `sectionRemainingMinutes`）は条項どおりで、**式そのものの誤り**
- 再現（現在 10:30・各セクションに未実行60分が1件）: 午前 09:00–13:00 は `+1:30`（正しい）／午後 13:00–翌06:00 は `+18:30`（枠17:00 より大きい）
- オーナー判断（2026-07-28）: **積み上げ（F-120）を使う形に改める**。かつ**積み上げがセクション開始より前に到達したときはセクション開始まで待つ**（残りが枠を超えないこと・溢れが先のセクションへ波及することの両方を満たすため）。確定した式は §4.3 が正
- 発見: 2026-07-28、オーナーが本番で気づいた
- 関連: [データモデル定義書](../仕様/14_データモデル定義書.md) §4.3（式）/ [画面定義書01](../仕様/13_画面定義書/01_デイリーリスト.md) §3.2（表示条件・符号・色）/ [要件定義書](../仕様/12_要件定義書.md) F-110 / F-104・F-120（同じ積み上げ）

### FB-81

- 現象: [FB-80](./closed_21_ユーザーフィードバック.md#fb-80) で入れた積み上げにより、セクション見出しの残り時間（F-110）が**他のセクションのやり残しで動く**。ある見出しの数字が変わった原因がその行の外にあるため、読み解きに手間がかかる
- オーナー判断（2026-07-28）: **セクションごとに独立した値にする**。各見出しの数字は「その時間帯の予定と枠の対比」として単独で読めることを優先し、他のセクションの状況は持ち込まない。1日全体の見通し（遅れが後ろへ押していく様子）は終了予定時刻（F-104）と行ごとの予想開始時刻（F-120）が担う
- 対応方針: §4.3 の式から `到達時刻` の持ち越しを外し、`残り(S) = Sの終了時刻 − max(now, Sの開始時刻) − Sの未完了見積もり` とする。**FB-80 の核心だった `max` は残す**（まだ始まっていないセクションを現在時刻起点で測ると残りが枠の長さを超える、という不具合の本体はこちらが直しているため）。波及がなくなるので、アーカイブ済み・過去セクションを「残りは出さないが積む」と特別扱いする条項も不要になる
- 発見: 2026-07-28、FB-80 をマージした後にオーナーが本番で確認して判断
