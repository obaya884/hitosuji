# FB 着手手順（FB → 仕様書 → 実装）

- 対象: [ユーザーフィードバック管理簿](./21_ユーザーフィードバック.md)のエントリに着手するときの手順（起票の運用ルールは管理簿側にある）

FB は「画面の話」として書かれるため、**画面定義書だけ直して上位文書に反映し忘れる**事故が起きやすい（2026-07-20 に F-306 で発生。指摘を受けて是正）。着手時は必ず上から順に判定する。

## 手順1: 既存の要求（F-XXX / N-XX）に当てはまるか判定する

`docs/仕様/11_要求定義書.md` §6 を検索し、この FB が実現しようとしていることが**既存要求の範囲に収まるか**を確かめる。

- **収まる** → 手順2へ（要求定義書の変更は不要）
- **収まらない** → **要求定義書に新しい ID を起こす**（要求文と優先度のみを表に書く）。例: FB-10「ルーチン一覧のソート軸選択」は F-303「一覧・編集・有効/無効切替」に含まれないため F-306 を新設した
- **既存要求の優先度を上げ下げする** → 要求定義書の優先度列の値だけを差し替える

> **理由は表に書かず、要求定義書 §10 決定ログ（[log_11_要求定義書.md](../仕様/log_11_要求定義書.md)）へ日付付きで積む**（表を読める状態に保つため。CLAUDE.md「書き方の規約」）。要件定義書・画面定義書も同様に、各文書と同階層の `log_<文書名>.md` へ書く。

## 手順2: 要件定義書へ反映する

- 要求IDを**新設・優先度変更**したなら [要件バックログ](./22_要件バックログ.md) の該当レーン（確定・着手待ち／候補・見極め中／監視項目）へ反映する（旧「§3 のフェーズ表」は廃止。要件定義書 §3＝開発の現況は散文のみで個別ID一覧を持たない）
- §5 の該当節に、挙動の要件を1行以上書く（画面の詳細ではなく「何がどうなるか」）

> **その場で実装まで進めないなら、バックログ反映は必須**（2026-07-25 に漏れた）。仕様を確定して実装を後回しにすると、新設した要求IDはどの台帳にも載らないまま各定義書に埋もれる。FB管理簿は「対応中」で追えても、**未実装要求の一覧はバックログが正**（要件定義書 §3 は個別IDを持たない）ため、そこに無い要求は次の選出（`next-task`）で拾えなくなる。

## 手順3: 画面定義書へ反映する

- 対象画面の本文（表示要素・操作仕様）に詳細を書く
- ヘッダの「対応要求」行に要求IDを追記する
- 判断が分かれた点は**理由と日付**を添える（後から読んで再現できるように）

## 手順4: データモデル定義書（列やテーブルが増減する場合のみ）

## 手順5: 実装 → 管理簿の状態を更新

対応済みにするとき、**どの文書のどこに反映したか**を状態欄に書き、行を[完了記録](./closed_21_ユーザーフィードバック.md)へ移す。

## 完了チェック（docs 反映のコミット前に全項目を確認する）

1. **3階層を見たか** — 「要求定義書 → 要件定義書 → 画面定義書」を上から判定したか。画面定義書しか触っていないなら手順1を飛ばしていないか
2. **要求IDを新設・優先度変更したなら要件バックログへ載せたか**（手順2。実装を後回しにする場合は特に）
3. **未実装のまま止めるなら、その旨が読み取れるか** — 要件定義書・画面定義書の該当条項に `（未実装 / F-XXX）` を付けたか（実装済みの記述と混ざると、コードとの乖離をレビューで指摘できなくなる）
4. **FB管理簿の状態を更新したか** — 実装まで終えたなら「対応済み」＋反映先を書いて `closed_21` へ移す。仕様確定で止めるなら「対応中」＋確定内容と反映先を残す
5. **判断の経緯を `log_` へ積んだか** — 本文には現在の仕様だけを書く（CLAUDE.md「書き方の規約」）
