# 要件バックログ 決定ログ

- 対象: [要件バックログ](./22_要件バックログ.md)の運用ルールをなぜそう定めたか
- 本文には現在のルールだけを書き、経緯は本書へ日付順に積む（CLAUDE.md「書き方の規約」）
- フェーズ運用から状態台帳へ移行した経緯（2026-07-23）は[log_12_要件定義書](../仕様/log_12_要件定義書.md)が持つ（本書より前の判断のため）

## 2026-07-26 チェックボックス＋平文を表形式へ移した（索引と詳細には分けない）

**背景**: 台帳21・23 を「一覧（索引）＋詳細節」へ再構成した際、本書も同じ形にするか検討した。**分割は不要と判断**——51行・2,544字・11エントリで1エントリが1行に収まり、全体が1画面で読める。21 が抱えた「1セルが1,000字を超えて表が壊れる」問題が存在せず、分けると参照が増えるだけになる。

**しかし別の問題があった**（オーナーの指摘）。1行の中身は実際には6つのフィールドが平文に埋まっているだけで、構造は既にあった。

```
- [ ] **F-118 タイトル** `[UI未詰め]` — 要約。トリガ: 条件。要件 §5.1 / 要求 §6.1
       └ ID  └ タイトル      └ 熟度        └ 内容    └ トリガ      └ 参照
```

**決定**: この6フィールドを列に開き、レーンごとの表にする。狙いは見た目ではなく**記入の強制と機械検査**。

- **トリガ欄を必須にできる**のが最大の利得。平文の頃は「トリガ: …」を書かなくても書式上は成立し、実際 F-404 は内容が無いまま、他も書式が揺れていた。**トリガの無いエントリは `next-task` の選出で永久に拾われない**（着手条件の達成判断がオーナー任せなので、条件が書かれていなければ候補にすら挙がらない）——最も静かに効く欠落なので、機械で押さえる価値が高い
- **熟度タグの語彙を検査できる**。実際に `[UI未詰め]` という宣言外のタグが1件あった（宣言は仕様済／設計済／列済／未詰めの4つ）。UI が未詰めであることは内容欄が既に述べているので未詰めへ正規化した。台帳23 でも同種の語彙ドリフト（種別4種の宣言に対し実際は8種、優先度に未宣言の `低`）が同時に見つかっており、**「宣言した語彙が本文と食い違う」は表にした瞬間に露出する**という共通の教訓
- **`[…]` の角括弧とコード装飾は外した**（オーナー指示）。平文の行中では他の語と区別する印が要ったが、列になれば位置そのものが区別を担う——**表にしたことで不要になった装飾**であり、残すと語彙検査の文字列も無駄に長くなる
- **チェックボックス `- [ ]` は落とした**。完了時に `closed_22` へ移す運用のため常に未チェックで、情報を持っていなかった

**索引と詳細に分けない代わりの歯止め**: 詳しく書きたくなったら、それは要件定義書へ書く合図とする（本書は一行の要約に留める、という既存の規律の言い換え）。

## 2026-07-26 熟度の意味を「仕様の熟れ具合」から「着手時にオーナー判断が要るか」へ変え、判定を docs の実体に紐づけた

**背景**: オーナーの実感「UI が詰まっていなくて着手後に確認していたパターンが多かった」を、完了済み4件で検算したところ**そのとおりだった**。

| ID | 完了時の熟度 | 着手時に実際に決めたこと | 決めた場所 |
|---|---|---|---|
| F-117 | 仕様済（**起票時から**） | 開き方（クリック＋`G`）・週の起点=月曜・月移動は前月/翌月のみ・カレンダー内のキー操作 | FB-39 |
| F-120 | 仕様済 | 導出の起点・見積もり無しの扱い・実行中/完了行での表示可否・割り込み時の再計算 | FB-47 |
| F-212 | 仕様済 | 戻す先・表示位置・`U` と O-13 の切り分け・undo の undo | FB-41 |
| F-121 | 仕様済 | 色トークン・強調手段・判定規律・日界回転・再描画契機 | FB-52 |

**4件とも着手時に FB（要仕様整理）で UI を決めている**。さらに重要なのは内訳で、F-120・F-212・F-121 は**仕様が決まった後に台帳へ書かれている**——`仕様済` は予測ではなく事後記録だった。素で予測に使われたのは F-117 だけで、**それは外れている**（起票時から仕様済だったのに、着手時に UI をまるごと決めた）。つまり**旧定義の熟度は一度も予測として機能していない**。

**原因**: `仕様済`＝「仕様が固まっている」という定義が、書き手にとって「要求として何をやるかは決まっている」と読めた。要求は決まっていても操作仕様は白紙、という状態がこの語に吸い込まれる。

**決定**: 熟度の意味を**「着手時にオーナーの仕様判断が要るか／着手したらどこから始まるか」**へ変え、判定条件を**参照先 docs の実体**に紐づけた（本文の判定表）。感覚ではなく「参照先を開いて確かめる」操作で決まるようにするのが眼目。

**訂正**: この基準で現存11件を当て直し、**F-108 を仕様済 → 未詰め**へ。参照先の画面定義書01 O-10 は `（未実装 / F-108 Could）` 付きの1行で、候補の出し方・キー操作・マッチ規則・クイック追加の `Enter` との干渉が何も書かれていない。対照的に F-506（仕様済のまま）は画面定義書04 §3.1・§3.3 に期間切替の UI と週・月表示の列追加が書かれており、条項だけで実装の判断がつく。F-119（設計済＝検討31 が実在）・F-206（列済＝`comment` 列が schema に実在）も裏付けを確認した。

**機械化**: `（未実装 / F-XXX）` は guide_21 の完了チェック3 が付ける「条項はスタブ」の印なので、**熟度が仕様済なのに参照先がその印を持つ行を `ledger:check` が落とす**ようにした。この過大申告は静かに起きる（F-117 は誰も気づかないまま2日間 `仕様済` だった）ので、感覚に頼らず機械で見る。ただし網は完全ではない——スタブ記法自体が現状 docs 全体で1か所しか使われておらず、**印が付いていないスタブは検出できない**。判定表の「参照先を開いて確かめる」が本体で、検査はその補助。

**closed_22 は書式を変えない**。完了記録は `## F-XXX タイトル（完了日）`＋対応・反映先の節形式のままとする——完了記録は「何をどう決めて何に反映したか」を残す文書で、バックログの一行要約とは持つべき情報が違う。したがって 22 には `ledger:move` を用意しない（行→節の書き下ろしは機械化できない）。台帳21・23 が移動をスクリプト化しているのと非対称だが、これは意図した非対称。
