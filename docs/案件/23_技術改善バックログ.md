## この文書の守備範囲

プロダクトの**挙動**に関わる変更は扱わない（それは要求 → 要件 → 画面/データモデルの軸で、着手前に該当文書を先に直す）。ここに書くのは、ユーザーから見た挙動を変えずに**開発の健全性を上げる活動**——依存追随・CI/ツール整備・内部設計の改善・テスト補強・調査など。

- 採番は **T-XX**（Technical）。1系列で通し、種別で区別する
- 種別: `負債返済` / `改善` / `ツール整備` / `調査`
- 優先度: `高` / `中` / `様子見`
- 状態: `未着手` / `進行中` / `完了` / `保留`
- **完了になったエントリは、状態更新と同じコミットで[closed_23_技術改善バックログ.md](./closed_23_技術改善バックログ.md)へ移す**（本書には未着手・進行中・保留だけを残す）
- 判断の経緯は本文に書かず、[log_23_技術改善バックログ.md](./log_23_技術改善バックログ.md) へ日付順に積む（CLAUDE.md「書き方の規約」に従う）
- リファクタ観点の棚卸しは `refactor-scout`（読み取り専用サブエージェント）が T-XX 案のドラフトを起票し、オーナー確認のうえメインセッションが本書へ記入する（CLAUDE.md「起動の契機」参照）

- 背景: `eslint-config-next` 同梱の `eslint-plugin-react` が ESLint 10 で削除された context API（`getFilename`）を使っており、eslint 10 では lint がクラッシュして起動しない（依存方向を守らせる `no-restricted-imports` すら実行不可）。Dependabot PR #4 はこの理由でクローズした
- 対応方針: `eslint-config-next` が ESLint 10 対応版を出したら再挑戦する。それまでは 9 系を維持。次に Dependabot が eslint の新版 PR を出したときに状況を再確認する

## T-05 esbuild dev-serve アラート（dismiss 済み・追跡）

- 種別: 負債返済 / 優先度: 様子見 / 状態: 保留（dismiss 済み）
- 背景: Dependabot セキュリティアラート（medium）。`drizzle-kit@0.31.10（最新）→ @esbuild-kit/esm-loader → esbuild@0.18` 経由。脆弱箇所は esbuild の dev serve が任意オリジンからの要求に応じる件だが、drizzle-kit は @esbuild-kit を設定ファイル変換にしか使わず dev serve を起動しない**到達不能パス**。最新 drizzle-kit でも @esbuild-kit を同梱しており上流にクリーンな修正が無い
- 対応: 理由 `not_used` でアラートを dismiss（`overrides` で esbuild を 0.25+ に上げると @esbuild-kit（0.18 前提）が壊れ、かつ CI で検出できないため見送り）
- 根治条件: drizzle-kit が @esbuild-kit を外す（または esbuild を上げる）版を出したとき。次に esbuild 系のアラート／更新が来たら再確認する

## T-25 データバックアップの自動化（暗号化確定・保存先2案は保留）

- 種別: ツール整備（当初は調査）/ 優先度: 中 / 状態: 未着手（暗号化方式は確定・保存先は保留）
- 背景: N-06 のバックアップ取得は手動（週次目安）で、取り忘れた期間はどこにも退避が無く Neon の PITR/履歴保持の窓を超えると復元不能になる。GitHub Actions cron で定期取得を自動化し取得漏れをなくしたい（README・要件定義書 §6 とも「運用の負担を見て判断」に留めていた）
- 方式: 難所は「取得の実行」ではなく **public リポジトリで実データを含むダンプをどこへどう置くか**。これを (1) 暗号化 (2) 保存先 に分解し、**`age` 非対称暗号（公開鍵はコミット可・復号鍵は CI に載せない）で秘匿を保存先に依存させない**設計に**確定**。保存先はクラウドオブジェクトストレージを前提に **案B（Cloudflare R2 / Backblaze B2・静的キー）と案C（AWS S3 / GCP GCS・OIDC/WIF で静的キーレス）を併記し、採用は保留**（両クラウド未保有につき、課金アカウントを作る段で B/C を確定）。差は CI 認証とセットアップの重さで機能・コスト差は極小データではほぼ無い。**詳細は [33_データバックアップ自動化検討.md](../検討/33_データバックアップ自動化検討.md) が正**
- 実装: 未着手（本 T は方式決定まで）。着手する場合は age 鍵ペア・`BACKUP_DATABASE_URL`（unpooled）シークレット・保存先（案B＝バケット＋静的キー／案C＝バケット＋OIDC/WIF 設定）・lifecycle rule・`.github/workflows/db-backup.yml`（`schedule`＋`workflow_dispatch`／`pg_dump`→age→upload／失敗通知）を用意する（検討ドキュメント §5・§7）。定期実行のため**承認ゲートは付けず**「非 PR イベント限定＋最小権限＋失敗通知」で担保する
- 着手条件: 手動運用の取得漏れが実害になり始めた／週次取得の手間を恒常的に感じるとき

## T-31 `updated_at` 比較に依存する統合テストの flaky 解消

- 種別: 改善（テスト補強）/ 優先度: 中 / 状態: 未着手
- 背景: `src/infrastructure/db/repositories/drizzle-section-repository.int.test.ts` の更新系テストが低頻度で落ちる（`expected <挿入時の updated_at> to be greater than or equal to <更新後の updated_at>`。再実行では緑）。原因は**時刻源が2つある**こと——挿入時の `updated_at` は DB の `now()`、更新時はアプリの `new Date()` で、コンテナとホストの時計が 1ms 単位で前後しうる。テスト内のコメントは「同一ミリ秒で等値になりうる」ケースだけを想定しており、逆方向のずれ（更新後が挿入時より前になる）を見落としている
- 対応方針: 時刻の**大小関係に依存しない検証**へ替える（更新後の `updated_at` が非 null であること・更新前の値と異なることなど）。同じ比較を持つ他のリポジトリの統合テストも横断して洗う。時刻源そのものを片方へ寄せる（更新も DB の `now()` にする）のは挙動に触るため本 T の範囲外
- 着手条件: 即（CI の偽陽性は並行開発でマージ判断のノイズになるため後回しにしない）
- 発見: F-212 実装時の `test-reviewer` レビュー（2026-07-25）。F-212 の差分とは無関係の既存問題
