- 関連文書: [アーキテクチャ定義書](../仕様/15_アーキテクチャ定義書.md)（設計・テスト戦略）/ [要件バックログ](./22_要件バックログ.md)（プロダクト軸の台帳）

## この文書の守備範囲

プロダクトの**挙動**に関わる変更は扱わない（それは要求 → 要件 → 画面/データモデルの軸で、着手前に該当文書を先に直す）。ここに書くのは、ユーザーから見た挙動を変えずに**開発の健全性を上げる活動**——依存追随・CI/ツール整備・内部設計の改善・テスト補強・調査など。

- 採番は **T-XX**（Technical）。1系列で通し、種別で区別する
- 種別: `負債返済` / `改善` / `ツール整備` / `調査`
- 優先度: `高` / `中` / `様子見`
- 状態: `未着手` / `進行中` / `完了` / `保留`
- **完了になったエントリは、状態更新と同じコミットで[closed_23_技術改善バックログ.md](./closed_23_技術改善バックログ.md)へ移す**（本書には未着手・進行中・保留だけを残す）
- 判断の経緯は本文に書かず、[log_23_技術改善バックログ.md](./log_23_技術改善バックログ.md) へ日付順に積む（CLAUDE.md「書き方の規約」に従う）
- リファクタ観点の棚卸しは `refactor-scout`（読み取り専用サブエージェント）が T-XX 案のドラフトを起票し、オーナー確認のうえメインセッションが本書へ記入する（CLAUDE.md「起動の契機」参照）

## T-02 eslint 10 への追随（保留）

- 種別: 負債返済 / 優先度: 様子見 / 状態: 保留
- 背景: `eslint-config-next` 同梱の `eslint-plugin-react` が ESLint 10 で削除された context API（`getFilename`）を使っており、eslint 10 では lint がクラッシュして起動しない（依存方向を守らせる `no-restricted-imports` すら実行不可）。Dependabot PR #4 はこの理由でクローズした
- 対応方針: `eslint-config-next` が ESLint 10 対応版を出したら再挑戦する。それまでは 9 系を維持。次に Dependabot が eslint の新版 PR を出したときに状況を再確認する

## T-05 esbuild dev-serve アラート（dismiss 済み・追跡）

- 種別: 負債返済 / 優先度: 様子見 / 状態: 保留（dismiss 済み）
- 背景: Dependabot セキュリティアラート（medium）。`drizzle-kit@0.31.10（最新）→ @esbuild-kit/esm-loader → esbuild@0.18` 経由。脆弱箇所は esbuild の dev serve が任意オリジンからの要求に応じる件だが、drizzle-kit は @esbuild-kit を設定ファイル変換にしか使わず dev serve を起動しない**到達不能パス**。最新 drizzle-kit でも @esbuild-kit を同梱しており上流にクリーンな修正が無い

- 根治条件: drizzle-kit が @esbuild-kit を外す（または esbuild を上げる）版を出したとき。次に esbuild 系のアラート／更新が来たら再確認する

## T-06 worktree を活用した AI 並行開発体制（体制案は検討済み）

- 種別: 改善（開発体制）/ 優先度: 中 / 状態: 未着手（体制案・通信方式は検討済み。採用判断と実装は着手条件待ち）
- 背景: 現状は単一ワークツリー・単一セッションで作業しており、別タスクが並行すると変更が交錯する。実際、別セッションで進行中だった作業（`docs/案件/21_ユーザーフィードバック.md` ほかの WIP）を中断・除外して本作業を進める必要が生じた。複数の作業を安全に並行させる仕組みが無い
- 目標: `git worktree` でタスクごとに独立したワークツリー／ブランチを持たせ、AI が複数タスクを並行実行できるようにする。それらを束ねる**ヘッドエージェント（オーケストレータ）**がタスク分配・進捗統合・レビュー/検証の集約とマージ順序の調停を担う
- 方式: 体制は**ヘッド1＋ワーカーN の2階層**（ヘッドはコードを編集しない／ワーカーは worktree の外に出ない）。統合は PR＋CI（T-01）に乗せ、マージ順序はヘッドが逐次調停する。通信機構は**サブエージェント（worktree 分離＋SendMessage 継続）を採用**し、Agent Teams（実験的機能）は再検討条件付きで見送り。DB 分離は Phase 1 では「ワーカーのローカル検証は unit まで・統合テストは CI に委ねる」で整備ゼロ開始、スキーマ変更タスクは常に最大1本。**本番反映はオーナーの合図**の規律を維持しヘッドにも自動マージ権を与えない。**詳細は [34_AI並行開発体制検討.md](../検討/34_AI並行開発体制検討.md) が正**
- 着手条件: 並行させたいタスクが実際に複数たまったとき（体制だけ先に作らない）。着手時は CLAUDE.md「サブエージェント運用」節の改訂から行う（検討ドキュメント §6）
- 関連: [CLAUDE.md](../../CLAUDE.md)「サブエージェント運用」節 / [完了記録](./closed_23_技術改善バックログ.md) T-01（CI 基盤）

## T-19 Shift+J/K のアーカイブ済みセクション境界で楽観更新とサーバ確定がずれうる

- 種別: 調査 / 優先度: 中 / 状態: 未着手
- 背景: T-11 のレビュー（spec-reviewer）で判明した既存の潜在論点。Shift+J/K の移動先算出で、サーバ側 `src/usecases/task/reorder-usecases.ts` の `moveTaskByOneStep` が組み立てる `sectionOrder` は `activeSections`（アーカイブ済みを除外）だが、presentation 側 `daily-board.tsx` の `sectionOrder` は `optimisticGroups` 由来で、当日タスクが属するアーカイブ済みセクション（画面定義書01: 当日タスクがある場合のみ表示）を含みうる。タスクがアーカイブ済みセクションに属し、その境界を跨ぐ Shift+J/K を行うと、client は移動先ありと判断するがサーバは `indexOf === -1` で「動かさない」と判定し、楽観更新が巻き戻りうる。**T-11 前後で挙動は同一**（旧 `moveByStep` も `optimisticGroups` 由来）＝ T-11 が生んだ回帰ではない既存の潜在事項
- 対応方針: まず再現条件と実害（巻き戻りの体感・データ不整合の有無）を切り分ける調査から。修正するならサーバ／client の `sectionOrder` の定義を揃える（アーカイブ済みでも当日タスクを持つセクションを両者に含める等）。**修正は表示・並び挙動を変えるため、着手時は要求軸（要件定義書・画面定義書01）を先に判断する**（本書の守備範囲外＝挙動が絡む）

## T-20 `npm run test:coverage` の `.tmp` 削除競合で Unhandled Rejection

- 種別: 負債返済 / 優先度: 様子見 / 状態: 未着手
- 背景: T-11/T-12 の検証（verifier）で判明した既存の設定負債。`test:coverage` が unit と integration の2プロジェクトを同一 `coverage.reportsDirectory` で並行実行するため、片方のクリーンアップがもう片方の `coverage/.tmp` を削除する競合が起き `ENOENT`（Unhandled Rejection）がログに出る。プロセスの exit code は 0 のため CI 上は成功扱いだが、ログにエラーが残る。**main でも再現**する既存事項（今回の変更と無関係）。`npx vitest run --coverage --project unit` 単体では正常完走する
- 対応方針: `vitest.config.ts` の coverage 出力先をプロジェクトごとに分ける、または `test:coverage` を unit → integration の逐次実行にする。挙動（プロダクト）に影響しないツール整備

## T-25 データバックアップの自動化（暗号化確定・保存先2案は保留）

- 種別: ツール整備（当初は調査）/ 優先度: 中 / 状態: 未着手（暗号化方式は確定・保存先は保留）
- 背景: N-06 のバックアップ取得は手動（週次目安）で、取り忘れた期間はどこにも退避が無く Neon の PITR/履歴保持の窓を超えると復元不能になる。GitHub Actions cron で定期取得を自動化し取得漏れをなくしたい（README・要件定義書 §6 とも「運用の負担を見て判断」に留めていた）
- 方式: 難所は「取得の実行」ではなく **public リポジトリで実データを含むダンプをどこへどう置くか**。これを (1) 暗号化 (2) 保存先 に分解し、**`age` 非対称暗号（公開鍵はコミット可・復号鍵は CI に載せない）で秘匿を保存先に依存させない**設計に**確定**。保存先はクラウドオブジェクトストレージを前提に **案B（Cloudflare R2 / Backblaze B2・静的キー）と案C（AWS S3 / GCP GCS・OIDC/WIF で静的キーレス）を併記し、採用は保留**（両クラウド未保有につき、課金アカウントを作る段で B/C を確定）。差は CI 認証とセットアップの重さで機能・コスト差は極小データではほぼ無い。**詳細は [33_データバックアップ自動化検討.md](../検討/33_データバックアップ自動化検討.md) が正**
- 実装: 未着手（本 T は方式決定まで）。着手する場合は age 鍵ペア・`BACKUP_DATABASE_URL`（unpooled）シークレット・保存先（案B＝バケット＋静的キー／案C＝バケット＋OIDC/WIF 設定）・lifecycle rule・`.github/workflows/db-backup.yml`（`schedule`＋`workflow_dispatch`／`pg_dump`→age→upload／失敗通知）を用意する（検討ドキュメント §5・§7）。定期実行のため**承認ゲートは付けず**「非 PR イベント限定＋最小権限＋失敗通知」で担保する
- 着手条件: 手動運用の取得漏れが実害になり始めた／週次取得の手間を恒常的に感じるとき
- 関連: [完了記録](./closed_23_技術改善バックログ.md) T-22（スキーマ更新のリモート化・同型の作業場）/ [README](../../README.md)「バックアップ（N-06）」/ [データモデル定義書](../仕様/14_データモデル定義書.md) §6

## T-26 git/ブランチ戦略の全体設計（T-06 と統合）

- 種別: 調査 / 優先度: 中 / 状態: 未着手（**意図の起票のみ**）
- 背景: git/ブランチ運用に明文規定がなく、実態は `main` 直コミットと PR（#16/#27 等）が混在。`main` への push＝本番デプロイ（Vercel）という制約の下で、変更の種類ごとの扱いを一貫させたい。並行開発（複数 worktree）まで見据えると、マージ順序の調停・スキーマ変更の直列化を扱う T-06「AI並行開発体制」と不可分であり、**両者を1つの設計として束ねる**。
- 方式（着手時に詰める）: (1) リスク別ルーティング（docs/低リスク＝main 直コミット／コード・挙動＝ブランチ＋CI＋プレビュー→合図でマージ／スキーマ＝T-22 のマイグレーション先行）、(2) push＝デプロイのオーナー合図規律の粒度、(3) 並行化の運用（ブランチ命名・マージ順序・スキーマ変更は常に最大1本・CI を統合ゲートに）。まとめ先は CLAUDE.md、長くなるなら専用検討ドキュメント。設計は [34_AI並行開発体制検討.md](../検討/34_AI並行開発体制検討.md)（T-06）と統合する
- 着手条件: 並行開発を実際に始める前、または現行の混在運用が実害になったとき
- 暫定運用: 確定までは軽微・docs 変更は `main` 直コミットで進める（オーナーの従来運用に合わせる）
- 関連: 本書 T-06（AI並行開発体制）/ [完了記録](./closed_23_技術改善バックログ.md) T-22（本番スキーマ更新パイプライン）/ [CLAUDE.md](../../CLAUDE.md)「このリポジトリは public」「本番マイグレーションの手順」

## T-29 postgres 18 系への追随（本番 Neon の移行と同時・保留）

- 種別: 負債返済 / 優先度: 様子見 / 状態: 保留
- 背景: 本番 Neon が PostgreSQL 17 系のため、ローカル開発DB・統合テストDBだけ 18 に上げると統合テストが本番と別メジャーで通ることになる。加えて postgres 18 の公式イメージは既定 PGDATA が `/var/lib/postgresql/18/docker` へ変わり、`/var/lib/postgresql/data` にマウントした既存の `db-data` ボリューム（17 で初期化）はそのままでは使えない。Dependabot PR #29（`docker-compose.yml` の 17-alpine → 18-alpine）はこの理由でクローズした
- 対応方針: 本番 Neon を 18 へ移すのと**同じ作業として一括で行う**。散在する4か所 — `docker-compose.yml`（db / db-test）・`.github/workflows/ci.yml`（統合テストの service コンテナ）・`scripts/db-backup.sh`（`pg_dump` クライアント）・[README](../../README.md)「バックアップ（N-06）」 — を1コミットで更新し、あわせて `db-data` のマウント先を `/var/lib/postgresql` へ変更してローカルDBは作り直す（開発データのみ）。本番の移行手順は N-06 のバックアップ資産をそのまま使う: ①`db-backup.sh` のクライアントを先に 18 へ（サーバより古いクライアントでは dump できない）→ ②現行17から dump → ③18 の新プロジェクトへ restore → ④`DATABASE_URL` 差し替え
- 着手条件: **Neon の PostgreSQL 18 が preview を抜け、かつ別件で本番DBを作り直す機会が来たとき**（Neon はメジャーの in-place アップグレード・`pg_upgrade` に未対応で、上げるには 18 で新プロジェクトを作りデータを移す＝接続文字列も変わる。単体で踏むには重く、どうせ作り直すタイミングに乗せると移行コストがほぼ消える）。PG17 のコミュニティ EOL は 2029-11 で期限起点の契機は遠い。次に Dependabot が postgres の新版 PR を出したときに Neon 側の状況を再確認する
- 補足: docker-compose エコシステムの Dependabot は `ci.yml` の service コンテナを見ないため、compose だけが単独で上がる PR が今後も来る。緑の `verify` はこの変更を検証していない（CI は自前の 17 ピンで走る）
- 関連: 本書 T-02（同型の「上流待ちで保留」）
