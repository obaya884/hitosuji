# 技術改善バックログ

- 作成日: 2026-07-22（改称: 2026-07-23、旧「技術改善計画」）
- 目的: 技術負債の返済・リファクタリング・開発ツール整備など、**プロダクト挙動を変えない技術活動**を、要求（F-XXX / N-XX）とは別軸で管理・計画する
- 関連文書: [アーキテクチャ定義書](../仕様/15_アーキテクチャ定義書.md)（設計・テスト戦略）/ [要件バックログ](./22_要件バックログ.md)（プロダクト軸の台帳）

## この文書の守備範囲

プロダクトの**挙動**に関わる変更は扱わない（それは要求 → 要件 → 画面/データモデルの軸で、着手前に該当文書を先に直す）。ここに書くのは、ユーザーから見た挙動を変えずに**開発の健全性を上げる活動**——依存追随・CI/ツール整備・内部設計の改善・テスト補強・調査など。

- 採番は **T-XX**（Technical）。1系列で通し、種別で区別する
- 種別: **何に触るか＝着手時に何が網になるか**で分ける（下表）。「負債返済」「改善」のような**本書の全件に当てはまる語は使わない**（種別として情報量がない）
- 優先度: `高` / `中` / `低` / `様子見`
- 状態: `未着手` / `進行中` / `完了` / `保留`
- **1エントリ ＝ [一覧](#一覧)の1行 ＋ [詳細](#詳細)の1節**（台帳21 と同じ書式）。一覧は索引に徹し `ID / タイトル / 種別 / 優先度 / 状態 / 詳細` の6列を持つ
  - **見出しは `### T-XX` の ID のみ**。タイトルを重ねると改題のたびにアンカーが壊れ、一覧との二重管理にもなる
  - **セル内に `|` を書かない**（`ledger:move` / `ledger:check` が列を数えられなくなる）。型を示すときは「未指定・`null`・空配列」のように語で書く
  - **種別・優先度・状態を詳細節に書かない**。一覧が正（二重に持つと必ず食い違う）
  - 詳細節の項目は `背景`（必須）に続けて `対応方針` / `着手条件` / `優先度の根拠` / `関連` を必要なだけ。エントリ固有の項目（`方式` `実害` `範囲` など）を足してよいが、上の5語を優先して使う
  - 詳細節の並び順は一覧と同じにする
- **完了になったエントリは、状態更新と同じコミットで[closed_23_技術改善バックログ.md](./closed_23_技術改善バックログ.md)へ移す**（本書には未着手・進行中・保留だけを残す）。**一覧の行と詳細節はセットで移す** — `npm run ledger:move -- T-XX` が両方を移す
- 判断の経緯は本文に書かず、[log_23_技術改善バックログ.md](./log_23_技術改善バックログ.md) へ日付順に積む（CLAUDE.md「書き方の規約」に従う）
- リファクタ観点の棚卸しは `refactor-scout`（読み取り専用サブエージェント）が T-XX 案のドラフトを起票し、オーナー確認のうえメインセッションが本書へ記入する（CLAUDE.md「起動の契機」参照）

### 種別

| 種別 | 何に触るか | 着手時に何が網になるか |
|---|---|---|
| 内部設計 | `src/` の構造（挙動不変） | 既存テスト。**変異させて振る舞い保存を確かめる** |
| 型安全 | 型定義（挙動不変） | コンパイラ。追加漏れがビルドエラーになる形へ寄せるのが目的 |
| テスト | テストコードのみ（本番コード不変。補強も整理も含む） | 本番コードに触れないので回帰の心配がない |
| ツール整備 | `scripts` / CI / 開発環境 | **自動テストの網が無い**。実行して確かめる |
| 依存追随 | 依存パッケージの更新・脆弱性対応 | 上流待ちが多く自分では動かせない。**再確認の契機を必ず書く** |
| 調査 | 何も変えない。判断を記録する | 成果物は決定そのもの |

## 詳細

### T-02

- 背景: `eslint-config-next` 同梱の `eslint-plugin-react` が ESLint 10 で削除された context API（`getFilename`）を使っており、eslint 10 では lint がクラッシュして起動しない（依存方向を守らせる `no-restricted-imports` すら実行不可）。Dependabot PR #4 はこの理由でクローズした
- 対応方針: `eslint-config-next` が ESLint 10 対応版を出したら再挑戦する。それまでは 9 系を維持。次に Dependabot が eslint の新版 PR を出したときに状況を再確認する

### T-03

- 背景: テストピラミッドの頂点。現状は手動の実運用確認で代替している（[アーキテクチャ定義書](../仕様/15_アーキテクチャ定義書.md) §8）。プロダクト要求（F-XXX / N-XX）には乗らない技術活動のため、実装計画 Phase 3 に置かれたまま行き場がなかったのを本書へ移した
- 対応方針: 必要性を運用で見極めてから、導入するなら Playwright。手動確認では追えない回帰が出てきた等を着手条件にする
- **導入時に最初に片付ける宿題: FB-42 の再現条件の特定**（T-39 第2バッチで判明）。FB-42（ポップオーバーで確定した `Enter` が背後の打刻へ抜ける）は `select-popover.tsx` の `stopPropagation` が防いでいるが、**コンポーネントテスト（jsdom）ではその盾が効いているかを合成側で観測できない**——`daily-board` 経由だと `setEditing(null)` が React の自動バッチで同一 dispatch 中に反映されず、`use-daily-shortcuts` 側の `editing` ガードだけで防げてしまうため、`stopPropagation` を外しても緑のまま（変異で実測）。部品単体では固定できている（`select-popover.test.tsx` が `window` に裸のリスナを張り `document` で発火する形）が、**FB-42 が現場で再現した「再レンダーとリスナー再登録の隙間」を段3で何を再現すれば捉えられるかは未特定**。ブラウザ段の最初の題材としてここから着手する

### T-05

- 背景: Dependabot セキュリティアラート（medium）。`drizzle-kit@0.31.10（最新）→ @esbuild-kit/esm-loader → esbuild@0.18` 経由。脆弱箇所は esbuild の dev serve が任意オリジンからの要求に応じる件だが、drizzle-kit は @esbuild-kit を設定ファイル変換にしか使わず dev serve を起動しない**到達不能パス**。最新 drizzle-kit でも @esbuild-kit を同梱しており上流にクリーンな修正が無い
- 対応: 理由 `not_used` でアラートを dismiss（`overrides` で esbuild を 0.25+ に上げると @esbuild-kit（0.18 前提）が壊れ、かつ CI で検出できないため見送り）
- 根治条件: drizzle-kit が @esbuild-kit を外す（または esbuild を上げる）版を出したとき。次に esbuild 系のアラート／更新が来たら再確認する

### T-25

- 背景: N-06 のバックアップ取得は手動（週次目安）で、取り忘れた期間はどこにも退避が無く Neon の PITR/履歴保持の窓を超えると復元不能になる。GitHub Actions cron で定期取得を自動化し取得漏れをなくしたい（README・要件定義書 §6 とも「運用の負担を見て判断」に留めていた）
- 方式: 難所は「取得の実行」ではなく **public リポジトリで実データを含むダンプをどこへどう置くか**。これを (1) 暗号化 (2) 保存先 に分解し、**`age` 非対称暗号（公開鍵はコミット可・復号鍵は CI に載せない）で秘匿を保存先に依存させない**設計に**確定**。保存先はクラウドオブジェクトストレージを前提に **案B（Cloudflare R2 / Backblaze B2・静的キー）と案C（AWS S3 / GCP GCS・OIDC/WIF で静的キーレス）を併記し、採用は保留**（両クラウド未保有につき、課金アカウントを作る段で B/C を確定）。差は CI 認証とセットアップの重さで機能・コスト差は極小データではほぼ無い。**詳細は [33_データバックアップ自動化検討.md](../検討/33_データバックアップ自動化検討.md) が正**
- 実装: 未着手（本 T は方式決定まで）。着手する場合は age 鍵ペア・`BACKUP_DATABASE_URL`（unpooled）シークレット・保存先（案B＝バケット＋静的キー／案C＝バケット＋OIDC/WIF 設定）・lifecycle rule・`.github/workflows/db-backup.yml`（`schedule`＋`workflow_dispatch`／`pg_dump`→age→upload／失敗通知）を用意する（検討ドキュメント §5・§7）。定期実行のため**承認ゲートは付けず**「非 PR イベント限定＋最小権限＋失敗通知」で担保する
- 着手条件: 手動運用の取得漏れが実害になり始めた／週次取得の手間を恒常的に感じるとき
- 関連: [完了記録](./closed_23_技術改善バックログ.md) T-22（スキーマ更新のリモート化・同型の作業場）/ [README](../../README.md)「バックアップ（N-06）」/ [データモデル定義書](../仕様/14_データモデル定義書.md) §6

### T-37

- 背景: presentation は自動テストの対象外（[アーキテクチャ定義書](../仕様/15_アーキテクチャ定義書.md) §8）のため、UI の挙動はオーナーの動作確認だけが網になっている。2026-07-25 に FB-51 で **Playwright による実機測定が2回とも決定的だった**——①「画面下部でポップオーバーが上向きに反転しない」の原因は、コードを読んで立てた仮説3つ（アンカーが想定外の祖先／実は反転不要／sticky ヘッダ未考慮）が**すべて外れ**で、測って初めて「アクティブ候補の `scrollIntoView({block:"nearest"})` が祖先＝ドキュメントまでスクロールし、反転判定が見る幾何情報を書き換えていた」と分かった ②修正後も測定で「ページのスクロール量0・パネル内だけが動く・上向きを維持」を確認できた。手作業で都度組むのは惜しい
- 方式の推し: **サブエージェント**（CLAUDE.md のレビュアー表に1行増える形。`verifier` が機械的検証、`spec-reviewer` が docs 整合、という既存の責務の切り方と揃う）。スキルにするとメインセッションが手順を踏む形になり、長いブラウザ操作でコンテキストを消費する
- 先に決めるべき論点:
  - **判定対象の線引き**: 幾何・スクロール量・クラスの有無・キーナビの追従・コンソールエラーの不在など**機械的に真偽が決まるもの**に限る。「色が見づらい」「2行になって気になる」は知覚の判断で代替できない（FB-52 の色・FB-51 のラベル折り返しはいずれもオーナーの実機知覚で決まった）。ここを曖昧にすると「確認したことになっている」状態を作る
  - **実データを壊さない担保**: 破壊的操作（打刻 `B`/`F`・削除 `D`・複製 `Y`）を禁じるか、専用の開発DBに向けるか。後者は **T-34 の「どのDBを向けるか」と同じ論点**に合流する
  - **T-03 との重複整理**: [T-03](#t-03)（E2E テスト導入の検討）と機構が大きく重なる。本 T は「オンデマンドの確認パス」、T-03 は「CI で回る自動テスト」で目的が違うが、**片方を作ればもう片方はその上に乗る**。別々に進めると二重投資になるため、着手時にどちらを土台にするかを決める
  - 起動の契機: 機能完成時（`spec-reviewer` / `test-reviewer` と並列）か、オーナー動作確認の直前か
- 前提: dev サーバと開発DBが必要。T-34（完了）で worktree でも `npm run dev` が本体（:3000）とは別のポートで立つようになったため、**ワーカーからも実行しうる**（ただし開発DBは本体と共有なので、下の「実データを壊さない担保」が未決のうちはヘッドに限るのが安全。worktree 同士のポートは重複しうる＝[T-40](#t-40)）
- 着手条件: UI の回帰を実機確認で取りこぼした事例が出たとき。または T-03 を検討するとき（機構が重なるため）
- 関連: T-03 / [完了記録](./closed_23_技術改善バックログ.md) T-34（dev サーバの並列化・DBは共有） / [アーキテクチャ定義書](../仕様/15_アーキテクチャ定義書.md) §8 / [定義書16](../仕様/16_git運用と並行開発体制定義書.md) §2・§3.2

### T-40

- 背景: `scripts/wt-new.sh` は dev ポートを **worktree 作成時点で 3001 から空きを探して** `.env.worktree` の `DEV_PORT` に焼き込む。dev サーバを立てずに worktree を続けて作ると全部が同じ 3001 になり、後から2つで `npm run dev` すると衝突する。2026-07-26 の T-39 第2バッチで worktree を6つ作り、**6つすべてが 3001** になって顕在化した——T-34 が言う「固有ポート」は、作成時点で他の dev サーバが動いていた場合にだけ固有になる
- 実害の程度: ワーカーは lint / build / test で完結し dev サーバを使わないため、並行実装そのものは妨げない。効くのは**オーナーが複数ブランチの画面を同時に確認したいとき**（片方を止めれば回避できる）
- 対応方針の候補（着手時に決める）:
  - **ブランチ名のハッシュから決める**（例 `3001 + hash % 90`）— 作成順に依存せず冪等で、`.env.worktree` へ焼き込む今の形をそのまま使える。衝突確率は残るが同時に扱う worktree が数個なら実用上足りる
  - **起動時に探す**（`scripts/dev.sh` が `DEV_PORT` を起点に空きを探す）— 実際に衝突しない保証は得られるが、表示ポートが起動のたびに変わり `wt:new` が案内した URL と食い違う
  - 併用（作成時はハッシュで焼き、起動時に埋まっていたらずらす）が素直かもしれない
- 着手条件: 2つ以上の worktree で dev サーバを同時に立てたくなったとき

- 背景: `wt-new.sh` の起点は既定でローカル `main`。**ローカルが origin より進んでいても検査せず worktree を作る**ため、未 push のコミットがそのまま全ブランチに複製される。2026-07-26 の T-39 第2バッチで実際に踏んだ——docs コミット1本（§8 の改訂）が未 push のまま6ブランチの起点になり、**6つの PR すべてに同じ docs 変更が写り込んだ**（GitHub は `origin/main` と比較するため）。ローカルで `main...branch` を見ると差分が出ないので、**ヘッドの検査では気づけずオーナーが PR 画面で発見した**

- 対応方針: ①読み取り中心の調査は `Explore`（読み取り専用・結論だけ返す）を既定にし、`general-purpose` は**編集を伴う自己完結タスクに限る** ②`general-purpose` を機械的な作業に使うときは起動時に `sonnet` を明示する ③タスクの切れ目で文脈を切る（150k 超が消費の7割）
- 見送った案: **レビュー系5本を sonnet へ落とす**。opus 指定の3本を全部落としても 9% しか動かず、節約が小さすぎて品質との取引が成立しない。とくに `test-reviewer`（レビュー中最大の 5%）は「実装をどう壊しても緑のままではないか」という反実仮想の推論が本体で、**見逃しが「指摘なし」と区別できない**沈黙する失敗になる。判断の経緯は[決定ログ](./log_23_技術改善バックログ.md)
- 関連: T-67（同じ日に同じ確認から出た別件） / [git運用と並行開発体制定義書](../仕様/16_git運用と並行開発体制定義書.md) §2〜§5（並行開発時のワーカー）

### T-67

- 背景: `verifier` は5本のサブエージェントで唯一 `Bash` による書き込み・実行の権限を持つ。2026-07-26 に**2度**、自分に課した制約を破って作業ツリーを壊した——①変異テストのために `git stash` → `git reset --hard` し、stash を戻さず終了（メインセッションの未コミット25ファイルが一時的に消失。`git stash pop` で復旧）②同日、変異を「Edit で1か所」ではなくスクリプトで一括適用し、停止時に戻さず `src/app/_testing/next-navigation.ts` に残した。**いずれも引き金は変異テスト（コードを壊してテストが落ちるか確かめる）を依頼したこと**
- 実害: メインセッションの未コミット作業の消失。①は気づかなければ数十ファイルを失っていた。②はツリーが汚れたまま次の作業に入る
- 対応方針: **`verifier` の責務から変異テストを外す**。禁止条項を積み増しても、破れる能力が残っている限り同じ事故が起きる（①のあとに条項を足したうえで②が起きた）。変異テストが要るときはメインセッションが Edit で行う——差分がチャットに出るので、戻し忘れもオーナーから見える（CLAUDE.md「規約」のスクリプト一括置換禁止と同じ理由）
- 優先度の根拠: 失うのが未コミットの作業で、復旧手段が `git reflog` / `git stash list` を思いつけるかに依存する。実際に2回踏んでいる
- 関連: T-66 / T-65（同じく `verifier` 運用から出た件）
