## T-25 データバックアップの自動化（暗号化確定・保存先2案は保留）

- 種別: ツール整備（当初は調査）/ 優先度: 中 / 状態: 未着手（暗号化方式は確定・保存先は保留）
- 背景: N-06 のバックアップ取得は手動（週次目安）で、取り忘れた期間はどこにも退避が無く Neon の PITR/履歴保持の窓を超えると復元不能になる。GitHub Actions cron で定期取得を自動化し取得漏れをなくしたい（README・要件定義書 §6 とも「運用の負担を見て判断」に留めていた）
- 方式: 難所は「取得の実行」ではなく **public リポジトリで実データを含むダンプをどこへどう置くか**。これを (1) 暗号化 (2) 保存先 に分解し、**`age` 非対称暗号（公開鍵はコミット可・復号鍵は CI に載せない）で秘匿を保存先に依存させない**設計に**確定**。保存先はクラウドオブジェクトストレージを前提に **案B（Cloudflare R2 / Backblaze B2・静的キー）と案C（AWS S3 / GCP GCS・OIDC/WIF で静的キーレス）を併記し、採用は保留**（両クラウド未保有につき、課金アカウントを作る段で B/C を確定）。差は CI 認証とセットアップの重さで機能・コスト差は極小データではほぼ無い。**詳細は [33_データバックアップ自動化検討.md](../検討/33_データバックアップ自動化検討.md) が正**
- 実装: 未着手（本 T は方式決定まで）。着手する場合は age 鍵ペア・`BACKUP_DATABASE_URL`（unpooled）シークレット・保存先（案B＝バケット＋静的キー／案C＝バケット＋OIDC/WIF 設定）・lifecycle rule・`.github/workflows/db-backup.yml`（`schedule`＋`workflow_dispatch`／`pg_dump`→age→upload／失敗通知）を用意する（検討ドキュメント §5・§7）。定期実行のため**承認ゲートは付けず**「非 PR イベント限定＋最小権限＋失敗通知」で担保する
- 着手条件: 手動運用の取得漏れが実害になり始めた／週次取得の手間を恒常的に感じるとき
- 関連: [完了記録](./closed_23_技術改善バックログ.md) T-22（スキーマ更新のリモート化・同型の作業場）/ [README](../../README.md)「バックアップ（N-06）」/ [データモデル定義書](../仕様/14_データモデル定義書.md) §6

## T-37 実装後のブラウザ実機確認を仕組み化する（Playwright・テストではない）

- 種別: ツール整備 / 優先度: 中 / 状態: 未着手
- 背景: presentation は自動テストの対象外（[アーキテクチャ定義書](../仕様/15_アーキテクチャ定義書.md) §8）のため、UI の挙動はオーナーの動作確認だけが網になっている。2026-07-25 に FB-51 で **Playwright による実機測定が2回とも決定的だった**——①「画面下部でポップオーバーが上向きに反転しない」の原因は、コードを読んで立てた仮説3つ（アンカーが想定外の祖先／実は反転不要／sticky ヘッダ未考慮）が**すべて外れ**で、測って初めて「アクティブ候補の `scrollIntoView({block:"nearest"})` が祖先＝ドキュメントまでスクロールし、反転判定が見る幾何情報を書き換えていた」と分かった ②修正後も測定で「ページのスクロール量0・パネル内だけが動く・上向きを維持」を確認できた。手作業で都度組むのは惜しい
- 方式の推し: **サブエージェント**（CLAUDE.md のレビュアー表に1行増える形。`verifier` が機械的検証、`spec-reviewer` が docs 整合、という既存の責務の切り方と揃う）。スキルにするとメインセッションが手順を踏む形になり、長いブラウザ操作でコンテキストを消費する
- 先に決めるべき論点:
  - **判定対象の線引き**: 幾何・スクロール量・クラスの有無・キーナビの追従・コンソールエラーの不在など**機械的に真偽が決まるもの**に限る。「色が見づらい」「2行になって気になる」は知覚の判断で代替できない（FB-52 の色・FB-51 のラベル折り返しはいずれもオーナーの実機知覚で決まった）。ここを曖昧にすると「確認したことになっている」状態を作る
  - **実データを壊さない担保**: 破壊的操作（打刻 `B`/`F`・削除 `D`・複製 `Y`）を禁じるか、専用の開発DBに向けるか。後者は **T-34 の「どのDBを向けるか」と同じ論点**に合流する
  - **T-03 との重複整理**: [T-03](#t-03-e2e-テストplaywright導入の検討)（E2E テスト導入の検討）と機構が大きく重なる。本 T は「オンデマンドの確認パス」、T-03 は「CI で回る自動テスト」で目的が違うが、**片方を作ればもう片方はその上に乗る**。別々に進めると二重投資になるため、着手時にどちらを土台にするかを決める
  - 起動の契機: 機能完成時（`spec-reviewer` / `test-reviewer` と並列）か、オーナー動作確認の直前か
- 前提: dev サーバと開発DBが必要。T-34（完了）で worktree でも `npm run dev` が本体（:3000）とは別のポートで立つようになったため、**ワーカーからも実行しうる**（ただし開発DBは本体と共有なので、下の「実データを壊さない担保」が未決のうちはヘッドに限るのが安全。worktree 同士のポートは重複しうる＝[T-40](#t-40-worktree-の-dev-サーバポートが並行時に衝突する)）
- 着手条件: UI の回帰を実機確認で取りこぼした事例が出たとき。または T-03 を検討するとき（機構が重なるため）
- 関連: T-03 / [完了記録](./closed_23_技術改善バックログ.md) T-34（dev サーバの並列化・DBは共有） / [アーキテクチャ定義書](../仕様/15_アーキテクチャ定義書.md) §8 / [定義書16](../仕様/16_git運用と並行開発体制定義書.md) §2・§3.2

- **第2バッチで得た教訓（次に並行でテストを書くとき効く）**:

  - **盾が二重にあるとき、合成側のテストは弱い方の盾に隠れる**。FB-42（確定の `Enter` が背後の打刻へ抜ける）は `select-popover` の `stopPropagation` が防いでいるが、`daily-board` 経由では `setEditing(null)` が React の自動バッチで同一 dispatch 中に反映されず、`use-daily-shortcuts` の `editing` ガードだけで防げてしまう——**`stopPropagation` を外しても緑のまま**（変異で実測）。盾ごとに観測可能な段へテストを置く。段3への申し送りは [T-03](#t-03-e2e-テストplaywright導入の検討) に記録

  - **エラー表示と `isPending` の解除は別のタイミングで届く**。マスタ管理のテストで「文言が出た瞬間に他行のセルを `click` すると、まだ `disabled` のままで無視される」flake を踏んだ（約2割の頻度で赤。実装は正しくテスト側の競合）。**エラー文言の出現だけを待って次の操作へ進まない**——押せる状態に戻るまで待つ

## T-46 `wt:new` が未 push のローカル main を起点にしても警告しない

- 種別: ツール整備 / 優先度: 中 / 状態: 未着手
- 背景: `wt-new.sh` の起点は既定でローカル `main`。**ローカルが origin より進んでいても検査せず worktree を作る**ため、未 push のコミットがそのまま全ブランチに複製される。2026-07-26 の T-39 第2バッチで実際に踏んだ——docs コミット1本（§8 の改訂）が未 push のまま6ブランチの起点になり、**6つの PR すべてに同じ docs 変更が写り込んだ**（GitHub は `origin/main` と比較するため）。ローカルで `main...branch` を見ると差分が出ないので、**ヘッドの検査では気づけずオーナーが PR 画面で発見した**
- 実害: 内容の巻き戻りは起きない（git は3方向マージなので、ブランチが変更していないファイルを古い版へ戻さない）。効くのは①PR の差分が汚れてレビューしづらい ②同じコミットが N 本の PR に重複して乗る ③マージ後にローカル main を rebase する際、既に適用済みのコミットの扱いで履歴が濁る
- 対応方針: `wt-new.sh` の起点解決時に `git rev-list --count origin/<base>..<base>` を見て、**0 でなければ警告して中断**する（`--allow-unpushed` 等で明示的に上書きできる逃げ道は残す）。スクリプト冒頭の「起点を最新にしたい場合は実行前に fetch / pull しておくこと」というコメントは**人間向けの注意で機械的な担保が無い**のが原因なので、そこを検査に変える
- あわせて検討: `origin/<base>` 自体が古い（fetch していない）場合も同様に危ういため、`git fetch` を内部で1回打つか、`--no-fetch` を既定にするかを着手時に決める
- 着手条件: 次に並行開発をするとき（同じ手順を踏むため）。単独モードでは worktree を作らないので急がない

## T-47 時刻の「表示は Asia/Tokyo 固定・入力解釈はローカル」が非対称

- 種別: 保守性 / 優先度: 低 / 状態: 未着手
- 背景: 表示側の `src/app/_lib/format.ts` は `APP_TIME_ZONE = "Asia/Tokyo"` を `Intl` に渡して**固定**で整形する一方、入力側の `applyClockTime`（`domain/task/punch-edit.ts`）は `Date#setHours` ＝**実行環境のローカルタイムゾーン**で解釈する。**JST で動く限り両者は一致するので実害は無い**が、前提が食い違っていること自体がコードから読み取れない
- 顕在化した経路: T-39 第2バッチ③のテストがこの非対称に足を取られ、UTC の CI で1件が反転して落ちた（JST では「開始 09:00 に対して 08:00 は前」、UTC では「開始 00:00 に対して 08:00 は後」）。テスト側は「表示を見るデータは JST 固定の壁時計・入力解釈を見るデータはローカルの壁時計」と使い分けて解決済み（②のワーカーは最初からこの使い分けができていた）
- 判断が要る点: **どちらに寄せるか**。①アプリ全体を Asia/Tokyo 固定にする（`applyClockTime` にタイムゾーンを渡す）②ブラウザのローカルに従う（`format.ts` の固定をやめる）。②は「海外に出たとき表示が現地時刻になる」という**挙動の変更**なので、そちらへ倒すなら本書ではなく要求軸（FB）へ移す。日界（`task_date` は保存された論理日付）の設計とも絡む
- **着手の順序（振り分けを先に決める）**: ①か②かは**オーナー判断が先**で、②（ブラウザのローカルに従う）なら挙動の変更になるため**本 T を取り下げて FB へ起票し直す**。①（Asia/Tokyo 固定に寄せる）なら本 T のまま実装に進む。判断前に手を動かさない
- 着手条件: 上の振り分けを決めるとき。きっかけは「時刻まわりを別件で触る」または「JST 以外の環境でアプリを開く可能性が出た」
- 関連: [T-43](#t-43-テストヘルパファクトリを集約する)（この非対称のせいで `at()` が同名・別契約で2つ存在し、素朴に統合すると CI が落ちる） / [データモデル定義書](../仕様/14_データモデル定義書.md)（`task_date` は打刻時刻から導出しない） / T-39 第2バッチ③
