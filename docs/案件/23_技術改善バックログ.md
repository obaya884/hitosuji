- 優先度: `高` / `中` / `様子見`
- 状態: `未着手` / `進行中` / `完了` / `保留`
- **完了になったエントリは、状態更新と同じコミットで[closed_23_技術改善バックログ.md](./closed_23_技術改善バックログ.md)へ移す**（本書には未着手・進行中・保留だけを残す）

## T-31 `updated_at` 比較に依存する統合テストの flaky 解消

- 種別: 改善（テスト補強）/ 優先度: 中 / 状態: 未着手
- 背景: `src/infrastructure/db/repositories/drizzle-section-repository.int.test.ts` の更新系テストが低頻度で落ちる（`expected <挿入時の updated_at> to be greater than or equal to <更新後の updated_at>`。再実行では緑）。原因は**時刻源が2つある**こと——挿入時の `updated_at` は DB の `now()`、更新時はアプリの `new Date()` で、コンテナとホストの時計が 1ms 単位で前後しうる。テスト内のコメントは「同一ミリ秒で等値になりうる」ケースだけを想定しており、逆方向のずれ（更新後が挿入時より前になる）を見落としている
- 対応方針: 時刻の**大小関係に依存しない検証**へ替える（更新後の `updated_at` が非 null であること・更新前の値と異なることなど）。時刻源そのものを片方へ寄せる（更新も DB の `now()` にする）のは挙動に触るため本 T の範囲外
- 規模: **1ファイル1行**。`grep` で確認したところ `updated_at` の大小比較を持つ統合テストは `drizzle-section-repository.int.test.ts:57` のみで、他の4リポジトリ（mode / project / routine / task）には同種の比較がない（起票時に書いた「他のリポジトリも横断して洗う」は空振り）。挙動に触れないテストの修正なので、[定義書16](../仕様/16_git運用と並行開発体制定義書.md) §1.1 のルーティングでは `main` 直コミットに収まる。ワーカーへ配るには小さすぎる
- 着手条件: 即（CI の偽陽性は並行開発でマージ判断のノイズになるため後回しにしない）。ただし並行作業中はヘッドがコードを編集しないため、**単独モードに戻った時点で処理する**
- 発見: F-212 実装時の `test-reviewer` レビュー（2026-07-25）。F-212 の差分とは無関係の既存問題

## T-32 `wt:rm` が worktree ディレクトリを消し残す

- 種別: ツール整備 / 優先度: 中 / 状態: 未着手
- 背景: `scripts/wt-rm.sh` の `git worktree remove` が **"Directory not empty" で落ちることがある**。2026-07-25 の並行3本（F-120・F-212・F-121）で **2件失敗・1件成功**と再現性が不定。失敗すると、その手前のテストDB 削除と worktree registration の解除までは通っているため**ディレクトリだけが残り**、ローカルブランチの削除も手作業になる。残骸は `node_modules` を欠いた状態でエディタの型チェック対象に残り続け、大量の偽エラーを出す
- 切り分け済み: **git の clean 判定による拒否ではない**。`node_modules` や `.next` は gitignore 対象なので `git status --porcelain`（スクリプト自身のチェックと git 内部のチェックの両方）を妨げない。落ちているのは**ディレクトリの再帰削除そのもの**で、削除中に何かがファイルを保持・再作成していると見られる（有力なのは worktree を開いたままのエディタの TS server。失敗した2件はいずれもエディタが当該 worktree の診断を出し続けていた）
- 対応方針: **`git worktree remove --force` を無条件に付ける形は採らない**（「dirty なら中断し `--force` は設けず、防護は git の安全装置に寄せる」という [定義書16 決定ログ](../仕様/log_16_git運用と並行開発体制定義書.md) 2026-07-25 の判断に反する）。tracked の変更による dirty 判定は現状のまま中断としたうえで、**削除を再帰削除の失敗に耐える形にする**（削除量の大きい `node_modules`・`.next` を先に落としてから `git worktree remove` する／失敗時にリトライする／最後の砦として `git worktree prune` ＋明示削除へフォールバックする、のいずれか。選択は着手時）。**ローカルブランチ削除・親ディレクトリの片付けまで一連で必ず通ること**を完了条件にする
- 着手条件: 即（失敗すると並行開発の後片付けに手作業が入り、残骸がエディタのノイズ源になる）。ただし**他の worktree が生きているあいだは着手しない**——本 T の検証は worktree の作成・破棄とテストDBの削除を実際に走らせる必要があり、スクリプトの不具合が**稼働中の別 worktree やそのテストDBを誤って消す**経路になりうる。並行作業が畳まって worktree が0本になった時点で着手する（`git worktree list` で確認）
- 関連: [定義書16](../仕様/16_git運用と並行開発体制定義書.md) §5-6 / [完了記録](./closed_23_技術改善バックログ.md) T-06（worktree 体制の整備）

## T-34 worktree ごとに dev サーバを立てられるようにする

- 種別: ツール整備 / 優先度: 中 / 状態: 未着手
- 背景: 並行開発で PR が複数同時に上がると、オーナーの動作確認が**直列化**する。現状 dev サーバは本体ワークツリーの1本だけで、確認のたびにヘッドが `git checkout --detach origin/<ブランチ>` で切り替えるため、同時に2本を見比べられない。2026-07-25 の並行4本（FB-48・FB-53・FB-51・FB-54）で実際にボトルネックになった
- 足りないもの（実機で確認済み）: ①**`DATABASE_URL` がない**——worktree には `wt:new` が作る `.env.worktree`（`TEST_DATABASE_URL` 1行・vitest 専用）しかなく、dev サーバが読む `.env.local` は本体ワークツリーにしか存在しない ②**ポートが固定**——`"dev": "next dev"` で常に :3000 のため2本目が起動できない
- 論点（着手時に確定）:
  - **`.env.local` の渡し方**: `wt:new` でコピーするか、本体へのシンボリックリンクを張るか。**リンク推奨**（資格情報のコピーを増やさず、Next の env 読み込み順で `.env.local` が最強という前提も壊さない。`.gitignore` の `.env*` でリンクも git から外れることは確認済み）
  - **ポート採番**: worktree ごとに固定値を割り当てて `.env.worktree` に持たせるか、起動時に空きポートを探すか。`next dev` のポートは env ファイルではなくプロセス起動時のシェル環境か `-p` で決まるため、`scripts/dev.sh` のような薄いラッパを挟む形になる見込み
  - **どのDBを向けるか**: (a) 本体の開発DB（`:5432/hitosuji`）を共有 = 実データの厚みがそのまま使えるが複数ブランチが同時に同じデータを書き換える／(b) worktree ごとに `hitosuji_dev_<task>` を作る = 完全隔離だが `db:seed` のマスタだけでは検証材料が足りず、`createdb -T hitosuji` のテンプレートコピーは**本体の dev サーバが繋いでいると失敗する**（`pg_dump | psql` なら排他不要だが遅い）
  - **プロセスの持ち主**: AI のバックグラウンドから立てると**30分前後で回収される**（2026-07-25 に3回連続で実測。約32分・約29分・約29分でいずれもクリーン終了）。したがって worktree の dev サーバは「オーナーが自分のターミナルで `npm run dev` すれば固有ポートで上がる」形にし、`wt:new` は環境を用意するところまでに留める。AI が代わりに立てるのは短時間の確認に限る
- 着手条件: 次に並行開発を回す前（今回の並行はもう畳む段のため、効くのは次から）
- 関連: **T-32（`wt:rm` の後片付け）と同じスクリプト群（`scripts/wt-new.sh` / `wt-rm.sh`）を触るため、まとめて1本で処理したほうが得**。[定義書16](../仕様/16_git運用と並行開発体制定義書.md) §3（テストDB分離の設計）が隣接する前例

## T-35 並行タスク間のファイル衝突を機械判定する

- 種別: ツール整備 / 優先度: 中 / 状態: 未着手
- 背景: 並行度4本以上を目標にした（[定義書16](../仕様/16_git運用と並行開発体制定義書.md) §2）が、タスク分割時の衝突判定が**ヘッドの目視**に依っている。2026-07-25 の並行4本では `Explore` の調査で FB-48 と FB-51 が `daily-list.tsx` の同じ関数（`TaskRow` 内の10行以内）で衝突することを見つけて直列化できたが、本数が増えれば見落とす。見落とすと「自動マージは通るが意味的に壊れる」形になり、CI では検出できない

## T-36 台帳の行操作をスクリプト化し、表構造を機械検査する

- 種別: ツール整備 / 優先度: 中 / 状態: 未着手
- 背景: 2026-07-25 の1日で、ヘッドが台帳（`docs/案件/21_ユーザーフィードバック.md`）の markdown テーブルを**3回壊した**——①行の削除で「途中から次の行頭まで」をアンカーにして FB-52 の行を切り落とし FB-54 を連結 ②同じ誤りを FB-54 の削除で再演 ③行の追加で「テーブルとセクション見出しを区切る空行」の下に挿入し、テーブルが3つに分断（オーナーがプレビュー崩れとして発見）。いずれも AI が長い1行のテーブル行を扱う際の構造的な失敗で、並行度が上がりヘッドの文脈切替が増えるほど起きやすい
- **本命は検査ではなく操作の自動化**。3件はいずれも判断のミスではなく「1行が千文字を超えるテーブル行を手で編集した」ことが原因で、検査は事後に気づく網にすぎない。手編集という誤りの入り口そのものを消す:
  - **`ledger-move <ID>`** — ライブ台帳の該当行を丸ごと取り出し、`closed_*` の正しい節の末尾へ移す。行の切り出しは ID の完全一致で行い、部分文字列をアンカーにしない（3件のうち2件はこれが原因）。挿入位置はテーブルの内側（最終行の直後）に限り、節見出しとの区切り空行の下に入れない（3件目の原因）
  - **`ledger-set <ID> <状態>`**（あってもよい）— 状態列だけを差し替える。本文列には触らない
  - 記入内容そのものはワーカーの完了報告に含まれる文案を使う（[定義書16](../仕様/16_git運用と並行開発体制定義書.md) §3.4）。スクリプトは「どこへどう置くか」だけを担う
- **検査は網として併設する**: 台帳3冊（21・22・23）と `closed_*` に対し、**①テーブル行の列数が揃っていること ②1行に複数のIDが混入していないこと ③テーブル内に空行がないこと**。実行契機は pre-commit フック（`docs/案件/` に差分があるときだけ）か CI のどちらか（着手時に決める。CI だけだと push まで気づけないが、フックはローカル環境に依存する）。検査は既に ad hoc で3回書いており、そのまま流用できる
- 運用側の規律（スクリプトを使わず手で触る場合の最低線）: **行の削除は行全体＋改行をアンカーにする／行の追加はテーブルの最終行をアンカーにする**——どちらも「テーブルの内側を指す」ことで避けられる
- 着手条件: 即（軽微な整備で、効果はヘッドのミス削減に直結する）
- 関連: [定義書16](../仕様/16_git運用と並行開発体制定義書.md) §2（並行度4本以上の条件④）/ §3.4（記入はヘッド・文案はワーカー。ヘッドの記入は本 T のスクリプト経由で行う前提）

## T-37 実装後のブラウザ実機確認を仕組み化する（Playwright・テストではない）

- 種別: ツール整備 / 優先度: 中 / 状態: 未着手
- 背景: presentation は自動テストの対象外（[アーキテクチャ定義書](../仕様/15_アーキテクチャ定義書.md) §8）のため、UI の挙動はオーナーの動作確認だけが網になっている。2026-07-25 に FB-51 で **Playwright による実機測定が2回とも決定的だった**——①「画面下部でポップオーバーが上向きに反転しない」の原因は、コードを読んで立てた仮説3つ（アンカーが想定外の祖先／実は反転不要／sticky ヘッダ未考慮）が**すべて外れ**で、測って初めて「アクティブ候補の `scrollIntoView({block:"nearest"})` が祖先＝ドキュメントまでスクロールし、反転判定が見る幾何情報を書き換えていた」と分かった ②修正後も測定で「ページのスクロール量0・パネル内だけが動く・上向きを維持」を確認できた。手作業で都度組むのは惜しい
- 方式の推し: **サブエージェント**（CLAUDE.md のレビュアー表に1行増える形。`verifier` が機械的検証、`spec-reviewer` が docs 整合、という既存の責務の切り方と揃う）。スキルにするとメインセッションが手順を踏む形になり、長いブラウザ操作でコンテキストを消費する
- 先に決めるべき論点:
  - **判定対象の線引き**: 幾何・スクロール量・クラスの有無・キーナビの追従・コンソールエラーの不在など**機械的に真偽が決まるもの**に限る。「色が見づらい」「2行になって気になる」は知覚の判断で代替できない（FB-52 の色・FB-51 のラベル折り返しはいずれもオーナーの実機知覚で決まった）。ここを曖昧にすると「確認したことになっている」状態を作る
  - **実データを壊さない担保**: 破壊的操作（打刻 `B`/`F`・削除 `D`・複製 `Y`）を禁じるか、専用の開発DBに向けるか。後者は **T-34 の「どのDBを向けるか」と同じ論点**に合流する
  - **T-03 との重複整理**: [T-03](#t-03-e2e-テストplaywright導入の検討)（E2E テスト導入の検討）と機構が大きく重なる。本 T は「オンデマンドの確認パス」、T-03 は「CI で回る自動テスト」で目的が違うが、**片方を作ればもう片方はその上に乗る**。別々に進めると二重投資になるため、着手時にどちらを土台にするかを決める
  - 起動の契機: 機能完成時（`spec-reviewer` / `test-reviewer` と並列）か、オーナー動作確認の直前か
- 前提: dev サーバと開発DBが必要。ワーカーの worktree では `.env.local` がなく動かせないため、**現状はヘッドだけが実行できる**（T-34 が入れば緩む）
- 着手条件: T-34 の方式が固まったあと（DB の論点を共有するため）。または UI の回帰を実機確認で取りこぼした事例が出たとき
