# ユーザーフィードバック管理簿

- 作成日: 2026-07-20
- 目的: 実運用で得たオーナーの気づきを一元管理し、今後の開発の入力にする

## 運用ルール

1. 気づきはまず本書に**起票**する（粒度はバラバラで良い。会話で出たものは AI が転記する）
2. 起票時に**分類**する: `不具合` / `改善（軽微）` / `改善（要仕様整理）` / `要求（優先度変更含む）` / `開発環境`
3. 対応するときは通常の開発ルールに従う — **挙動レベルの変更は該当仕様書を先に更新**し（下記「着手手順」）、本書には対応結果と参照先だけを残す
4. 状態は `未対応` / `対応中` / `対応済み` / `見送り` の4つ。対応済み・見送りには日付と理由（または反映先）を書く

## 着手手順（FB → 仕様書 → 実装）

FB は「画面の話」として書かれるため、**画面定義書だけ直して上位文書に反映し忘れる**事故が起きやすい（2026-07-20 に F-306 で発生。指摘を受けて是正）。着手時は必ず上から順に判定する。

### 手順1: 既存の要求（F-XXX / N-XX）に当てはまるか判定する

`docs/仕様/要求定義書.md` §6 を検索し、この FB が実現しようとしていることが**既存要求の範囲に収まるか**を確かめる。

- **収まる** → 手順2へ（要求定義書の変更は不要）
- **収まらない** → **要求定義書に新しい ID を起こす**（要求文と優先度のみを表に書く）。例: FB-10「ルーチン一覧のソート軸選択」は F-303「一覧・編集・有効/無効切替」に含まれないため F-306 を新設した
- **既存要求の優先度を上げ下げする** → 要求定義書の優先度列の値だけを差し替える

> **理由は表に書かず、要求定義書 §10 決定ログ（[log_要求定義書.md](../仕様/log_要求定義書.md)）へ日付付きで積む**（表を読める状態に保つため。CLAUDE.md「書き方の規約」）。要件定義書・画面定義書も同様に、各文書と同階層の `log_<文書名>.md` へ書く。

### 手順2: 要件定義書へ反映する

- 要求IDを**新設・優先度変更**したなら [要件バックログ](./要件バックログ.md) の該当レーン（確定・着手待ち／候補・見極め中／監視項目）へ反映する（旧「§3 のフェーズ表」は廃止。要件定義書 §3＝開発の現況は散文のみで個別ID一覧を持たない）
- §5 の該当節に、挙動の要件を1行以上書く（画面の詳細ではなく「何がどうなるか」）

### 手順3: 画面定義書へ反映する

- 対象画面の本文（表示要素・操作仕様）に詳細を書く
- ヘッダの「対応要求」行に要求IDを追記する
- 判断が分かれた点は**理由と日付**を添える（後から読んで再現できるように）

### 手順4: データモデル定義書（列やテーブルが増減する場合のみ）

### 手順5: 実装 → 本書の状態を更新

対応済みにするとき、**どの文書のどこに反映したか**を状態欄に書く。

> チェック: 実装に入る前に「要求定義書 → 要件定義書 → 画面定義書」の3階層すべてを見たか？ 画面定義書しか触っていないなら、手順1の判定を飛ばしていないか確認する。
