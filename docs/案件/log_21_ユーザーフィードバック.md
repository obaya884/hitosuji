# ユーザーフィードバック管理簿 決定ログ

- 対象: [ユーザーフィードバック管理簿](./21_ユーザーフィードバック.md)の運用ルールをなぜそう定めたか
- 本文には現在のルールだけを書き、経緯は本書へ日付順に積む（CLAUDE.md「書き方の規約」）

## 2026-07-26 一覧を索引に分け、詳細を `### FB-XX` 節へ出した（4列 → 5列＋詳細節）

**背景**: T-39（コンポーネントテスト整備）で FB を12件まとめて起票した結果、`内容` 列に1,000字を超えるセルが並び、**表として読めなくなった**。1件ずつは正当な調査結果（詰める点の列挙・関連 FB との統合可否）で削るべき情報ではないが、一覧を開いたときの認知負荷が実務に耐えなくなった。オーナーの申告で判明。

**決定**: 1エントリを「§一覧の1行」＋「§詳細の1節」に分け、一覧は `ID / 起票日 / タイトル / 詳細 / 状態` の5列の索引に徹する。詳細節の項目は `現象 / 原因 / 対応方針 / 詰める点 / 発見 / 関連` の6語に固定した。

判断の根拠:

- **分けたのは「読む目的が2つある」から**。候補を選ぶとき（`next-task`）に要るのは ID・タイトル・状態だけで、詰める点まで読むのは着手対象を1件に絞ったあと。同じ表に両方を載せていたのが誤りだった
- **詳細の置き場所は同ファイル下部の節にした**（別ファイル `detail_21_*.md` は不採用）。ライブ台帳を最小に保つ点では別ファイルが優るが、`detail_` プレフィックスを CLAUDE.md の命名規約に足す必要があり、`closed_21` への移動が3ファイルに跨る。台帳23 が既に `## T-XX` 節＋アンカー参照で回っており、**同じ形に揃えるほうが規約の数を増やさない**
- **詳細節の見出しは ID のみ**（`### FB-68`）。タイトルを重ねると改題のたびにアンカーが壊れ、一覧との二重管理にもなる。台帳23 の `#t-42-server-action-の…` 形式の弱点を繰り返さない
- **分類と状態は詳細節に書かない**。分類は節の位置、状態は一覧の状態列が正。詳細にも書くと必ず食い違い、`ledger:move` が2か所を書き換える必要も出る（「同じ規則を2か所に書きたくなったら下位に寄せる」の適用）
- **項目語を固定したのは、書き手が AI だから**。自由記述のままだと粒度が起票ごとに揺れ、読む側が毎回どこを探すか判断させられる。該当しない項目は省く（空欄で残さない）ことにして、固定と省略可を両立させた

**移行範囲**: ライブ台帳の13件のみを新書式へ移した。`closed_21` の既存エントリ（60件超）は旧4列のまま[旧書式の記録](./closed_21_ユーザーフィードバック.md#旧書式の記録2026-07-26-以前)へ束ねて凍結し、書き換えていない。**過去の完了記録は読み返す頻度が低く、書き換えると原文性が失われる**ため。以後 `closed_21` へ移すエントリは新書式で §一覧・§詳細に積まれ、同ファイル内に2つの書式が共存する（これは意図した状態）。

**道具の追随**: `ledger:move` は行と詳細節の両方を移すよう作り直し、`ledger:check` に「一覧の行と詳細節が1対1か」「詳細列のリンク先が自分の ID を指すか」の2検査を足した。**新書式の主な事故は片方の置き忘れ**であり、そこだけは機械で押さえる（旧書式で長大な1行を手編集して3件壊した実績があり、同じ轍を踏まない）。
